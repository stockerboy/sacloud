### ④ `<a>` 에 준 색이 **한 개도 안 먹고 있었다**

> a:hover{color:var(--color-accent)}  살아 있다
> ```
> 즉 **의도한 대로 정확히 반영됐다.** 남은 것은 눈으로 보는 확인 사살뿐이다.

### ⑥ 선수 상세도 **운영에서 500 이었다** — 이쪽이 더 나빴다

클랜 상세를 고치고 **같은 방법으로**(캐시 우회 + 가장 무거운 대상) 훑다가 찾았다.
선수 상세는 엣지 캐시가 아예 없어서 **사용자가 그대로 맞는다.**

```
운영 DPL 상위 6명    4명이 500 (11~22초)
운영 열산 상위 4명    **4명 전부 500** (11~17초)
```

가지별로 재니 범인이 하나였다 — **`playerTraits`(육각형) 6.6초.**
나머지 넷(누적·폼·오늘·티어별)을 다 더해야 0.7초다.

육각형 백분위는 **그 리그 같은 무기 선수 전원의 분포**가 있어야 나온다. 그래서 리그
전체 참가기록을 통째로 집계하는데, 열산은 200만 행이다. 프로세스 안 캐시가 있지만
**서버리스는 매번 차갑다 — 캐시는 콜드 스타트를 못 덮는다.**

```
                     전              후
열산 상위 4명    전부 500      →   대부분 200 (1.4~9.3초)
DPL 상위 8명     4명 500       →   전부 200 (1.1~6.6초)
로컬 playerTraits  6.6초       →   1.05초
```

인덱스 하나(`matchId` 에 `playerId·weapon·kill·damage` 를 얹어 index-only)와,
**선수 상세에도 엣지 캐시**를 붙였다 — 인덱스로도 콜드 첫 요청은 무겁고, 그 한 번을
엣지가 덮는다.

> **두 장애를 같은 방법으로 찾았다** — 캐시를 우회해서, 가장 무거운 대상으로.
> 앞서 캐시 HIT 값을 보고 「1.2초」로 넘어갔던 것이 **둘 다 숨기고 있었다.**

**고친 뒤 표본으로 확인했다 (05:35 · 전부 캐시 우회):**
```
클랜 상세  세 리그 30곳   30/30 = 200
선수 상세  두 리그 30명   30/30 = 200
그 밖      기록실 · 매치 상세 · 지난시즌 · 참여리그 · 통합래더 · 무소속래더 · 폼랭킹
           전부 200 (0.17 ~ 5.6초)
선수 상세 엣지 캐시  MISS 5.7초 → HIT 0.25초
```

> **곁다리 — B팀이 한 시간 전에 문서화한 함정을 내가 그대로 밟았다.**
> 이 표본 검사를 처음 돌렸을 때 **30곳이 전부 `000`** 이 나왔다. 원격을 의심할 뻔했는데,
> B팀의 규칙(**「우리가 보낸 바이트를 먼저 본다」**)대로 `cat -A` 로 URL 을 찍으니
> `.../clans/lpcrew^M/show` — Windows 파이썬이 `` 을 붙이고 있었다.
> `tr -d ''` 하나로 30/30 이 됐다. **같은 함정에 두 사람이 두 시간 안에 걸렸다.**

### ⑦ 서브내비 **활성 밑줄이 그려진 적이 없다** (D팀 · 07:00)

D팀이 ④(색 유틸리티)를 렌더로 확인하다가 **그 자리에서** 찾았다.

```
활성 탭의 borderBottomColor        rgba(0,0,0,0)   ← 투명
border-b-transparent 만 떼면        rgb(217,43,43)  ← 진홍이 돌아온다

### ⚠ 그리고 같은 함정의 **세 번째 사례** — 임계값을 고장난 상태로 쟀다

C팀이 신선도 알람 임계값을 **실측으로** 정했다(추측하지 않으려고). daerule 은
최근 8일 최대 공백이 116시간이라 `168h` 로 느슨하게 잡았다.

**그런데 체인이 돌아 빠진 경기가 들어오자 그 최대 공백이 116.3h → 46.5h 로 바뀌었다.**

즉 임계값을 정할 때 쓴 분포는 **수집이 멈춰 있던 기간의 분포**였다.
**고장난 상태를 정상으로 재서 기준을 세운 것**이고, 지금 값은 너무 느슨할 수 있다.

> **오늘 밤 같은 함정에 세 번 걸렸다.**
> ```
> C팀  러너 지연 가설      실은 데이터 양이었다        (A/B 로 반증)
> 나   「클랜 상세 1.2초」  실은 캐시 HIT 를 잰 것       (두 장애를 숨겼다)
> C팀  신선도 임계값        실은 고장난 기간을 잰 것     (기준이 느슨해졌다)
> ```
> 셋 다 같은 문장으로 요약된다 — **잰 것이 내가 재려던 그것인지 먼저 확인하지 않았다.**
> 숫자가 나왔다는 것과 그 숫자가 내가 묻는 질문의 답이라는 것은 다르다.

**지금 고치지 않았다.** 깨끗한 데이터가 아직 하루치도 없어서, 지금 임계값을 다시 잡으면
같은 실수를 반복한다. 체인이 하루쯤 정상 가동한 뒤 세 리그 간격 분포를 **다시 재서**
고쳐야 한다 — 아침 숙제가 아니라 **내일 할 일**이다.

**폴링 하한은 설계대로 돌고 있다** — 바쁜 리그에서는 아무것도 안 하고, 굶는 리그에서만 채운다.

  참고로 밤 초반(경합이 심할 때) 측정은 **1,335 통과 · 3 실패**였다
- **CSS 수정(④)을 눈으로는 확인 못 했다.** 다만 **운영 CSS 번들에서 규칙 자체는 확인했다** —
  남은 `a{color:inherit}` 은 preflight 것 하나뿐이고 `a:hover` 는 살아 있다.
  즉 「반영됐는가」는 닫혔고, 「보기에 어떤가」만 남았다
- **커버링 인덱스를 안 만들었다.** 순간 700MB 여유가 필요한데 Supabase 실제 할당량이
  SQL 로 안 읽힌다

**뒤집은 판단 (그대로 적는다)**
1. **「넥슨이 연결을 막았다」 → 우리 버그였다.** Windows 파이썬이 URL 목록에 CRLF 를
   붙였고 curl 이 `\r` 을 물고 나갔다. `od -c` 로 확증하고 같은 주소를 다시 쏴서 8/8 로
   반증했다. **없는 위험을 보고하면 다음 사람이 그것 때문에 잘못된 결정을 한다**
2. **「전수 집계가 밀려서 취소됐다」 → 90분 타임아웃이었다**
3. **「daerule 49시간은 밀린 것」 → 정상 분포 안이었다**
4. **「러너가 미국이라 지연이 지배적」 → 반증됐다.** 52초 대 72~108초, 2배지 10배가 아니다.
   원인은 지연이 아니라 **데이터 양**이다
5. **「배틀로그 적재가 1,174행」 → 이미 7,815행이었다.** 기록이 낡아 있었다
6. **「정답 라벨 20명이 없다」 → 파일이 있었다** (23명)
7. **「UI 차이 45건 중 35건 미착수」 → 재감사 결과 유효 1 · 무효 6 · 해소 37**
8. **C팀이 자기 추정을 실측으로 내려잡았다** — 「하루 260사이클」 → 실측 196,
   step 9 예상 20분 → 실측 26.9분
9. **내가 「푸시했습니다」라고 말했는데 안 했다.** B팀이 원격을 직접 확인해 잡았다.
   ⚠ **「했다고 말했는데 안 한 것」은 틀린 판단보다 나쁘다** — 다음 사람이 확인 없이 믿는다.
   원인은 단순하다: `git push` 를 다른 명령과 묶어 돌리고 **출력을 안 읽었다.**
   앞으로 푸시는 원격 해시를 **다시 읽어** 확인한다

## 6. 밤새 어떻게 일했나

사용자가 팀 넷을 켜 주었고, 각 팀이 서브에이전트를 붙였다.

```
나(claude-ce)  성능 · 알 시스템 · 통합 · 배포 · 결정 문서       + 서브에이전트 8
A팀 lg-8f      칭호 인증 · UI 45건 재감사
B팀 lg-68      클랜마크 · CSS 레이어 분석 · 수집 준비
C팀 lg-94      예약 드롭 · 폴링 하한 · 신선도 알람
D팀 lg-c8      렌더 검수 (헤드리스 크롬 CDP 하네스를 직접 만들었다)
```

**밤새 서로를 여러 번 고쳤다. 그게 이 밤의 방법이었다.**
- B팀이 내 「수집 상한 5,000건」 승인을 **거부했다** — *「규모를 줄인다고 성격이 바뀌지
  않는다」*. 옳았다. 내 승인이 사용자 승인이 아니라는 지적도 정확했다
- C팀이 내 D-224 원인 판정을 뒤집었다 (concurrency 가 아니라 90분 타임아웃이었다)
- C팀이 **자기 코드가 만든 버그**를 첫 실전 30분 만에 찾았다 —
  체인을 시각으로 끊는 가드가 「고치려던 병을 하루 한 번 다시 앓게」 하고 있었다
- B팀이 자기 오탐(CRLF)을 스스로 잡아 보고서에서 빼게 했다
- B팀이 **자기 공으로 적힌 것을 정정했다** — 「캐시가 비용을 가린다」는 관점은 자기가
  낸 게 아니라고. 실제로 그쪽이 한 건 **관측(`X-Cache: HIT`)을 해석 없이 날것으로
  남겨 둔 것**이고, 거기서 원인을 본 건 내 쪽이다.
  **해석을 붙이지 않고 숫자를 그대로 남기는 습관이 값을 했다**

> 그리고 **틀린 판단을 고친 것보다, 고쳤다는 사실을 문서에 남긴 것이 더 값지다.**
> D-224 는 3일을 잃었는데 원인이 「빨간 CI 를 아무도 안 본 것」이었다.
> 오늘 밤 뒤집은 일곱 개를 안 적었으면 다음 사람이 같은 자리에서 또 넘어진다.

**A팀과 D팀은 서브에이전트를 못 썼다.** 그 세션들의 설정이 「사용자가 직접 요청하지
않으면 에이전트를 쓰지 않는다」이고, **동료의 메시지는 사용자 승인이 아니다.**
아침에 그 두 세션에 직접 한 줄 쳐 주면 병렬로 전환된다.

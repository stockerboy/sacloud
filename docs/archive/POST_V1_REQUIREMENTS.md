# POST_V1_REQUIREMENTS.md — V1 이후 확정 요구사항

> 작성일: 2026-08-20 · 상태: **확정된 요구사항 / 미구현**

> ## ⚠ 2026-08-20 범위 변경
>
> 아래 **1장(관리자 대시보드) · 2장(시즌 시스템) · 3장(스나이퍼/라이플 래더 분리)** 은
> **V1 필수 범위로 승격**됐다. 더 이상 "V1에서 구현 금지" 대상이 아니다.
> 기존 3rd.supply 데이터 마이그레이션(`docs/IMPLEMENTATION_PLAN_1.md` Phase 8-M)이
> 시즌 스냅샷 · 과거 시즌 조회 · 무기별 분리 기록을 전제로 하기 때문이다.
>
> **4장(유료 상품) · 5장(게임 계정 소유권 인증)** 은 그대로 V1 제외다.

## 0. 이 문서의 위치

- 여기 적힌 기능은 **지금 구현하지 않는다.** 현재 최우선 목표는 여전히 **3rd.supply 기반 V1 복원**이다.
- 이 기능들 때문에 **V1의 UI·기능·흐름을 바꾸지 않는다.** 원본에 없는 화면·버튼·컬럼을 미리 넣지 않는다.
- 이 문서의 목적은 단 하나다: **DB / 시즌 / 유저 / 래더 구조를 설계할 때 나중에 재공사가 나지 않도록** 확장 지점을 미리 알고 있는 것.
- `docs/IMPLEMENTATION_PLAN_1.md` 6장의 `V2 후보`는 "원본 분석 중 발견한 개선 아이디어(미확정)"이고,
  이 문서는 **확정된 요구사항(구현 시점만 V1 이후)** 이다. 둘을 섞지 않는다.
- 스키마를 확정하는 시점(**Phase 7**)과 레이팅·시즌 엔진을 만드는 시점(**Phase 9**)에는 이 문서를 반드시 다시 읽는다.

## 1. 관리자 대시보드

관리자 계정으로 로그인하면 `/admin`에 접근할 수 있다.

### 관리 기능

| 구분 | 기능 |
|---|---|
| 클랜 | 클랜 추가 / 클랜 삭제·비활성화 |
| 유저 제재 | 특정 유저 랭킹 제외 / 랭킹 제외 해제 |
| 유저 제재 | 특정 유저 영구제명 / 영구제명 해제 |
| 제재 운영 | 제재 사유 관리 |
| 감사 | 관리자 작업 audit log |
| 시즌 | 현재 시즌 확인 |
| 시즌 | 시즌 종료·초기화 날짜 및 시간 설정 |
| 시즌 | 시즌 종료 날짜 변경 |
| 시즌 | 필요 시 수동 시즌 종료 |

### 원칙

**삭제 데이터와 관리자 조치는 가능한 한 복구 가능한 방식으로 보존한다.**
하드 삭제를 기본 동작으로 만들지 않는다.

### 설계 시 고려사항 (재공사 방지)

- **하드 삭제를 전제로 스키마를 짜지 않는다.** 클랜·유저·기록 삭제는 상태 전이(soft delete)로 표현할 수 있어야 한다.
  → 삭제 가능성이 있는 주요 테이블에 `deleted_at`(또는 `status`) 자리를 남겨 둔다.
- **"랭킹 제외"는 삭제와 다른 축이다.** 데이터는 남기고 랭킹 집계에서만 빠진다.
  → 랭킹 산출 쿼리·배치가 처음부터 "제외 대상 필터"를 통과하도록 만들어 두면 나중에 조건만 추가하면 된다.
  → V1의 랭킹 배치(Phase 9)를 짤 때 이 필터 자리를 비워 두는 정도만 한다. **기능은 만들지 않는다.**
- **제재는 유저 단위인지 플레이어 단위인지 구분이 필요하다.** (사이트 계정 ↔ 게임 계정은 5장 참조)
- **audit log는 나중에 붙이기가 가장 어렵다.** 관리자 조치가 생기는 시점에 "누가·언제·무엇을·이전 값→이후 값"을
  남기는 공통 경로를 하나 만들고 모든 조치가 그 경로를 지나게 한다.
- 이 문서의 어떤 기능도 **V1 화면에 진입점을 만들지 않는다.** `/admin`은 V1 이후에 생긴다.

## 2. 시즌 시스템

### 요구사항

- 시즌 종료 시 현재 기록을 **단순 삭제하지 않는다.**
- 종료 직전 최종 기록을 **Snapshot으로 저장한 뒤** 새로운 시즌을 시작한다.
- 사용자 페이지에는 각 과거 시즌 기록이 **영구적으로** 남는다.

### 시즌 Snapshot 최소 저장 항목

**공통**
- 시즌 번호
- 최종 통합 순위
- 최종 통합 래더

**스나이퍼 기록**
- Kill
- Death
- KD %
- 승
- 패
- 승률 %
- 스나이퍼 래더 기여값 / 누적값
- 스나이퍼 순위

**라이플 기록**
- Kill
- Death
- KD %
- 승
- 패
- 승률 %
- 라이플 래더 기여값 / 누적값
- 라이플 순위

### 표시 규칙

- **통합 KD는 사용자에게 표시하지 않는다.** (스나이퍼 KD·라이플 KD는 표시한다)
- 통합은 **순위와 래더만** 노출한다.

### 설계 시 고려사항 (재공사 방지)

- V1의 `LeaguePlayerSeason`(지난시즌)은 원본 재현 범위라 **통합 지표만** 담는다.
  위 항목은 그보다 넓으므로, 시즌 스냅샷 테이블을 만들 때 **무기별 지표를 나중에 붙일 수 있는 형태**를 염두에 둔다.
  (지금 컬럼을 미리 만들라는 뜻이 아니다 — 스냅샷을 "행 하나에 통합 지표만" 강하게 못박지 말라는 뜻이다.)
- 시즌 종료는 **배치 작업 + 스냅샷 생성 + 새 시즌 시작**의 3단계다. 종료 시각이 관리자 설정값이고 수동 실행도 가능하므로,
  Phase 9에서 시즌 전환을 만들 때 "시각이 코드에 박히지 않게" 한다.
- 스냅샷은 **집계 결과의 보존본**이다. 원본 매치 데이터는 그대로 두고, 스냅샷을 지우면 다시 만들 수 있는 구조가 안전하다.
- 통합 KD를 저장은 하되 노출만 막을지, 아예 저장하지 않을지는 **[미확정]**. 저장해 두면 정책이 바뀌어도 대응이 쉽다.

## 3. 스나이퍼 / 라이플 래더 분리의 정확한 정의

### 절대 규칙

**새로운 래더 계산 공식을 만들지 않는다.**

- 3rd.supply의 개인 래더 계산 구조를 **가능한 한 동일하게, 하나만** 재현한다.
- 각 경기에서 3rd.supply 방식으로 계산된 `rating_update`를 **그대로 사용한다.**
- 그 다음, 해당 경기의 `weapon` 값에 따라 **기록만 분리한다.**
  - 스나이퍼 경기의 `rating_update` → `sniper_rating_delta`에 누적
  - 라이플 경기의 `rating_update` → `rifle_rating_delta`에 누적
- 스나이퍼와 라이플에 **서로 다른 계산식이나 KD 보정 공식을 만들지 않는다.**

### 통합 래더

```
통합 래더 = 기본 래더 + sniper_rating_delta + rifle_rating_delta
```

- 통합 래더는 모든 경기의 래더 증감값을 합친 결과다.
- **동일한 경기 데이터를 쓰면 통합 래더가 기존 3rd.supply 개인 래더와 같은 결과가 나오는 것이 목표다.**
- 통합 KD는 표시하지 않는다.

### 개인 랭킹 페이지

향후 3개 랭킹으로 분리한다.

- 통합
- 라이플
- 스나이퍼

### 설계 시 고려사항 (재공사 방지)

- 분리는 **계산이 아니라 집계 축**이다. 레이팅 엔진은 하나만 존재하고, 무기 구분은 그 결과를 어느 통에 담을지만 결정한다.
  → Phase 9의 `RatingEngine`을 만들 때 "경기 → 증감값" 단계와 "증감값 → 누적" 단계를 섞지 않는다.
    두 단계를 분리해 두면 이 요구사항은 누적 통을 늘리는 것으로 끝난다.
- `weapon`은 이미 V1 계약에 있다 (`0 = 라이플`, `1 = 스나이퍼`, `MatchPlayerStat.weapon`).
  경기 스탯에 무기 값이 남아 있으면 **과거 데이터도 소급해서 분리 집계할 수 있다.** 이 점이 중요하므로
  V1에서 `weapon`을 누락하거나 뭉뚱그리지 않는다.
- 한 경기에서 무기를 섞어 쓰는 경우의 판정 기준은 **[미확정]**. 원본의 `weapon`이 경기당 단일 값으로 관측되었으므로
  V1은 관측대로 두고, 판정 규칙이 필요해지면 그때 정한다.
- 3개 랭킹은 **랭킹 스냅샷의 종류(kind)가 늘어나는 것**으로 보는 편이 안전하다.
  Phase 9의 `RankSnapshot`에 `kind`(클랜/개인) 축이 이미 있으므로, 여기에 값이 추가되는 형태를 상정해 둔다.
- **V1의 개인 랭킹 화면은 원본대로 1개다.** 지금 탭을 3개로 만들지 않는다.

## 4. 유료 상품

가격은 **초기 가격안**이며 **향후 변경 가능하게 설계한다.** 가격을 코드에 박지 않는다.

### 4-1. 진행 중 시즌 기록 초기화권 — 4,900원

- 자신의 **현재 시즌 기록 전체**를 초기화한다.
- 스나 / 라플 / 통합을 **따로 초기화하지 않는다.** 현재 시즌 전체가 **하나의 단위**로 초기화된다.
- 초기화 이전 데이터는 **운영용 Snapshot / Audit으로 보존**하되 **사용자에게는 표시하지 않는다.**
- **시즌당 기본 1회** 사용 가능으로 설계하되, **설정으로 변경 가능**하게 한다.

### 4-2. 과거 시즌 기록 통합 삭제권 — 9,900원

- 사용자의 개인 페이지에서 **모든 과거 시즌 기록을 숨긴다.**
- 실제 데이터는 운영상 복구를 위해 **soft delete로 보존하는 것을 원칙**으로 한다.

### 4-3. 번들 — 12,900원

- 위 두 상품의 묶음.

### 설계 시 고려사항 (재공사 방지)

- **"사용자에게 보이는 기록"과 "저장된 기록"이 달라진다.** 이것이 이 요구사항의 핵심 파급 효과다.
  → 개인 페이지·랭킹·기록실의 조회 경로가 처음부터 **가시성 필터를 한 곳에서** 통과하는 구조면 나중에 조건만 추가하면 된다.
  → 가시성 필터를 각 화면에 흩어 두면 나중에 전부 고쳐야 한다.
- 초기화는 **삭제가 아니라 "이 시점 이전 기록을 현재 시즌 집계에서 제외"** 로 표현하는 편이 복구에 유리하다.
  구체적 방식은 **[미확정]**.
- 랭킹 집계가 이미 "제외 대상 필터"를 갖고 있으면(1장 참조) 초기화된 사용자 처리도 같은 자리를 쓴다.
- 결제·주문·상품·사용권(entitlement) 도메인은 V1에 존재하지 않는다. **V1에 미리 만들지 않는다.**
  다만 사용 횟수 제한이 "시즌당 N회 / 설정 변경 가능"이므로, 상품 사용 이력은 **시즌 단위로 조회 가능**해야 한다.
- 결제 수단·PG·환불 정책·세금계산은 **[미확정]** — 별도 조사 필요.

## 5. 게임 계정 본인 소유권 인증

### 요구사항

- 현재 시즌 초기화 및 과거 시즌 삭제는 **아무 플레이어에게나 사용할 수 없다.**
- 사이트 로그인 계정과 실제 서든어택 플레이어 계정 / **OUID**의 **소유권 인증이 완료된 경우에만**
  자신의 기록에 사용할 수 있다.
- **동일 OUID가 여러 사이트 계정에 동시에 소유권 인증되지 않도록 한다.**
- 정확한 소유권 인증 방식은 **별도 조사 후 확정한다** — 현재 **[미확정]**.
- **프론트엔드에서 버튼을 숨기는 것만으로 처리하지 않는다.**
  서버에서 로그인 사용자와 인증된 게임 계정 소유자가 동일한지 **반드시 검증한다.**

### 설계 시 고려사항 (재공사 방지)

- V1에도 이미 **서든어택 계정 연동**(`/me/link`)이 있다. 원본 재현 범위의 연동이며,
  **그 연동이 곧 "소유권 인증"인지는 확인되지 않았다 [미확인].** 둘을 같은 것으로 단정하지 않는다.
- 연동 정보를 저장할 때 **OUID(또는 그에 준하는 게임 측 고유 식별자)를 담을 자리**와
  **유일성 제약(동시에 하나의 사이트 계정)** 을 걸 수 있는 형태를 염두에 둔다.
  → Phase 7의 `UserPlayerLink`가 이 자리에 해당한다. 여기에 "인증 완료 시각"과 "해제 이력"을 남길 수 있으면 좋다.
- 소유권 검증은 **서버 측 공통 가드**로 만든다. 화면 조건문으로 흩어지면 나중에 우회 경로가 생긴다.
- 연동 해제 후 재연동, 게임 계정 명의 변경, 계정 도용 신고 시의 처리 정책은 **[미확정]**.

## 6. 현재 작업과의 관계

- 위 내용은 **Phase 1에서 구현하지 않는다.** V1의 어떤 Phase에서도 구현하지 않는다.
- 현재 최우선 목표는 여전히 **3rd.supply 기반 V1 복원**이다.
- V1 작업 중 이 문서를 근거로 **UI를 바꾸거나 기능을 추가하지 않는다.**
  이 문서가 허용하는 것은 오직 **"나중에 확장 가능한 형태로 만들어 두는 것"** 뿐이며,
  그것조차 V1 화면에 드러나서는 안 된다.
- 확장 지점을 고려해야 하는 시점:
  - **Phase 7** (DB 스키마 확정) — 1·2·4·5장의 저장 구조
  - **Phase 9** (레이팅 / 시즌 / 랭킹 배치) — 2·3장의 집계 구조
- 착수 전 확인이 필요한 **[미확정]** 항목: 소유권 인증 방식, 초기화의 내부 표현, 통합 KD 저장 여부,
  무기 혼용 경기의 판정 기준, 결제 수단·환불 정책.

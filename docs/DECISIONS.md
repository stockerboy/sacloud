# DECISIONS.md — 프로젝트 결정 기록

`CLAUDE.md` 3장 11번(중요한 프로젝트 지식과 결정은 문서화)에 따라, **원본 관측으로 정해지지 않아 우리가 결정한 사항**을 남긴다.
여기 적힌 것은 전부 "원본과 동일함이 검증되지 않은" 자체 결정이며, 실측 결과가 나오면 갱신한다.

## Phase 0 (2026-08-20)

### D-001. 저장소 구조 — pnpm workspace 모노레포

```
apps/web/            Next.js 15 (App Router)
packages/contract/   Zod 스키마 + 엔드포인트 레지스트리   ← 단일 진실 원천
packages/mock/       결정적 픽스처 생성기 + MSW 핸들러
```

- 계획서의 `apps/worker`, `packages/db`, `packages/ui`는 **아직 만들지 않았다.**
  각각 Phase 8, Phase 7, Phase 1에서 실제로 필요해질 때 만든다. (지금 만들면 빈 껍데기만 남는다.)
- 내부 패키지는 빌드 단계 없이 `src/*.ts`를 직접 참조한다(`exports` → `./src/index.ts`).
  Next.js는 `transpilePackages`로 컴파일한다. 빌드 산출물 관리 비용을 없애기 위한 선택이다.

### D-002. 계약 표기 규칙

| 항목 | 결정 | 근거 |
|---|---|---|
| 필드명 | 원본 응답 그대로 **snake_case** (`win_rate`, `rating_update`) | 관측된 응답 형태를 유지해야 비교 검수가 쉽다 |
| 식별자 타입 | 전부 **문자열** | 매치 ID가 18자리(`YYMMDDHHmmss`+6)라 `Number.MAX_SAFE_INTEGER`를 넘는다 |
| 날짜/시각 | ISO 8601 + `+09:00` (예: `2026-06-05T00:06:24+09:00`) | 원본 포맷은 `[미확인]`. 계약으로 고정 |
| 파생값 | `win_rate`, `kd_rate`, `kill_per_match`, `damage_percent`를 **응답에 포함** | 원본이 서버 계산인지 `[미확인]`. 계산 규칙을 `packages/mock/src/derive.ts` 한 곳에 두고 Phase 7 서버도 동일 규칙을 구현한다 |
| 커서 | `base64url("next__<id>" \| "prev__<id>")`, 랭킹 20 / 게시판 15 | 관측값. 테스트로 고정 |

### D-003. 엔드포인트 출처 표시 (`origin`)

모든 엔드포인트에 `origin: 'observed' | 'designed'`를 붙였다.

- `observed` — `docs/3rd-supply-structure.md`에 기록된 실제 관측 엔드포인트
- `designed` — 화면 동작은 관측됐지만 경로·본문이 확인되지 않아 **우리가 설계**한 것

`designed`로 표시된 것은 전부 `[미확인]`이며, 실측되면 경로를 바꾼다.
현재 `designed`인 것: 비밀번호 재설정/이메일 인증, 갱신 요청(`/renew`), 플레이어·클랜 설정,
클랜 지난시즌, 리그 참여 클랜원 목록, 맵 목록, 리그 생성·관리 전반, 추천/비추천.

### D-004. 상대팀 결측(`알수없음`) 재현 방식

원본은 상대 클랜 플레이어의 딜량·헤드샷을 `알수없음`으로 표시한다.

- Mock 데이터에는 **양쪽 값을 모두 저장**하고, 응답 단계에서 **보는 쪽이 아닌 팀의 값을 null로 지운다.**
- 매치 상세(`GET /leagues/:leagueId/matches/:matchId`)에는 "어느 기록실에서 펼쳤는지"가 필요해서
  선택 쿼리 `league_clan_id`를 추가했다 — **자체 설계** `[미확인]`.
  원본은 아코디언이라 매치 개별 URL이 없어 이 정보를 어떻게 넘기는지 알 수 없다.

### D-005. 픽스처 정책

- 시드 고정(`FIXTURE_SEED = 20260820`) + 기준 시각 고정(`FIXTURE_NOW = 2026-08-20T12:00:00+09:00`).
  실제 시계를 쓰지 않으므로 스냅샷·테스트가 흔들리지 않는다.
- 규모: 리그 4(단일 1 + N부 3, 공식 2) / 클랜 60 / 플레이어 920 / 매치 3,000 / 게시글 400 / 댓글 1,200.
- 클랜명·닉네임·리그명·게시글 문구는 **전부 새로 만든 가상의 이름**이다. 원본 자산·문구를 복사하지 않았다.
- 클랜마크·업로드 이미지 URL은 존재하지 않는 자리표시자 호스트(`static.sacloud.local`)를 쓴다.
- 래더 증감은 관측 범위(승 +7~+12 / 패 −10~−19)의 **난수**다. **레이팅 엔진이 아니다** — Phase 9에서 다룬다.
- 승/패·킬뎃·래더는 생성된 매치를 시간순으로 누적해서 만들었다. 랭킹과 기록실이 서로 어긋나지 않게 하기 위함이다.

### D-006. 임시로 정한 값 (원본 미확인)

| 값 | 임시 결정 | 실제 확인 필요 시점 |
|---|---|---|
| 배치고사 판정 경기 수 | 10경기 | Phase 9 |
| `hot`(인기) 선정 가중치 | `추천×3 + 댓글×2 + 조회수/100` | Phase 7 |
| 리그맵 목록 | `맵 01`~`맵 08` 자리표시자 | Phase 3 이전 |
| 익명 별칭 형식 | `무명-123` 형태 | Phase 5 |
| 공식 리그 배지 필드명 | `official: boolean` | 실측 시 |
| 에러 응답 포맷 | `{ message, data?, errors? }` | Phase 7 |

### D-007. 툴체인

- **TypeScript는 5.9로 고정.** 최신 7.0.2에서 `next build`가 `next.config.ts`를 읽지 못한다
  (`Cannot read properties of undefined (reading 'fileExists')`). Next 15.5가 TS 7을 지원하면 올린다.
- pnpm 11은 설치 스크립트를 기본 차단한다. `pnpm-workspace.yaml`의 `allowBuilds`로 `msw`(워커 설치)와
  `sharp`(Next 이미지 최적화)만 허용했다.
- ESLint는 flat config 하나(루트)를 쓰고, `apps/web/eslint.config.mjs`는 루트 설정을 재수출한다
  (`next build`가 앱 디렉터리에서 설정을 찾기 때문).
- **Redis / BullMQ / Prisma / PostgreSQL / Auth.js / Tiptap은 설치하지 않았다.**
  각각 Phase 7~9에서 실제로 필요할 때 넣는다.

### D-008. Phase 0 범위에서 하지 않은 것

- 실제 데이터 연결 없음. 넥슨 병영수첩·3rd.supply의 어떤 API도 호출하지 않는다.
- 로그인 상태는 항상 비로그인(`/infos`의 `user: null`). 세션 전환 스위치는 Phase 6.
- 쓰기 계열(POST/PUT/DELETE) 핸들러는 **계약 형태만** 돌려준다. 저장·rate limit·캡차 시뮬레이션은 Phase 5~6.
- 랭킹은 요청 시 정렬한다. 1시간 주기 배치 재현은 Phase 9.
- **광고 관련 요소는 일절 만들지 않았다** (`CLAUDE.md` 4장).

### D-010. `.pc-container` 는 고정폭 1120px 가운데 정렬

원본 CSS 규칙에는 `min-width: 80rem; margin: 0 auto` 만 있지만, **관측된 동작**은 다음과 같다.

- 창이 넓으면 1120px 고정폭으로 가운데 정렬 (뷰포트 1517px에서 좌측 여백 198.5px)
- 창이 1120px보다 좁아지면 줄어들지 않고 넘쳐서 가로 스크롤 (뷰포트 1014px에서 `margin-right: -105.6px`)

`min-width` 만으로는 넓은 창에서 가운데 정렬이 나오지 않으므로 `width: 80rem` + 좌우 `auto` 마진으로 구현했다.
CSS 선언은 원본과 다르지만 **두 경우의 렌더 결과가 모두 원본과 일치**하는 것을 실측으로 확인했다.

### D-011. 상대시간 포맷 규칙

원본 홈에서 관측된 표기는 `6시간 전` `15시간 전` `1일 전` `2일 전` `3일 전` 뿐이다.
`분` `달` `년` 단위와 1분 미만 표기는 해당하는 글이 없어 확인하지 못했다 `[미확인]`.

우리 규칙(`packages/ui/src/common/relative-time.ts`, 테스트로 고정):
`60초 미만 = 방금 전` / `분` / `시간` / `일` / `30일 = 1달` / `365일 = 1년`, 미래 시각은 `방금 전`.
**원본과 동일함이 검증되지 않았다.**

### D-013. Phase 1에서 추가한 것 / 하지 않은 것

- `packages/ui` 를 계획대로 이번 Phase에 만들었다. `next/link`·`next/navigation` 에 의존한다(peer).
- **TanStack Query 도입.** Phase 1에서 실제로 서버 상태(`/boards?category=hot`)를 다루기 시작했기 때문이다.
  커서 무한스크롤(`useInfiniteQuery`)은 Phase 3에서 쓴다.
- Mock(MSW)은 브라우저 Service Worker라 **첫 방문에는 아직 페이지를 제어하지 않는다.**
  그 사이 나간 요청은 가로채이지 못하고 응답 없이 매달린다. `controllerchange` 를 기다렸다가
  준비 완료로 표시하도록 `apps/web/app/providers.tsx` 에서 처리했다. 원본에 대응하는 동작이 아니라
  Mock 단계의 구현상 장치이며, Phase 10(SSR 전환)에서 대부분 사라진다.
- `Skeleton` / `EmptyState` / `ErrorState` 도 같은 성격의 구현상 장치다.
  원본은 SSR이라 로딩·빈 목록·오류 표시를 관측할 수 없었다 `[미확인]`.
- **Playwright E2E와 반응형 스냅샷(1280/1024/390)은 하지 않았다.** 계획 6장에는 있으나,
  원본이 1120px 고정폭 데스크톱 전용이고 모바일 화면이 `[미확인]` 이라 기준이 없다.
  이번 Phase의 검수는 Chrome 실브라우저 직접 비교로 대신했다.
- 광고 관련 요소는 만들지 않았다. 원본 홈의 광고 슬롯(`h-wide-ad` 280px + 상하 여백)을 통째로 빼고
  히어로 다음에 인기게시글 카드가 바로 이어지게 했다 (`CLAUDE.md` 4장).


### D-014. `.next` 오염으로 CSS가 통째로 빠지는 문제 (2026-08-20 발생 · 해결)

**증상** — `localhost:3000`이 브라우저 기본 스타일로만 렌더됐다. HTML과
`<link rel="stylesheet" href="/_next/static/css/app/layout.css">`는 정상인데
**그 CSS 파일이 404**였고 `.next/static` 안에 CSS 파일 자체가 없었다.

**원인** — Tailwind/PostCSS 설정 문제가 아니었다. `app/globals.css`를
`@tailwindcss/postcss`로 직접 돌려보면 18KB가 정상 생성되고
`@import '../../../packages/ui/src/styles.css'` 인라인과
`@source "../../../packages/ui/src"` 스캔도 모두 정상이었다.
문제는 **`.next` 디렉터리가 깨진 상태**였다는 것이다.
`next build`(프로덕션)와 `next dev`를 같은 `.next`에 번갈아 돌렸고,
그 중 일부가 컴파일 도중에 강제 종료되면서 매니페스트는 CSS를 가리키는데
정작 CSS 청크는 없는 상태로 남았다. 포트를 붙잡고 있던 좀비 dev 서버가 그 깨진 `.next`를 계속 서빙했다.

**해결 / 재발 방지**
- `pnpm clean` 스크립트 추가 (`apps/web/.next` 삭제)
- `pnpm build` 를 `pnpm clean && next build` 로 변경 — 프로덕션 빌드가 dev 산출물 위에 겹쳐 쓰이지 않는다

### D-019. Chrome 검수 시 탭이 백그라운드면 React 상태가 갱신되지 않는다 (2026-08-21)

**증상** — 로그인 폼에 실제로 타이핑해도 버튼이 계속 비활성이었다.
DOM `value`는 바뀌는데 React 상태가 안 바뀌고, 컨트롤드 입력인데도 React가 값을 되돌리지 않았다.
`__reactProps`에 `onChange`는 정상적으로 붙어 있었고 콘솔 오류도 없었다.

**원인** — 앱 버그가 아니다. 검수용 탭이 `document.visibilityState === 'hidden'` 상태였다.
Chrome은 백그라운드 탭에서 타이머·MessageChannel을 throttle하는데,
React 스케줄러가 이것을 쓰기 때문에 **상태 업데이트가 flush되지 않는다.**
CDP 평가가 45초 타임아웃 나던 것("renderer frozen")도 같은 원인이다.

**대응**
- 상호작용을 검수할 때는 **탭이 visible인지 먼저 확인한다** (`document.visibilityState`).
  스크린샷을 찍으면 대체로 활성화된다.
- 데이터 렌더(React Query 결과)는 백그라운드에서도 보이므로 "화면이 나온다 = 상호작용도 된다"가 아니다.
- 폼 검증 같은 순수 로직은 브라우저 대신 **단위 테스트로 고정**한다
  (`signup-rules.test.ts`, `league-create.test.ts`).

### D-032. 검수는 개발 서버가 아니라 프로덕션 빌드로 한다 (2026-08-21)

앱 문제로 오인하기 쉽다 — 실제로 몇 번 그렇게 헷갈렸다.

→ 화면 검수는 `pnpm build` + `pnpm --filter @sacloud/web start`로 한다. 응답이 0.2~0.3초로 떨어진다.
**사용자가 실제로 보는 것과 같은 빌드**라는 점에서도 이쪽이 맞다.

### D-031. 로그인 직후 화면 전환의 두 가지 함정 (2026-08-21 수정)

**증상 1** — 로그인은 200인데 로그인 화면에 그대로 남았다.
`invalidateQueries`를 기다리지 않고 이동해서, 도착한 화면의 `AuthGuard`가 아직 갱신되지 않은
`/infos`(비로그인)를 보고 되돌려보냈다. → 갱신을 `await` 한 뒤 이동한다.

**증상 2** — 1번을 고치려고 `AuthGuard`가 "갱신 중에는 children을 내리도록" 만들었더니,
`/infos`를 다시 받을 때마다 **하위 화면이 통째로 다시 마운트**됐다.
마이페이지에서 저장은 되는데 "저장했습니다"가 나타나지 않는 것으로 드러났다.
→ **판정만 미루고 화면은 계속 그린다.**

교훈: 보호막이 로딩 상태를 이유로 children을 내리면, 그 아래의 입력값·성공 메시지 같은
지역 상태가 조용히 사라진다. 로딩 처리는 "무엇을 감출지"가 아니라 "무엇을 판정하지 않을지"로 짠다.

### D-030. 리프레시 토큰을 실제로 쓰게 만들었다 (2026-08-21 수정)

발급해서 DB에 저장까지 해놓고 **아무도 쓰지 않았다.** 계약이 응답 본문으로만 주는데
브라우저 클라이언트는 그걸 보관할 곳이 없어서, 액세스 토큰(1시간)이 만료되는 순간
**말없이 로그아웃**됐다. 검수 중 정확히 1시간 뒤에 드러났다.

- 리프레시 토큰도 **httpOnly 쿠키**로 내려보낸다
- 액세스 토큰이 만료됐으면 리프레시 쿠키로 **조용히 재발급**한다
- 이때 **리프레시 토큰은 돌리지 않는다.** 한 페이지가 동시에 여러 요청을 보내는데
  그중 하나가 회전시키면 나머지가 무효 토큰으로 실패한다. 회전은 `POST /auth/token`에서만.
- 로그아웃은 두 쿠키를 모두 지운다

### D-029. Phase 0 픽스처의 시각이 id 순서와 어긋나 있었다 (2026-08-21 수정)

Mock↔실제 API 응답을 값까지 대조하다가 발견했다. 픽스처가 아래 세 곳의 시각을 **무작위로**
뽑고 있어서, id(=표시 순서)와 시각이 맞지 않았다.

| 대상 | 증상 |
|---|---|
| 게시글 `createdAt` | 목록은 최신순인데 `작성시간` 열이 내림차순으로 보이지 않았다 |
| 댓글 `createdAt` | 한 글 안에서 댓글 시각이 뒤죽박죽이었다. 대댓글이 부모보다 앞서기도 했다 |
| 리그 참여 `joinedAt` | 리그 목록의 대표 클랜 3개가 Mock과 실제 DB에서 서로 달랐다 |

Mock은 배열 순서(=id)로 정렬하고 실제 DB는 시각으로 정렬하므로, 이대로면 두 모드의
화면이 달라진다. **화면 자체도 틀린 상태였다** — 원본은 최신순 정렬이다.

→ `rng`를 뽑는 **순서는 그대로 두고**(다른 필드가 흔들리지 않게) 값의 배치만 정렬했다.
회귀 테스트 4건을 추가해 다시 어긋나면 바로 잡히게 했다.
댓글 시각이 기준 시각을 넘어 **미래로 찍히던 것**도 함께 막았다.

### D-028. 계약이 `:leagueId`인 자리에 슬러그도 받는다 (2026-08-21 사고)

**증상** — 실제 화면에서 클랜랭킹·개인랭킹·기록실이 전부 비어 보였다.

**원인** — 계약은 랭킹·매치 경로를 `:leagueId`로 적어 두었지만,
화면은 이 자리에 **URL 슬러그를 그대로 넣어 호출한다**
(`app/league/[leagueSlug]/rank/...`). Mock 핸들러가 `resolveLeagueId`로 둘 다 받아 왔기 때문에
Phase 1~6 내내 드러나지 않았다.

→ 실제 API도 `resolveLeagueId`로 슬러그·ID를 모두 받는다. 회귀 테스트로 고정했다.

**교훈** — 이 버그는 **curl로도, 계약 준수 테스트로도 잡히지 않았다.**
둘 다 "우리가 옳다고 생각한 경로"로 호출했기 때문이다. 실제 화면을 열어봐야 드러났다.
`CLAUDE.md` 3장 10번(렌더 확인 필수)이 왜 있는지 보여주는 사례다.

### D-027. Next 서버 번들에서 `Prisma.sql` 태그드 템플릿을 쓰지 않는다 (2026-08-21)

`hot`(인기) 게시판은 저장 컬럼이 아니라 계산식으로 정렬해야 해서 raw SQL이 필요하다.
그런데 Next 서버 번들 안에서는 `Prisma.Sql` 인스턴스 검사가 통과하지 못해,
SQL 조각으로 넣은 값이 **바인드 파라미터(jsonb)로 직렬화**된다.

```
ERROR: argument of WHERE must be type boolean, not type jsonb
```

같은 코드가 `tsx` 단독 실행에서는 정상이라 재현이 헷갈린다.

→ `$queryRawUnsafe` + 번호 플레이스홀더(`$1`)로 직접 조립한다.
**사용자 입력은 전부 `bind()`를 거쳐 `$n`으로만 넣고**, 테이블·컬럼명과 정렬식은
파일 안의 리터럴만 쓴다. `LIKE` 검색어는 `%`·`_`·`\`를 이스케이프한다.

### D-026. 라우트 세그먼트 이름을 계약과 1:1로 맞추지 않는다 (2026-08-21)

계약은 같은 자리에 서로 다른 이름을 쓴다.

```
/leagues/:leagueSlug          /leagues/:leagueId/ranks/clans
/leagues/:leagueSlug/clans/:clanSlug/show
/leagues/:leagueSlug/clans/:leagueClanId/division
```

Next는 **한 세그먼트에 서로 다른 이름의 동적 라우트를 둘 수 없다.**
그래서 파일 경로에서는 이름을 하나로 통일하고(`[league]`, `[clan]`),
**핸들러마다 계약대로 슬러그인지 ID인지 해석**한다. 각 파일 주석에 어느 쪽인지 적어 둔다.

외부에서 보이는 URL은 계약 그대로다. 바뀐 것은 우리 저장소의 폴더 이름뿐이다.

### D-025. Auth.js(NextAuth)를 쓰지 않고 직접 구현한다 (2026-08-21)

**계획 문서(`docs/IMPLEMENTATION_PLAN_1.md` 1장)와 어긋나는 결정이다.** 사용자 확인이 필요하다.

계획은 인증에 Auth.js(NextAuth v5)를 적었다. 그런데 Phase 0에서 확정한 계약이
자체 토큰 흐름을 정의하고 있다.

```
POST /auth/login  → { access_token, refresh_token, expires_at, user }
POST /auth/token  → 토큰 갱신
```

NextAuth의 세션 모델(자체 쿠키 + `/api/auth/*` 예약 경로)과 정면으로 부딪힌다.
NextAuth를 얹으면 계약을 맞추려고 감싸는 코드가 더 늘어난다.

→ `jose`(JWT) + `bcryptjs`로 직접 구현했다.
- 액세스 토큰: JWT 1시간. **httpOnly 쿠키로도 내려보낸다** (스크립트로 못 읽는다)
- 리프레시 토큰: 불투명 문자열 30일. **평문을 저장하지 않고 해시만** DB에 둔다. 갱신 시 폐기(rotation)
- 계약이 본문에도 토큰을 요구하므로 본문에도 넣는다

로그아웃은 계약에 없었다(원본에 엔드포인트가 있는지 `[미확인]`). 세션이 httpOnly 쿠키라
서버가 지워야 해서 `authLogout`을 **계약에 `designed`로 추가**했다.

### D-024. 닉네임 유일 제약을 걸지 않는다 (2026-08-21)

Phase 7 스키마 초안에서 `User.nickname`에 `@unique`를 걸었다가 **되돌렸다.**

원본이 닉네임 중복을 막는지는 **관측되지 않았다**. 회원가입 폼에서 확인한 것은 길이 제약(2~16자)뿐이다.
확인되지 않은 제약을 임의로 만드는 것은 `CLAUDE.md` 3장 7번 위반이다.
게다가 Mock 픽스처(사용자 40명)에 이미 닉네임 충돌이 있어, 유일 제약을 걸면
**mock 모드와 live 모드의 데이터가 달라진다.** 화면 비교의 기준이 무너진다.

→ `@unique` 대신 조회용 `@@index([nickname])`만 둔다.
원본이 중복을 막는다는 것이 확인되면 그때 제약과 마이그레이션을 추가한다.

### D-023. 시드 데이터는 출처를 남긴다 (2026-08-21)

개발 시드로 들어가는 3,000경기는 **가짜다.** 실제 3rd.supply 기록이 아니고,
래더 값도 픽스처 난수라 SACLOUD 공식으로 계산된 것이 아니다.

나중에 실제 기록과 섞이면 구분할 방법이 없어지므로 두 곳에 표시를 남긴다.

- `Match.origin = "mock"` — 실제 수집분(`nexon` / `3rd.supply`)과 구분
- `MatchPlayerStat.formulaVersion = "mock-fixture"` — 공식 계산 결과로 오인하지 않게

같은 이유로 `CLAUDE.md` 3-A 2번(기존 `rating_update`를 추정 공식으로 덮어쓰지 않는다)을
스키마 수준에서 지킬 수 있다. 이전된 과거 기록은 `formulaVersion`이 다르므로 재계산 대상에서 제외된다.

### D-022. 로컬 개발 DB는 `embedded-postgres`로 띄운다 (2026-08-21)

**문제** — 이 개발 PC에는 Docker도 PostgreSQL도 설치돼 있지 않다(2026-08-21 확인).
관리자 권한 설치를 요구하지 않고 개발을 진행할 방법이 필요했다.

**선택** — `embedded-postgres`(PostgreSQL 17 공식 바이너리를 `node_modules`에 내려받아
일반 사용자 권한으로 기동). `pnpm db:start` / `db:stop` / `db:reset`으로 다룬다.
**개발 전용이며 운영에는 쓰지 않는다.** 운영은 관리형 PostgreSQL을 쓴다.

**한국어 Windows에서 막혔던 지점 두 가지** (둘 다 실제로 실패를 확인하고 우회했다)

1. 데이터 디렉터리를 저장소 안(`C:\Users\LG\Desktop\서플라이\.pgdata`)에 두면
   `initdb`가 경로를 CP949로 다뤄 깨진다. → 저장소 밖 **ASCII 경로**
   (`%LOCALAPPDATA%\sacloud\pgdata`)에 둔다. `SACLOUD_PGDATA`로 바꿀 수 있다.
2. 기본 로케일이 `Korean_Korea.949`라
   - `initdb`가 "could not find suitable text search configuration"으로 실패 → `--locale=C`
   - post-bootstrap의 `pg_import_system_collations()`가 Windows collation 이름을 CP949로 넣어
     `invalid byte sequence for encoding "UTF8": 0xbc`로 실패 → 템플릿을 `--encoding=SQL_ASCII`로 만든다.

   **템플릿만 SQL_ASCII이고, 실제 사용 DB(`sacloud`)는 `TEMPLATE template0`으로
   UTF8 + `LC_COLLATE=C`로 따로 만든다.** 한글 저장은 UTF8이며,
   `pnpm db:check`가 한글 왕복과 DB 인코딩을 매번 검증한다.

**포트는 5433.** 나중에 시스템에 PostgreSQL을 설치해도 기본 포트(5432)와 겹치지 않는다.

### D-021. 개발 서버는 반드시 하나만 띄운다 (2026-08-21 사고)

**증상** — `/auth/login`이 브라우저에서 **404**로 보였다. 그런데 코드·빌드·라우트는 전부 정상이었다.

**원인** — `pnpm dev`가 여러 번 실행돼 있었다. Next는 3000이 점유돼 있으면
`Port 3000 is in use ... using available port 3003 instead` 로 **다른 포트에 뜬다.**
그래서 3000번에는 **인증 페이지가 생기기 전에 띄운 옛날 서버**가 남아 있었고,
사용자가 보는 3000번만 404였다. 실제로 3000/3001/3002/3003 네 개가 동시에 떠 있었다.

**대응**
- `pnpm dev:clean` 추가 (`scripts/dev-restart.mjs`) — 3000~3010의 프로세스를 정리하고
  `.next`를 지운 뒤 서버를 **한 번만** 띄운다.
- 404나 "옛날 화면"이 보이면 먼저 **몇 번 포트에 무엇이 떠 있는지** 확인한다.
  Next 시작 로그의 `Local: http://localhost:PORT` 줄을 반드시 본다.

### D-020. 클라이언트 번들에 `@sacloud/mock` 진입점을 넣지 않는다 (2026-08-21)

### D-018. 래더 사양 문서 신설 (2026-08-21)

## Phase 8 — 넥슨 Open API 수집 (2026-08-21)

사양 문서: `docs/NEXON_INGEST_SPEC.md` (엔드포인트 실측 · 흐름 · 규칙)

### D-034. 원본이 주지 않는 값은 전부 `null`이다. `false`를 기본값으로 쓰지 않는다

넥슨 Open API는 **무기 · 플레이시간 · 종료시각 · 선공진영 · MVP · 탈주**를 제공하지 않는다
(공식 OpenAPI 스펙 실측, 2026-08-21).

`mvp = false` / `dropout = false` / `blueFirst = false` 는 "아니다"라는 **실제 정보**다.
우리는 그 사실을 모르므로 `null`(= 알 수 없음)이어야 한다.

바꾼 것

| 위치 | 변경 |
|---|---|
| `Match.endAt` `Match.playTime` `Match.blueFirst` | NOT NULL → nullable (기본값 제거) |
| `MatchPlayerStat.weapon` `dropout` `mvp` | NOT NULL → nullable (기본값 제거) |
| 계약 `MatchPlayerStat.weapon/dropout/mvp` | `.nullable()` |
| 계약 `MatchListItem.end_at/play_time/blue_team` | `.nullable()` |
| 계약 `MatchLineupEntry.weapon/dropout` | `.nullable()` |
| UI `MatchCard` | 플레이시간·무기 `알수없음`, `[S]`·MVP·탈주 미표기, 선레드/선블루 **행 자체를 감춤** |

**기존 mock 시드는 실제 값이 있으므로 그대로 둔다.** 값을 지우지 않는다.

### D-035. 내부 ID와 외부 source ID를 분리한다

```
Match.id            = SACLOUD 내부 식별자 (18자리 숫자 규칙, 계약 MatchId)
Match.origin        = "nexon" | "3rd.supply" | "sacloud" | "mock"
Match.sourceMatchId = 넥슨 원본 match_id (문자열 원형)
중복 방지            = @@unique([origin, sourceMatchId])
```

넥슨 `match_id`를 내부 `Match.id`로 쓰지 않는다. 외부 공급자의 ID 형식이 내부 도메인 규칙에
침투하면 공급자가 늘 때마다 계약이 흔들린다. 내부 ID는 `YYMMDDHHmmss`(KST) + 6자리 일련번호로
우리가 만든다. **원본 대조는 언제나 `sourceMatchId`로 한다.**

### D-036. ouid로도, 닉네임으로도 동일인을 자동 확정하지 않는다

- 넥슨은 "게임 콘텐츠 변경으로 ouid가 변경될 수 있다"고 명시했다 → **ouid는 영구 식별자가 아니다.**
- 닉네임도 영구 식별자가 아니다 → 닉네임 일치만으로 병합하지 않는다.
- `Player.nexonOuid`는 **비권위 캐시**다. 판단 근거로 쓰지 않는다.

`NexonIdentity.status` = `unresolved`(기본) | `active` | `superseded` | `conflicted`.
근거가 부족한 연결은 `NexonIdentityCandidate`(open/accepted/rejected)로만 남기고
**자동 승인 경로를 만들지 않았다.** 참가자 해석은 `active` + `playerId`가 있는 신원만 쓰며,
둘 이상 걸리면 `ambiguous`로 두고 투영을 보류한다.

### D-037. 진영(red/blue) 배정은 내부 규칙이다

넥슨은 진영 색을 주지 않고 `team_id`의 의미도 `[미확인]`이다.
그래서 **`team_id` 오름차순으로 red/blue를 배정**한다. 재실행해도 같은 결과가 나오게 하려는
내부 규칙일 뿐, "원본이 이랬다"는 주장이 아니다. 승패는 참가자 `match_result`로 판정하며
갈리지 않으면 투영하지 않는다.

### D-038. `damage` 정밀도 — 스테이징은 원본, 도메인은 정수

넥슨 `damage`는 소수(double)다. 계약의 딜량은 정수(`Count`)다.
`NexonMatchParticipant.damage`에 **소수 원본을 그대로** 두고, 운영 `MatchPlayerStat.damage`에만
반올림해 넣는다. 정확한 값이 필요하면 스테이징·원본에서 다시 읽을 수 있다.

### D-039. `RawImport`는 append-only다

`contentHash`(sha256)를 유니크 키에 넣었다.

- 같은 내용을 다시 받으면 **새 행을 만들지 않고** `fetchCount` / `lastFetchedAt`만 올린다.
- 내용이 달라지면 **새 행**을 추가한다. 이전 원본을 덮어쓰지 않는다.

30일 갱신 재수집이 과거 원본을 지워 버리면 `CLAUDE.md` 3-A 1번(원본 보존)이 깨진다.
**요청 헤더는 저장하지 않는다.** API 키가 저장소에 들어갈 경로 자체를 없앴다.

### D-040. Phase 8은 큐 인프라를 도입하지 않는다

Redis / BullMQ를 쓰지 않는다. 체크포인트는 `ImportJob`(+`ImportFailure`)에 남기고
실행은 워커 CLI가 한다. 넥슨 `/match`에 커서가 없어 체크포인트 단위는 매치가 아니라
**대상(ouid × match_mode)** 이다. 규모가 실제로 문제가 되면 별도 Phase에서 큐를 얹는다.

`정보갱신` / `전적갱신` 버튼은 넥슨 API를 인라인 호출하지 않고 `ImportJob`에 `pending`으로
등록만 한다. 사용자 클릭이 곧바로 외부 호출이 되면 호출 한도를 순식간에 소진한다.

### D-041. 신선도 주기는 설정값이다 (`NEXON_REFRESH_INTERVAL_DAYS`, 기본 30)

넥슨 이용 조건에 "가져간 데이터는 최소 30일마다 갱신"이 명시돼 있다.
다만 **그 의무가 어느 데이터 범위까지 어떻게 적용되는지는 검증되지 않았다 `[미확인]`.**
그래서 특정 일수를 비즈니스 규칙처럼 코드에 고정하지 않고 환경변수로 받는다.
기한이 지난 스테이징은 `refreshDueAt`으로 뽑아 재수집하고, 갱신하지 못하면 `staleAt`을 남긴다.

### D-042. 호출 한도를 추측하지 않는다

넥슨 스펙·문서 어디에도 호출 한도 수치가 없다. 테스트 키의 한도는 더더욱 모른다.
그래서 `NEXON_RATE_LIMIT_PER_SEC`(보수적 기본값)에서 시작해 **429를 받으면 스스로 감속**한다
(`Retry-After` 존중 + 지수 백오프 + 지터). 403·키 오류는 재시도하지 않고 **전체를 멈춘다.**
"우리 추정 한도"를 코드에 적어 두지 않는다.

## Phase 8 — 실응답 검증 (2026-08-21)

### D-043. 실제 응답의 클랜명 필드는 `clan_name`이 아니라 `guild_name`이다


### D-044. 한 경기 응답에 양 팀이 함께 오지 않는다 — **Phase 9 blocker**

실측 5경기(개인전 1 · 퀵매치 클랜전 4)에서 **양 팀 라인업이 온전히 온 경우가 한 번도 없었다.**

| 조회 대상의 결과 | 응답 구성 |
|---|---|
| 승리 (3건) | 승리 팀 6명만. 상대 팀 0명 |
| 패배 (1건) | 승리 팀 6명 + **본인 1명** (총 7명) |
| 무승부 (1건) | 한 팀 5명만 (전원 k/d 0) |
| 개인전 (1건) | 7명, `team_id`가 전부 `null` |

관측된 규칙은 "승리 팀 전원 + (졌다면) 조회 대상 본인"에 가깝다. **원인은 `[미확인]`**
(공개 동의 여부·API 정책 등). 넥슨 스펙에는 이런 제한이 적혀 있지 않다.

영향

- 클랜 vs 클랜 경기를 **한 사람의 조회만으로 재구성할 수 없다.**
- 우리 투영 규칙(양 팀·양 클랜·인원 일치)은 실데이터에서 항상 보류된다. 규칙이 틀린 게 아니라
  **입력이 부족한 것**이다.
- 해결 후보: ① 같은 경기를 여러 참가자 ouid로 조회해 합치기(양쪽 클랜원을 모두 알아야 한다)
  ② 넥슨에 문의 ③ 클랜 단위 조회 수단 확보. **어느 것도 아직 검증되지 않았다.**

Phase 9(래더 계산)는 경기 단위 승패와 양 팀 구성이 필요하므로, 이 문제가 풀리기 전에는
**넥슨 데이터만으로 래더를 산정할 수 없다.**

### D-045. 개발 도구는 자기 데이터 밖을 건드리면 안 된다 (사고 기록)

빈 DB에서 만든 `offlineSmoke.ts`가 실수집 데이터가 있는 DB에서 돌자,

  **범위를 인자로 강제**했다. 스모크는 자기 경기 ID만 넘긴다.
- 교훈: "빈 DB에서 통과"는 안전의 근거가 아니다. 개발 도구도 대상 범위를 명시해야 한다.

### D-046. 실응답 픽스처는 가명화해서만 저장소에 넣는다

실응답에는 제3자의 닉네임·클랜명·계정 식별자가 들어 있다.

- 저장 직전 API 키 포함 여부를 다시 검사하고, 걸리면 파일을 쓰지 않는다

도구는 `apps/worker/src/dev/exportFixtures.ts`.

## Phase 8.1 — D-044 후속 검증 · 적응형 폴링 (2026-08-21)

### D-044 결론 — **CASE 1 + 조건부 CASE 3** (실측 근거)

**A-1. 같은 `match_id`를 다시 조회하면 완전히 같은 응답이 온다.**

클랜전 3건을 재호출한 결과 `contentHash`가 **전부 동일**했고, `RawImport`에 새 행이 생기지 않고
`fetchCount`만 2로 올랐다. `/match-detail`의 파라미터는 `match_id` 하나뿐이므로
**"다른 사람의 계정으로 같은 경기를 다시 조회해 합친다"는 방법은 성립하지 않는다** → **CASE 1**.

(단, 같은 API 키로만 확인했다. 다른 앱/키에서도 같은지는 `[미확인]`.)

**A-2. 같은 경기가 다른 참가자의 매치 목록에는 존재한다.**

7명짜리 클랜전(상대 팀 6명 + 본인)에서 상대 팀 참가자 2명을 골라 확인했다.

| 대상 | 그 경기가 목록에 있는가 | 목록이 준 값 |
|---|---|---|
| `MMA수련중` (상대 팀) | **있음** | `result=1` `kill=9` `death=8` `assist=3` |
| `미키` (본인) | 있음 | `result=2` `kill=13` `death=11` `assist=3` |
| `혀반샷` (상대 팀) | **없음** | — |

목록이 준 값은 상세 응답의 같은 사람 기록과 **일치**했다(kill 9 / death 8 / assist 3).
→ 여러 사람의 목록을 모으면 **그 사람들의 개인 기록**은 채울 수 있다 → **조건부 CASE 3**.

**한계 (그래서 CASE 3만으로 완성되지 않는다)**

1. 목록에는 `team_id`도 클랜명도 없다. 승패(`match_result`)로만 편을 가를 수 있다.
2. **모르는 참가자는 발견할 방법이 없다.** 상세가 상대 팀 닉네임을 주지 않으므로
   그 사람의 `/id`조차 부를 수 없다. 우리가 이미 아는 사람만 채워진다.
3. `혀반샷`처럼 **닉네임으로 조회한 계정이 그 경기의 그 사람이 아닐 수 있다.**
   닉네임은 영구 식별자가 아니다 — D-036이 실제 데이터로 확인된 사례다.

**결론**: 넥슨 데이터만으로 **양 팀 전원을 보장하는 재구성은 불가능**하다.
다만 SACLOUD 리그처럼 **참가자 명단을 우리가 이미 아는 경우**에는, 리그 소속 선수들을 폴링해
같은 `match_id`를 교차 발견하고 각자의 기록을 합치는 경로가 있다. 그것도 미등록 참가자가 있으면
인원이 맞지 않아 투영되지 않는다. **BLOCKER는 유지된다.**

### D-048. 상세 참가자와 목록 관측값을 섞지 않는다

목록에서 얻은 개인 기록은 `NexonMatchObservation`에 **출처(`player_match_list`)와 함께** 쌓고,
상세에서 온 참가자(`NexonMatchParticipant.source = "match_detail"`)와 같은 표에 넣지 않는다.

이유: 둘은 신뢰도와 내용이 다르다. 상세는 팀·클랜명이 있고, 목록은 본인 기록뿐이다.
섞으면 "이 참가자 정보가 어디서 왔는지"를 나중에 구분할 수 없다.
**나오지 않은 참가자를 만들지 않는다** — 관측된 사람만 저장한다.

### D-049. 활동량 기반 적응형 폴링 (고정 전수 조회 폐기)

5,000명을 같은 주기로 계속 조회하지 않는다. 한 명을 한 번 보는 데 모드 4개 = **호출 4회**다.

| 티어 | 뜻 | 기본 주기 |
|---|---|---|
| `hot` | 방금 새 경기를 발견 | 30분 |
| `warm` | 연속 빈 조회 2회 이상 | 3시간 |
| `cold` | 연속 빈 조회 5회 이상 | 1일 |
| `dormant` | 연속 10회 이상 또는 30일간 새 경기 없음 | 7일 |

- 전환 규칙: 새 경기 발견 → 즉시 `hot`·연속 빈 조회 0으로 초기화 / 빈 조회 → 누적 후 강등 /
  **실패는 활동량이 아니다** → 티어를 내리지 않고 다음 조회만 미룬다(백오프)
- 우선순위: 수동 갱신(0) > hot(1) > warm(2) > cold(3) > dormant(4), 같으면 오래 기다린 순
- **starvation 방지**: 예정보다 크게 밀린 대상은 티어와 무관하게 우선순위를 올린다
- **숫자는 전부 설정값**(`NEXON_POLL_*`). 실제 호출 한도를 모르는 상태에서
  "몇 분마다 반드시"를 영구 규칙으로 코드에 박지 않는다

`정보갱신`/`전적갱신` 버튼은 `manualRefreshRequestedAt`을 찍어 **최우선**으로 올린다.
여전히 화면에서 넥슨 API를 직접 부르지 않는다(E 결정).

### D-050. 이미 저장한 경기의 상세는 다시 부르지 않는다

A-1에서 확인했듯 같은 `match_id`는 언제 불러도 같은 응답이다.
그래서 다른 사람의 목록에서 같은 경기가 나와도 **상세를 다시 부르지 않는다.**
예외는 신선도 정책(기본 30일) 재검증뿐이다(`decideDetailFetch`).

목록 관측값 병합(D-048)과 상세 재조회는 **다른 일**이다. 전자는 호출 없이 쌓이고,
후자는 호출이 든다. 코드에서도 분리했다.

### D-051. 호출량을 기록한다 (`NexonPollRun`)

5,000명 운영 비용을 추정이 아니라 **숫자로** 계산하기 위해 실행마다 남긴다:
대상 수 · 목록 호출 · 신규/중복 match_id · 상세 호출 · dedupe로 건너뛴 수 · 빈 조회 ·
429 횟수 · 실패 · 활동/비활동 대상별 호출 수. `pnpm nexon:report`로 본다.
**관리자 UI는 만들지 않는다** (F 결정 유지).

## Phase 8.2 — 로스터 기반 재구성 (2026-08-22)

> 전제: **D-044는 해결되지 않았다.** 넥슨 `/match-detail`은 여전히 참가자 일부만 준다.
> Phase 8.2는 그 한계를 없애는 것이 아니라, **우리가 아는 정보(리그 로스터)로 완전한 경기를
> 만들 수 있는 조건**을 정한 것이다.

### D-052. 경기 시점 소속은 **등록 기간**으로 판정한다 (`LeagueRosterMembership`)

넥슨은 참가자의 클랜을 문자열(`guild_name`)로만 주고, 그것도 상세에 나온 사람만 준다.
문자열이 같다고 같은 클랜이라고 볼 수 없고(동명 클랜·개명), 상세에 없는 사람은 아예 알 수 없다.

대신 SACLOUD는 리그 운영자로서 **누가 언제 어느 클랜으로 등록됐는지**를 안다.
그 사실을 `joinedAt ~ leftAt` 기간으로 보존하고, 경기 시각이 그 기간 안인지로만 판정한다.

- 판정 규칙: `joinedAt <= 경기시각 < leftAt` (leftAt이 null이면 현재까지)
- 같은 시각에 소속이 둘 이상이면 **판정하지 않는다.** 추측하지 않는다
- `verified=false`(운영자 미확인) 소속은 기본적으로 완전성 판정에 쓰지 않는다.
  `--allow-unverified-roster`로 운영자가 명시할 때만 쓴다
- 닉네임으로 소속을 정하지 않는다 (D-036 유지)

### D-053. 공식리그 등록 선수를 **같은 티어 안에서** 먼저 조회한다

우리가 완성해야 하는 것은 리그 경기이고, 리그 경기의 완전성은 등록 선수 **전원의 관측**에 달려 있다.
그래서 `NexonPollState.priorityClass = "league"`인 대상의 우선순위를 `leaguePriorityBoost`만큼 올린다.

- **호출량을 늘리지 않는다.** 주기(티어)는 그대로고 **순서만** 바뀐다
- 티어를 뒤집지 않는다. hot 일반 유저가 warm 리그 선수보다 여전히 먼저다
- 수동 갱신 요청은 여전히 최우선이다
- 값은 `NEXON_POLL_LEAGUE_BOOST` 설정값이다. `0`이면 기능이 꺼진다

### D-054. 상세(`match_detail`)는 **보조 증거**다

재구성의 1차 근거는 각 선수의 매치 목록에서 온 개인 관측값(D-048)이다.
상세는 (1) 교차검증과 (2) 상세에만 있는 값(헤드샷·데미지·team_id) 보완에만 쓴다.

- 상세와 관측이 어긋나면 **자동 투영하지 않는다.** 사유를 남기고 사람이 본다
- 상세가 주지 않은 값(`null`)은 불일치로 보지 않는다. 모른다는 뜻이다
- 상세에 나왔는데 목록 관측이 없는 **로스터 선수**가 있으면 `missing_observation`으로 보류한다.
  그 사람을 폴링하면 채워질 자리이지, 우리가 채울 자리가 아니다

### D-055. 새 클랜전을 발견하면 같은 경기를 봤을 사람의 조회를 **앞당긴다** (전파)

각자의 티어대로만 돌면 한 경기가 다 모이는 데 며칠이 걸린다.

- **호출을 새로 만들지 않는다.** 어차피 조회할 사람의 `nextPollAt`을 당길 뿐이다
- 대상은 (1) 발견자와 같은 클랜의 등록 선수, (2) **증거로 확인된** 상대 클랜의 등록 선수뿐이다.
  상대 클랜이 관측·상세로 확인되지 않았으면 **추측해서 전파하지 않는다**
- 한 번에 앞당기는 수에는 상한이 있다 (`NEXON_POLL_PROPAGATION_FANOUT`, 기본 20)
- 티어·주기·수동 갱신 표시는 건드리지 않는다. 사유는 `propagationReason`에 남는다

### D-056. 재구성은 **완전할 때만** 투영하고, 판정 근거를 남긴다

부분 저장을 하지 않는다. 다음이 모두 참일 때만 운영 `Match`를 만든다.

1. 경기 시각·맵·매치 유형이 리그 기록 대상이다
2. 참가자 전원이 **목록 관측**으로 확인됐다 (관측되지 않은 사람을 만들지 않는다)
3. 전원이 경기 시점 로스터로 뒷받침된다 (D-052)
4. 클랜이 정확히 둘이고, 양 팀 인원이 같고, 리그 대전 인원과 일치한다
5. 같은 클랜 안에서 승패가 일치하고 승자가 하나다
6. 상세와 어긋나는 값이 없다 (D-054)

판정 결과는 성공·실패 모두 `NexonMatch.reconstruction`(JSON) + `reconstructedAt`에 남긴다.
**계산 결과가 아니라 증거다.** 무엇이 모자라서 미완인지 숫자로 남아야 다음 판단을 할 수 있다.

래더 값은 여전히 넣지 않는다. 재구성된 경기도 `origin="nexon"`이고 래더 컬럼은 전부 `null`이다 (Phase 9).

## Phase 9 — 래더 정책 (2026-08-22 사용자 확정)

> 이 장의 결정은 **사용자가 직접 확정한 제품 정책**이다. 우리가 추정한 것이 아니다.
> 일부는 3rd.supply 재현보다 **새 SACLOUD의 래더 품질**을 우선한 선택이며, 그 사실을 명시한다.
> 상수의 근거는 `docs/LADDER_TUNING_REPORT.md`의 시뮬레이션이다.

### D-057. 경기 인정 기준 — **양측 각각 3명 이상**

같은 `sourceMatchId`에서 **양 클랜이 각각 3명 이상** 확인되면 경기로 인정한다.

```
A 4명 · B 3명 → 인정
A 5명 · B 2명 → 인정하지 않음
```

기존 Phase 8.2 기준(양 팀 전원 복원 + 인원 일치)은 **폐기한다.** 넥슨이 참가자 전원을 주지
않는 이상(D-044) 전원 복원을 기다리면 대부분의 경기가 영원히 인정되지 않는다.

**확인(confirmed)의 정의** — 그 선수의 *자기 기록*(승패·k/d/a) 근거가 그 경기에 있어야 한다.

- 목록 관측값(`NexonMatchObservation`) **또는** 매치 상세의 본인 행(`NexonMatchParticipant`)
- 그리고 신원이 확정돼 있고, 경기 시각에 그 클랜 로스터에 등록돼 있어야 한다

모르는 참가자를 추측해서 채우지 않는다.

### D-058. 개인 래더는 P-A 계보를 **잠정** 채택한다

`0.6`의 적용 위치 해석 중 P-A(반올림 전)를 채택한다. 다만 D-059로 division 보정 자체를
쓰지 않게 되어 **P-A와 P-B의 계산 차이는 나타나지 않는다.**

그래도 `formulaVersion`을 `sacloud-p1-PA`로 분리해 둔다. 과거 `rating_update` 표본을 확보하면
P-A/P-B를 다시 비교할 수 있어야 하기 때문이다.

### D-059. division을 공식에 넣지 않는다

`1부니까 +x%` 같은 보정을 두지 않는다. **division은 시즌 상태일 뿐이다.**

- 2부 클랜의 rating이 1부 최하위보다 높아질 수 있다. 그래도 시즌 중 자동 승격하지 않는다
- 승강은 시즌 종료 후 별도 규칙으로 처리한다 (기본안: 1부 최하위 ↔ 2부 최상위, 플레이오프 없음)

원본은 div1에 `K=24 · 배수 1.15`, div2에 `K=30 · 배수 1.00`, 교차 시 div1만 `×0.6`이라는
**비대칭 보정**을 썼다. 그것을 버린다.

### D-060. 인플레이션을 없앤다 — `D=800`, 승리 배수 1.0, 대칭 K

원본 구조를 그대로 쓰면 두 가지 문제가 생긴다(시뮬레이션으로 확인).

| 문제 | 원본 값에서의 현상 |
|---|---|
| div1 인플레이션 | 동급 경기마다 `+17 / -12` = **경기당 +5가 주입**된다. 승률 50%로 200경기만 해도 +158 |
| 양학 무한 상승 | `D=3400`은 너무 평평해서 800점 차에서도 기대승률이 0.63이다. 약체만 잡아도 계속 오른다 |

바꾼 것 세 가지.

1. **승리 배수 1.0** — 1.15는 점수를 주입한다
2. **패배 K도 `K(R)`을 쓴다** — 승/패에 같은 K를 써야 동급 경기가 제로섬이 된다
3. **`D = 3400 → 800`** — 실력차가 점수에 제대로 반영된다

결과: 동급 경기 증감 합 **정확히 0**, 리그 100명 5,000경기 평균 이동 **+1.4점**.

**과거 3rd.supply 기록은 원본값 그대로 보존한다. 새 시즌만 이 공식으로 계산한다** (스펙 §9).

### D-061. 클랜 래더 = Team Elo

클랜 자체가 rating을 가진다. 개인 증감의 평균이 아니다(라인업 조작에 노출된다).
division을 입력으로 쓰지 않고, 개인과 같은 구조에 `K`만 고정값(16)을 쓴다.

### D-062. 양학 억제 — 점수차 보상 감쇠

이긴 상대와의 점수 차가 크면 **승리 보상을 깎는다.**

```
차이 ≤ 300  → 그대로
300 ~ 900   → 선형 감소
차이 ≥ 900  → 0 (아무리 이겨도 오르지 않는다)
```

**패배에는 적용하지 않는다.** 약한 상대에게 지면 제값을 잃어야 한다(D-066).

### D-063. 반복 대전 감쇠

같은 상대에게 **같은 결과가 반복되면** 보상을 깎는다 (`0.6ⁿ`, 하한 0.15, 기간 14일).
결과가 뒤집히면 새 정보이므로 깎지 않는다. **반복 경기를 금지하지 않는다** — 효율만 낮춘다.

### D-064. 시즌 종료 soft reset

```
newRating = baseline + (oldRating - baseline) × carryRate     baseline 1500 · carryRate 0.5
```

완전 초기화가 아니다. 순위 순서는 **그대로 보존**되고 폭만 절반으로 줄어든다.

### D-065. 라인업 전력은 **확인된 선수만**으로 계산한다

클랜 공식 rating과 별개로, 그 경기에 **실제로 확인된** 선수들의 개인 래더 평균을 낸다.
양측 확인 인원이 **4명 미만이면 반영하지 않는다.** 3명 평균을 5명 팀의 전력으로 쓰는 것은
추정이기 때문이다. 확인되지 않은 선수의 래더를 채워 넣지 않는다.

시뮬레이션에서 이 방식(blend 0.5)이 반영하지 않는 쪽보다 클랜 전력 추적이 더 정확했다
(상관 0.982 vs 0.976).

### D-066. 업셋 보상은 유지한다

양학 억제 때문에 업셋 보상까지 죽이면 안 된다. 다음이 항상 성립해야 한다.

```
약팀이 강팀을 이김  →  큰 보상   (+30)
강팀이 약팀을 이김  →  적은 보상 (+7, 격차가 크면 0)
비슷한 팀끼리       →  정상 변화
```

### D-067. 개인 점수는 **확인된 선수에게만** 만든다

경기가 3v3으로 인정됐더라도, 확인되지 않은 4·5번째 선수의 개인 점수는 만들지 않는다.
없는 참가자를 만들지 않는다.

### D-068. 확인 수준을 보존한다 · 로스터는 "후보 목록"이다

경기마다 다음을 저장해 화면까지 그대로 들고 간다.

```
clanAConfirmedCount · clanBConfirmedCount
observationParticipantCount · detailParticipantCount
participantCompleteness ("5v4") · reconstructionConfidence ("high"|"medium"|"low")
```

그리고 로스터의 역할을 명확히 한다.

> 로스터는 "이 선수가 경기에 참가했을 것이라고 **추측**"하는 근거가 아니라,
> "이 선수의 넥슨 매치 목록을 **확인해야 한다**"는 후보를 제공하는 것이다.

로스터 등록만으로는 참가가 확인되지 않는다. 로스터는 `LeaguePlayer` 기반 자동 파생 +
클랜장/운영자 verify를 기본 경로로 쓰고, CSV는 **대량 등록 보조 수단**으로만 둔다.

## Phase 9 audit — 정책 정정 (2026-08-22)

> 아래는 Phase 9 최종 audit에서 **사용자가 확정한 정정 사항**이다.
> 앞선 D-057 ~ D-068 중 충돌하는 부분을 대체한다.

### D-069. 보상 감쇠는 **부호**를 본다. 승리 증감은 음수가 되지 않는다

점수차 보상 감쇠(D-062)는 `본인 래더 − 상대 래더`라는 **부호 있는 값**으로 걸린다.

```
2600이 1200을 이김  → 차이 +1400 → 감쇠 → +0
1200이 2600을 이김  → 차이 -1400 → 감쇠 없음 → +30
```

절대값으로 걸면 업셋 보상까지 죽는다. 그래서 **강자의 승리만** 깎고 약자의 승리는 그대로 둔다.

그리고 **승리 증감은 어떤 조건에서도 0 미만이 되지 않는다.** 코드로 못박았고 전 구간을 테스트로 고정했다.

**감쇠 구간을 뒤로 물렸다** (`300~900` → `600~1200`).
이유: Elo는 기대 승률대로 이기면 장기 기댓값이 0이 되게 설계돼 있는데, 승리만 깎고 패배는
그대로 두면 "기대대로 이겼는데도 점수가 줄어드는" 구간이 생긴다. 그 구간이 실제 리그에서
자주 나오는 격차(≤600)에 걸리지 않게 했다.

측정 결과 — 격차별 1경기 기댓값: `0점차 0.00 · 200점차 -0.08 · 400점차 +0.27 · 600점차 +0.07`

> 참고로 audit에서 지적된 "300승 후 1496"은 **300연승이 아니라 90% 승률 300경기**(270승 30패)였다.
> 실제 300연승은 `1500 → 1938`이고 최소 승리 증감은 `+1`이다. 보고서의 표기가 부정확했다.

### D-070. 반복 대전 감쇠는 **기본값 꺼짐**이다 (멸망전 보호)

SACLOUD에는 같은 두 클랜이 연달아 붙는 **멸망전** 문화가 있다. 정상적인 실력 검증이다.

- 반복 경기를 **전부 기록하고 전부 승패에 반영한다.** 제외·무효·0점 처리를 하지 않는다
- 감쇠 기능은 남기되 **기본값 `repeatDecay = 1`(꺼짐)** 이다
- 켜더라도 **점수 차가 `repeatDecayMinGap`(600) 이하면 걸리지 않는다**

왜 껐는가 — 측정해 보니 점수차 보상 감쇠만으로 farming이 이미 죽어서, 반복 감쇠를 켜도
결과가 **한 점도 달라지지 않았다**.

```
900 낮은 상대에게 20연승   켬 1820 · 끔 1820   (차이 없음)
비슷한 상대 멸망전 20연승   켬 1817 · 끔 1817   (차이 없음, 새 상대 20연승과도 동일)
```

승패 교대(A승 B승 A승 …) 패턴을 조작으로 판정하지 않는다. 정상적인 접전에서도 나온다.
collusion 탐지는 Phase 9 래더 공식의 요소가 아니며, 필요해지면 별도 이상탐지로 다룬다.

### D-071. 공식전 인정은 **본클랜원** 3+3이다 (용병은 못 채운다)

D-057의 "확인 3명"을 정밀화한다. 양 팀 각각 **그 클랜 소속 본클랜원**이 3명 이상 확인돼야 한다.

```
베리타스 본클랜원 3 + 용병 2  vs  메쏘드 본클랜원 4 + 용병 1  → 공식전 인정
베리타스 본클랜원 2 + 용병 3  vs  메쏘드 본클랜원 5          → 불인정
```

### D-072. "원소속 클랜"과 "이 경기에서 뛴 팀"을 분리한다

두 값은 다르다. 팀 배정은 다음 근거로 한다 — **추측하지 않는다.**

1. 본클랜원 3명 이상이 모인 클랜 **두 곳**이 그 경기의 두 팀이다
2. 각 팀의 승패는 그 팀 본클랜원들의 **다수 결과**로 정해진다
3. 나머지 확인된 선수는 **자기 승패와 같은 팀**으로 배정한다 (승자가 하나뿐이므로 승패가 곧 팀이다)
4. 배정된 팀이 자기 등록 클랜과 다르면 그 경기의 역할은 **용병**이다

본클랜원 승패가 정확히 반반이면 판정하지 않는다. 그때는 근거가 없다.

### D-073. 용병도 개인 기록과 개인 래더를 받는다

3+3은 **경기를 공식전으로 인정하기 위한 기준**일 뿐이다.
경기가 인정된 뒤에는 **출전이 확인된 전원**이 `MatchPlayerStat`·개인 승패·K/D·개인 래더를 받는다.

판단 기준은 **소속이 아니라 실제 출전 확인 여부**다.
본클랜원이 아니라는 이유로 개인 기록을 만들지 않는 일은 없다.
반대로 로스터에 있다는 이유만으로 출전을 추정하지도 않는다 (D-068 유지).

역할과 원소속은 경기별로 저장한다 — `MatchPlayerStat.participantRole` · `rosterLeagueClanId`.

### D-074. 확인 수준(completeness)은 **출전자 전원** 기준이다

`5v5` 같은 표기와 UI 배지는 **실제로 확인된 전체 참가자 수**를 쓴다.
본클랜원만 세서 `3v4`로 표시하지 않는다.

상세 근거는 따로 보존한다 — 이긴 팀·진 팀의 `본클랜원 수`와 `용병 수`를 각각 남긴다.

### D-075. 용병의 원소속 클랜 래더는 변하지 않는다

클랜 래더는 그 경기를 치른 **두 클랜**만 변한다.
리릭 소속 선수가 베리타스 용병으로 이겨도 리릭의 승패·래더는 그대로다.

### D-076. 라인업 전력에 용병을 포함한다

실제로 출전이 확인된 용병도 그 경기의 전력 일부다. 라인업 평균에 넣는다.
단 확인된 선수만 쓴다. 확인 인원이 모자라면 라인업 전력을 아예 반영하지 않는다 (D-065 유지).

### D-077. 시즌 전환은 **운영자 액션**으로만 한다

현재 활성 시즌은 **Season 7**이다. 운영자가 Season 8 시작을 실행하기 전까지 모든 새 공식경기는
Season 7에 기록한다. 날짜·배포·월 변경으로 자동 전환하지 않는다.

### D-078. 시즌 귀속은 **실제 경기 시각**으로 정한다

늦게 수집된 경기는 수집 시각이 아니라 `startAt`으로 시즌을 정한다.

```
Season 8 시작 20:00
19:55 경기 → 20:10에 수집돼도 Season 7
20:05 경기 → Season 8
```

### D-064(개정). 시즌 soft reset 폐기 — 새 시즌은 **모두 같은 출발점**

```
(폐기) newRating = 1500 + (old - 1500) × 0.5
(현행) newRating = seasonBaseline (1500)   ← 개인·클랜 전부 동일
```

전 시즌 1위라고 높은 점수에서 시작하지 않고, 하위권이라고 낮게 시작하지도 않는다.
`seasonCarryRate`는 설정에서 **제거했다.**

**지난 시즌 기록은 그대로 보존한다.** 최종 개인·클랜 랭킹, 최종 rating, 승패, 경기 기록,
시즌 통계(`LeaguePlayerSeason` · `LeagueClanSeason` · `RankSnapshot` · `Match`)를 건드리지 않는다.
`nexon:season-start`가 바꾸는 것은 "지금 시즌의 현재 점수"뿐이다.

## Phase 9 정책 동기화 — 최신 (2026-08-22, authoritative)

> 이 장이 **가장 최신 정책**이다. 앞선 D-057 ~ D-078 중 충돌하는 부분을 대체한다.

### D-079. 공식 경기 인정은 **OR** 조건이다 (D-071 대체)

**양 팀 중 한쪽이라도** 같은 클랜 본클랜원이 3명 이상 확인되면 **공식 경기**다.

```
클3+용2 vs 클3+용2  → 공식        클2+용3 vs 클2+용3  → 비공식 경기
클3+용2 vs 클2+용3  → 공식        클2+용3 vs 클1+용4  → 비공식 경기
클3+용2 vs 클1+용4  → 공식        클1+용4 vs 클1+용4  → 비공식 경기
클3+용2 vs 클0+용5  → 공식
```

```
homeClanMembers >= 3  OR  awayClanMembers >= 3
```

**AND가 아니다.** 기존 D-071의 "양쪽 모두 3명" 기준은 폐기한다.

### D-080. 공식 통계 미반영 경기도 **지우지 않는다**

양쪽 다 3명 미만이어도 경기 자체는 기록실에 남긴다.
참가자·K/D/A·맵·경기시간·결과·양 팀 구성을 그대로 볼 수 있다.

다만 다음에 **전혀 반영하지 않는다**:
시즌 승패 · 시즌 킬/데스 · 킬뎃 · 평균킬 · MVP 누적 · 개인 래더 · 클랜 래더 · 랭킹

`Match.official = false`로 저장하고, 화면에 **`비공식 경기 · 래더 미반영`** 배지를 보여 준다.

### D-081. 클랜 래더 반영률은 **팀마다 독립**이다

같은 공식 경기라도 각 팀의 본클랜원 수에 따라 클랜 래더 반영률이 다르다.

| 본클랜원 | 반영률 |
|---|---|
| 3명 이상 | 100% |
| 2명 | 70% |
| 1명 | 40% |
| 0명 | 0% |

승리·패배 양쪽에 같은 배율을 쓴다.

```
라텐시 클1+용4  vs  메쏘드 클3+용2
원래 증감 +20 / -20  →  실제 라텐시 +8 · 메쏘드 -20
```

**한 경기의 클랜 증감 합이 0이 아닐 수 있다.** 의도된 것이며 장기 영향은 D-083에서 확인했다.

### D-082. 개인 래더에는 차등이 없다

정상 경기라면 **출전이 확인된 모든 선수**가 개인 래더를 100% 받는다.
용병이라는 이유로 승리 점수를 줄이거나 패배 점수를 덜 깎지 않는다.

> 개인 래더는 "그 사람이 실제 경기에서 누구를 상대로 어떤 결과를 냈는가"를 평가한다.
> 클랜 래더는 "그 클랜이 얼마나 자기 전력으로 참가했는가"까지 평가한다.

### D-083. 반영률 차등의 장기 영향 — 측정 결과 문제없다

40클랜 4,000경기 시즌 시뮬레이션(`apps/worker/src/lab/clanWeightSim.ts`).

| 시나리오 | 평균 이동 | 표준편차 | 하한 집중 | 실력 상관 |
|---|---|---|---|---|
| 전원 본클랜원 5명 | -1.7 | 339 | 0 | 0.986 |
| 가끔 용병 (본클 3~5) | -2.1 | 340 | 0 | 0.992 |
| 용병 흔함 (본클 1~5) | -1.4 | 298 | 0 | 0.980 |
| 용병 남용 (본클 0~3) | -4.0 | 199 | 0 | 0.979 |

인플레이션·디플레이션·분포 붕괴·하한 집중 모두 나타나지 않았다.
용병을 많이 쓸수록 클랜 점수가 덜 움직여 분포가 좁아지는 것은 **의도된 효과**다.
숨은 보정을 추가하지 않았다.

### D-084. 경기마다 순차 계산한다

여러 경기가 한꺼번에 발견돼도 `startAt` 오름차순으로 **한 경기씩** 계산한다.
멸망전 6판을 시작 시점 래더로 일괄 계산하지 않는다.
각 경기마다 개인 래더·클랜 래더·라인업 전력을 **직전 경기 결과가 반영된 상태**로 다시 잡는다.

`nexon:rate`는 시즌 전체를 처음부터 다시 계산하므로 이 순서가 항상 보장된다.

### D-085. 시즌 종료 시 최종 랭킹을 스냅샷으로 굳힌다

새 시즌이 시작되면 현재 점수가 초기화되므로, 닫기 전에 그 시즌의 최종 순위를
`RankSnapshot`(클랜은 부리그별, 개인은 전체)으로 저장한다. 경기·시즌 통계는 건드리지 않는다.

### D-086. 시즌 승강은 시즌 시작 시점에만 (기본안 유지)

**1부 최하위 ↔ 2부 최상위** 1팀 교환. 플레이오프는 넣지 않는다.
시즌 중에는 절대 승강하지 않는다. `season --start`를 부를 때만 반영된다.

### D-087. 열산·열빡은 추측으로 분류하지 않는다

넥슨 API로 확실히 구분할 수 없다. 그래서 **추측으로 강제 분류하지 않는다.**
현재는 본클랜원 구성 조건(D-079)이 사실상 그 역할을 한다 — 클랜원이 모이지 않은 경기는
자동으로 비공식 경기이 되어 공식 통계에서 빠진다.
확실하지 않은 것은 `reconstruction` 근거와 confidence로 남긴다.

### D-088. 클랜 자동 병합 금지 (운영 규칙)

`Veritas` · `VERITAS` · `베리타스`를 이름이 비슷하다는 이유로 같은 클랜으로 묶지 않는다.
병합은 운영자가 **정확한 slug 두 개를 지정**할 때만 실행된다(`nexon:clan --merge --from --into`).
병합해도 원본 클랜 행을 **삭제하지 않고** 이름에 표시만 남긴다 — 되돌릴 수 있어야 한다.

## Phase 10 — 베타 운영 준비 (2026-08-22)

### D-089. 운영 기능은 **CLI와 웹이 같은 코드**를 쓴다

시즌·클랜·로스터 운영 로직을 `packages/db/ops/`에 두고 `apps/worker`(CLI)와
`apps/web`(관리자 화면)이 함께 부른다. 두 경로가 갈라지면 "CLI로는 되는데 화면으로는
다르게 되는" 사고가 난다.

### D-090. 관리자 권한은 **서버에서** 판정한다

`requireAdmin(request)`가 모든 관리자 API의 첫 줄이다. 화면에서 버튼을 감추는 것은 보안이 아니다.
비로그인·일반 사용자가 요청을 직접 만들어 보내도 403이다 (조회·변경 모두 테스트로 고정).

### D-091. 파괴적 작업은 **미리보기 → 확인** 두 단계다

시즌 종료·시작은 `confirm: false`(기본)면 미리보기만 한다.
무엇이 바뀌는지(스냅샷 건수·승격/강등 클랜·초기화 대상 수)를 보여 준 뒤에만 실행된다.
실행은 **트랜잭션**이라 "시즌 7은 닫혔는데 8이 없는" 중간 상태가 생기지 않는다.

### D-092. 삭제 대신 **비활성·종료 표시**를 쓴다

- 클랜은 `active = false`로 감춘다. 행을 지우지 않는다
- 로스터에서 뺄 때는 `leftAt`을 찍는다. 지우면 **과거 경기의 소속 판정이 바뀐다**
- 클랜 병합도 원본 행을 남기고 이름에 표시만 더한다

### D-093. 클랜 별칭(`ClanAlias`)은 운영자가 등록할 때만 생긴다

넥슨 `guild_name`이 우리 클랜명과 글자가 다를 수 있다. 그 연결은 팀 식별의 1차 근거지만
(D-072), **비슷하다고 자동으로 만들지 않는다** (D-088). 관리자 화면에서 등록한 것만 쓴다.

### D-094. 베타오픈 시각은 설정값이다 (`AppSetting.betaOpenedAt`)

코드에 날짜를 박지 않는다. 운영자가 관리자 API로 정한다. 정해지기 전에는 `미설정`이다.

### D-095. 공식 ↔ 비공식 전환은 비대칭이다

운영자가 잘못 인식된 경기를 바로잡을 수 있어야 한다 (정책 18).

- **공식 → 비공식**: 바로 된다. 통계에서 빼는 방향이라 안전하다
- **비공식 → 공식**: `reason`을 적어야만 된다. 근거 없이 통계에 넣지 않는다

어느 쪽이든 `AdminAuditLog`에 남고, 래더에 반영하려면 `nexon:rate`를 다시 돌려야 한다.

### D-096. 검증 도구는 **실운영 데이터가 들어와도 흔들리지 않아야 한다**

Phase 10 E2E에서 실제로 깨졌던 것들을 고쳤다.

| 도구 | 문제 | 수정 |
|---|---|---|
| `db:check` | 전체 개수를 세서 실운영 클랜·리그가 생기자 실패 | **픽스처가 만든 행만** 센다 |
| `nexon:check` | "참가자 전원이 로스터로 뒷받침" — 용병은 원래 아니다 | **본클랜원만** 검사 |
| `nexon:check` | "양 팀 인원 균형" — 확인 수준은 원래 다를 수 있다 | 검사 삭제 |
| `nexon:check` | 인정 기준이 AND로 남아 있었다 | **공식 경기만** OR 조건 검사 + 비공식 경기 래더 미반영 검사 추가 |
| `compare` | 실제 리그가 생기자 목록 길이가 달라 실패 | **픽스처 항목만** 골라 대조 |
| 오프라인 스모크 | 전역 `origin=nexon` 개수를 세고 있었다 | 스모크 리그로 범위 제한 (D-045와 같은 실수) |

> 검사가 정상적인 운영 데이터에 반응해 실패하면, 진짜 문제와 구분할 수 없게 된다.

### D-097. 라플/스나 포지션 래더는 **데이터가 없어서 구현하지 않는다** (D-034 재확인)

경기별 라플/스나를 나누려면 "이 선수가 **이 경기에서** 어떤 역할이었나"를 알아야 한다.
실제 저장된 원본을 다시 뒤져서 확인했다 (`pnpm --filter @sacloud/worker exec tsx src/dev/probeWeaponRole.ts`).

**넥슨 `match-detail` 참가자 필드는 이게 전부다.**

```
user_name  team_id  match_result  guild_name  season_grade
kill  death  assist  headshot  damage
```

무기·역할·병과·포지션에 해당하는 키는 **하나도 없다.** `match` 목록에도 없다.
정규식(`weapon|gun|rifle|sniper|role|class|position`)으로 전체 키를 훑어도 0건이다.
즉 **normalize에서 버리고 있는 값이 아니라, 원본에 처음부터 없다.**

| 출처 | 무기 정보 | 왜 못 쓰는가 |
|---|---|---|
| `/match-detail` | 없음 | 필드 자체가 없다 |
| `/match` 목록 | 없음 | 필드 자체가 없다 |
| `/user/recent-info` | **총기별 킬데스는 있다** | **계정 단위 최근 누적**이다. 경기 하나를 라플/스나로 판정할 수 없다 |
| mock 픽스처 `weapon` 0/1 | 있어 보이지만 | `rng.chance(0.22)`로 **생성한 난수**다. 정보가 아니다 |
| 실수집 `MatchPlayerStat.weapon` | 전부 `null` | 7건 모두 `null` (D-034대로) |
| 3rd.supply 원본 사이트 | 있었다 | 그쪽 자체 데이터다. 우리에게 임포트된 적이 없다 (`origin='3rd.supply'` 0건) |

**딜량·헤드샷으로 추정하지 않는다.** 스나이퍼가 헤드샷이 많고 딜량이 낮은 경향은 있지만,
경향은 판정이 아니다. 틀린 분류는 그 선수의 포지션 래더·포지션 킬뎃·포지션 랭킹을 전부 오염시키고,
사용자는 그게 추정값이라는 것을 알 수 없다.

**그래서 다음 중 하나가 생기기 전까지 포지션 래더를 만들지 않는다.**

1. 넥슨이 `match-detail` 참가자에 무기/역할 필드를 추가한다
2. 경기별 역할을 **사람이 입력**하는 경로를 만든다 (선수 자기 신고 또는 운영자 입력).
   이 경우 `roleSource` / `roleConfidence`를 반드시 같이 남겨서 추정과 구분한다
3. 역할이 기록된 외부 데이터를 확보한다

지금 스키마·래더·랭킹·UI를 먼저 만들어 두는 것도 하지 않는다.
분류를 한 건도 받을 수 없는 통계 화면은 "라플 0판 / 스나 0판"만 영원히 띄운다.

#### 보강 (2026-08-22) — 3rd.supply 쪽에는 **경기별 weapon이 실제로 있다**

정상 브라우저 실측으로 확인된 내용을 기록만 해 둔다. **결론은 바뀌지 않는다.**

```
GET https://api-v2.3rd.supply/leagues/1/players/{playerId}/matches
SSR payload: data.matches.data[]
경기 summary 안: matches[].summary.red[] / matches[].summary.blue[]
  { "player": { "id": 1963120755, "name": "천세", "clan": null }, "weapon": 1 }
```

- `weapon 0 = 라이플` · `weapon 1 = 스나이퍼` — 렌더된 화면과 10명 전원 일치
- 같은 선수의 값이 **경기마다 달라진다** → 계정 고정값이 아니라 **경기별 값**이다

그래도 지금 우리가 쓸 수 없는 이유는 그대로다.

1. **우리 수집 경로(넥슨 Open API)에는 이 필드가 없다.** 위는 3rd.supply 자체 데이터다
2. 그 값의 **원 출처가 무엇인지 검증되지 않았다** (넥슨이 준 값인지, 그쪽에서 입력·추정한 값인지)
3. 3rd.supply 접근은 **WAF로 막혀 있다**(D장). 우회하지 않는다

적용 범위도 시즌마다 다르다.

| 시즌 | weapon 취급 |
|---|---|
| Season 1~7 (legacy) | 원본에 있으면 **그대로 보존**만 한다. 지금 legacy 이관은 시즌 카드 단위라 경기별 weapon이 들어올 자리가 아직 없다 |
| Beta | 신규 경기 weapon을 **정상·안정·허용된 경로로** 확보할 수 있을 때만 시험한다. 없으면 `weapon = null`, 역할 랭킹 미출시 |
| Season 8 | 베타에서 그 경로가 검증된 경우에만 라플/스나 랭킹 정식 적용. 아니면 계속 보류 |

헤드샷률·딜량·킬수로 추정하지 않는다는 규칙은 어느 시즌에도 예외가 없다.

### D-098. 베타 시즌은 **번호 0**이고, 사용자에게는 `Beta Season`이다

사용자에게 보이는 시즌 흐름은 하나로 이어져야 한다.

```
Season 1 … Season 7 → Beta Season → Season 8
```

`@@unique([leagueId, number])` 때문에 베타에도 번호가 필요한데, 정식 번호를 쓰면
Season 7 다음이 8이 아니게 된다. 그래서 **0**을 쓴다.

- 다음 정식 번호는 `max(number)+1`로 뽑으므로 7 다음은 그대로 8이다
- **화면에 "Season 0"이라고 쓰지 않는다.** 표기는 `seasonLabel()` 한 곳에서만 정한다
- 화면 정렬은 번호가 아니라 **`startedAt`** 기준이다. 그래야 베타가 7과 8 사이에 온다

`Season.seasonType`은 `legacy` | `beta` | `official` 셋이다.
`legacy`는 3rd.supply에서 이전된 기록이고 **재계산 대상이 아니다**.

### D-099. 과거 시즌 카드의 빈 값은 `null`이다. 역산하지 않는다

3rd.supply의 지난시즌 응답에는 `rank rank_count win lose win_rate kill death kd_rate`만 있다.
`rating` `assist` `headshot` `kill_per_match` `mvp_count` `clan` `division`은 없다.

승률·킬뎃은 승패·킬데스로 계산할 수 있지만 **계산하지 않는다.**
원본이 준 값과 반올림이 다를 수 있고, 그러면 그 시즌의 화면과 우리 화면이 어긋난다.
원본에 있으면 그대로 저장하고, 없으면 `null`로 둔다.

없는 값을 채우려면 시즌 **마감 직전**의 현재 성적을 따로 떠서 병합해야 한다.
`mergeRows()`가 그 일을 한다 — 뒤에 오는 `null`이 앞의 값을 덮지 않는다.

### D-100. 과거 기록은 **닉네임으로 사람을 합치지 않는다**

닉변·동명이인·OUID 변경이 전부 실재한다. 닉네임이 같다는 이유로 과거 카드를 붙이면
엉뚱한 사람의 프로필에 남의 시즌 성적이 들어간다.

그래서 과거 선수는 3rd.supply `player.id`로만 만든다 — `Player.id = "SUPPLY-{playerId}"`.
`legacyPlayerId` / `legacyLeaguePlayerId` / `nicknameAtSeason`을 그대로 보존한다.
현재 신원(`NexonIdentity`)과의 연결은 **근거가 있을 때 운영자가** 한다.

### D-101. 시즌을 닫을 때 **카드**를 남기고, 시작할 때 **누적까지** 0으로 되돌린다

Phase 11에서 찾은 실제 버그 두 개다. 둘은 같이 고쳐야 한다.

| 문제 | 결과 |
|---|---|
| `startSeason`이 rating만 되돌렸다 | 베타의 승패·킬데스·MVP가 다음 시즌에 그대로 남는다 |
| `closeSeason`이 시즌 카드를 안 만들었다 | 위를 고치는 순간 그 시즌 성적이 통째로 사라진다 |

또 시즌 시작 로직이 `ops`와 `apps/worker`에 **두 벌** 있었다. 한쪽만 고치면
CLI로 시작할 때 격리가 안 된다. `runSeasonStart`는 이제 `startSeason`에 위임한다.

무기별 누적(`LeaguePlayerWeaponStat`)도 같이 비운다 —
`통합 = baseRating + 무기별 delta 합` 불변식이 깨지기 때문이다.

### D-102. `[폐기됨 — D-107로 대체]` 무소속은 계산 조건이 아니라 공개 범위 조건이다

> **2026-08-23 폐기.** "무소속 선수의 장기 누적 개인 기록을 숨긴다"는 결론은 더 이상 쓰지 않는다.
> 무소속리그는 별도 리그이고 개인 기록·개인 랭킹이 정상으로 존재한다. 감추는 것은
> **누적 kill/death/킬뎃 세 가지뿐**이다 — **D-107**을 본다.
>
> 아래 본문에서 아직 유효한 부분은 하나다: **무소속을 래더 계산에서 빼지 않는다.**
> 그 이유(라인업 전력 계산에 실제 실력값이 필요하다)는 D-107에서도 그대로 유지된다.

먼저 잘못 구현했던 것을 적는다. 처음에는 `Clan.category === 'independent'`인 팀의
참가자를 **래더 계산에서 뺐다**. 그건 틀렸다.

왜 틀렸나
  클랜 경기의 전력차를 계산하려면 **실제 참가 선수의 실력값**이 필요하다.
  무소속 선수를 계산에서 빼거나 1500 고정으로 두면,
  `무소속 A(라인업 평균 1700) vs 무소속 B(1450)` 같은 경기의 예상 승률이 통째로 틀어진다.
  그러면 무소속 클랜의 래더도 같이 틀린다.

확정된 정책

| 단계 | 무소속을 어떻게 다루나 |
|---|---|
| 경기 저장·공식 판정 | 1부/2부와 **완전히 동일** |
| 클랜 래더 (Team Elo) | 동일. 무소속 전용 K값·전용 공식 없음 |
| 개인 래더·개인 누적 | **계산하고 저장한다**. 생략하지 않는다 |
| 사용자 화면 | 그 선수의 **장기 누적 개인 기록**만 숨긴다 |

즉 "수집 안 함 / 계산 안 함 / 저장 안 함"이 아니라 **"사용자에게 숨김"** 하나다.

숨기는 곳은 조회 계층 한 곳이다 — `apps/web/lib/server/queries/visibility.ts`.
개인 랭킹 목록과 **순위 계산 모집단**에서 같이 빼야 한다.
한쪽만 빼면 "N명 중 M위"의 명수와 등수 기준이 어긋난다.

숨기지 않는 것: 경기 상세(참가자·K/D/A·맵·시간·승패), 클랜 래더, 클랜 승패, 상대별 전적.
개별 경기 결과는 숨기지 않는다. 숨기는 것은 장기 누적 커리어뿐이다.

### D-103. 공식 판정과 클랜 가중치는 **순서가 있는 별개 단계**다

섞으면 둘 다 틀린다.

```
1단계  공식인가?        homeMembers >= 3  OR  awayMembers >= 3     ← 경기 하나에 한 번
2단계  얼마나 반영하나?  팀마다 자기 본클랜원 수로 100/70/40/0%     ← 팀마다 따로
```

`클1+용4 vs 클5`는 **공식**이다(오른쪽이 3명 이상). 그리고 클랜 반영은 40% / 100%다.
1단계에서 떨어뜨리면 안 되고, 2단계의 40%를 인정 조건으로 쓰면 안 된다.

가중치는 승패 **양방향 모두** 같게 적용한다. 이길 때만 깎지 않는다.
양쪽 가중치가 다르므로 한 경기의 증감 합이 0이 아닐 수 있다 — **의도된 것이다**.
zero-sum으로 맞추는 normalization을 넣지 않는다.

개인 래더에는 가중치가 없다. 용병도 100%다.

### D-104. 클랜 순위는 **네 가지**이고 서로 섞지 않는다

| 순위 | 모집단 | 정렬 | 쓰임 |
|---|---|---|---|
| 1부 standings | 1부만 | rating | **승강 판단** |
| 2부 standings | 2부만 | rating | **승강 판단** |
| 무소속 Tier 내 순위 | 같은 Tier만 | rating | Tier 화면 |
| 무소속 전체 래더 | 무소속 전부 | rating | Tier **무시** |
| 전체 통합 래더 | 1부+2부+무소속 | rating | 부리그·Tier **무시** |

두 가지가 특히 중요하다.

**① Tier는 rating으로 자동으로 움직이지 않는다.**
Tier 1의 W가 1500이고 Tier 2의 A가 1800이어도 W는 Tier 1, A는 Tier 2다.
`Clan.tier`는 운영자가 정한 값이고 순위 계산은 그 값을 **읽기만** 한다.
점수 구간 → Tier 매핑은 코드 어디에도 없다. 무소속 Tier 1의 1부 진입은
운영자 승인 방식이며 자동 승격 로직을 만들지 않는다.

**② 전체 래더는 Tier도 부리그도 보지 않는다.**
Tier 5 클랜이 전체 1위일 수 있고, 2부 클랜이 1부 클랜보다 위일 수 있다.
정렬 기준은 `rating` 하나뿐이고, 동점은 id로 고정한다.

한 무소속 클랜은 **두 순위를 동시에** 가진다 — `tier_rank`와 `overall_rank`.
둘 다 파생값이라 저장하지 않고 질의로 계산한다.

무소속 클랜의 승·패·승률·rating·최근 경기·상대 전적은 **전부 공개한다.**
숨기는 것은 무소속 선수의 **장기 누적 개인 기록**뿐이다 (D-102).

### D-105. 베타 안내는 **배지 + 리그홈 안내 한 번**이다

베타는 공개 시즌이다(D-098). 그래서 두 가지를 동시에 지켜야 한다 —
**숨기지 않는다**, 그리고 **과도한 경고 UI를 만들지 않는다**.

| 어디 | 무엇 |
|---|---|
| 리그 서브내비 (모든 리그 화면) | `Beta Season` 배지. tooltip에 승계 안내 한 문장 |
| 리그홈 헤더 아래 (한 번) | 제목 + 두 문장 안내 |

```
Beta Season
현재 SACLOUD 래더 시스템을 검증하는 공개 테스트 시즌입니다.
베타 시즌의 랭킹과 점수는 정식 Season 8에 승계되지 않습니다.
```

- 랭킹·기록실·프로필 화면에 같은 안내를 반복하지 않는다. 배지가 이미 상시로 알린다
- 경고색(빨강)·모달·상시 배너를 쓰지 않는다. 베타는 사고가 아니라 공개 운영 상태다
- 문구는 `packages/ui/src/league/betaNoticeText.ts` **한 곳**에서만 정한다.
  화면마다 다시 쓰면 문장이 갈라진다
- 시즌 종류를 **모를 때는 아무것도 띄우지 않는다.** 로딩 중에 경고가 번쩍이면 안 된다

### D-106. 과거 기록에 **없는 값은 `null`이다.** 0으로 채우지 않는다

Phase 11 감사에서 찾은 실제 버그다. 파서는 규칙을 지켰는데 **importer가 어겼다.**

```
parser        win: null        ← 원본에 없으니 null (D-099 준수)
importer      win: row.win ?? 0   ← 여기서 0이 됐다
화면          0승 0패 · 승률 56.9%   ← 거짓 기록
```

3rd.supply 시즌 카드는 **시즌마다 제공 필드가 다르다.** 시즌 6은 승패·킬데스를 주지만
시즌 4는 순위·승률·킬뎃만 준다. 그 시즌에 0을 넣으면 "0번 이겼다"가 되는데, 사실은 "모른다"다.
**0과 모름은 다른 값이고, 한 번 섞으면 되돌릴 수 없다.**

확정 사항

| 곳 | 규칙 |
|---|---|
| `LeaguePlayerSeason.rating/win/lose/kill/death` | **nullable**. 마이그레이션 `20260822235000_legacy_season_nullable_stats` |
| importer | `legacySeasonCardData()` 한 곳에서 매핑. `?? 0` 금지 |
| 조회 계층 | `winRateOrNull` / `kdRateOrNull` — 입력이 모르면 결과도 `null` (0%로 만들지 않는다) |
| 화면 | `알수없음` (프로젝트 표기 규칙과 동일) |

SACLOUD가 계산한 카드(`closeSeason`)는 값이 **항상 있다.** nullable은 과거 기록을 위한 것이지
우리 계산 결과를 비워도 된다는 뜻이 아니다.

같이 고친 것: 지난시즌 표가 `season.season`을 그대로 찍어 **베타 카드가 `시즌 0`** 으로 보였다.
서버가 주는 `season_label`을 쓰도록 바꿨고, 클랜 시즌 응답에도 `season_label`/`season_type`을 넣었다 (D-098).

### D-107. 무소속리그는 **리그다.** 개인 기록도 랭킹도 존재한다 (2026-08-23 확정)

**이전 결정을 폐기한다.** D-102의 "무소속 개인 커리어를 숨긴다"도,
그보다 앞선 "무소속 개인 커리어를 만들지 않는다"도 둘 다 아니다.

#### 확정 정책

무소속리그는 공식리그와 **완전히 별개인 리그**이고, 그 안에 개인 기록이 정상으로 존재한다.

| | 무소속리그 | 공식리그 |
|---|---|---|
| 개인 rating · ranking | **있다** | 있다 |
| 승 · 패 · 승률 · 평균킬 · MVP | **있다** | 있다 |
| 시즌 카드 · 최근 경기 · 경기 상세 | **있다** | 있다 |
| 경기 한 판의 K/D/A | **보인다** | 보인다 |
| **누적** kill · death · 킬뎃 | **화면에 안 보인다** | 보인다 |

숨기는 것은 그 하나뿐이다. `23 / 7 / 3` 같은 그 경기 성적은 숨기지 않고,
`시즌 누적 13,123킬 / 12,837데스 / 50.6%` 만 내보내지 않는다.

**저장은 그대로 한다.** DB에는 누적 킬·데스가 계속 쌓이고 계산에도 쓴다.
정하는 것은 "응답에 넣는가"뿐이다.

#### 기록은 리그 단위로 완전히 분리된다

같은 선수라도 리그가 다르면 **다른 그릇**이다.

```
길수 + 무소속리그   100전 89승 11패  rating 1742
길수 + 공식리그     238전 149승 89패 rating 1625
```

한쪽 경기 결과가 다른 쪽 rating·승패·랭킹·최근 경기·시즌 카드에 닿는 경로가 없어야 한다.
**기록이 쌓이는 곳을 정하는 것은 선수의 현재 소속이 아니라 "어느 리그 경기였는가"다.**
무소속 클랜 선수가 공식리그에 용병으로 뛰면 그 경기는 공식리그 기록이고,
공식리그 카드에는 누적 킬뎃이 정상으로 나온다.

#### 구현 — 스키마를 다시 짜지 않았다

개인 기록은 이미 리그 단위였다.

```
LeaguePlayer        @@unique([leagueId, playerId])   rating·승패·킬·데스·MVP
LeaguePlayerSeason  @@unique([leaguePlayerId, seasonId])
Match.leagueId
```

그래서 무소속리그는 **별도 League 행**으로 둔다. 추가한 것은 컬럼 하나뿐이다.

- `League.category` = `official` | `independent` (기본 `official`)
- 마이그레이션 `20260823001500_league_category` — 추가만, 파괴적 변경 없음
- 공개 범위 판단은 `apps/web/lib/server/queries/visibility.ts` 한 곳
- 응답 계약에 `LeagueSummary.hides_cumulative_kd` 를 실어 화면이 이유를 알 수 있게 했다
- 감출 때는 `null`이다. **0으로 만들지 않는다** — 0킬은 사실이 아니다
- 화면은 `null`이면 그 항목·칸을 **아예 그리지 않는다** (`알수없음`으로도 쓰지 않는다.
  그건 "원본이 값을 안 줬다"는 뜻이라 D-106과 섞인다)

#### 폐기된 동작

`PUBLIC_CAREER_WHERE`로 개인 랭킹 목록과 순위 모집단에서 무소속 선수를 빼던 것,
`isCareerPublic`으로 순위를 `null`로 만들던 것 — 둘 다 제거했다.
무소속리그 선수는 자기 리그 안에서 정상으로 순위를 받는다.

회귀 테스트는 `apps/web/tests/independentLeague.test.ts` 24건이다
(실제 DB에 임시 리그 두 개를 만들어 조회 함수를 그대로 돌린다).


### D-108. 클랜은 **등록된 순간부터** 기록이 시작된다. 소급하지 않는다

무소속 클랜은 운영자가 등록하기 전까지 SACLOUD에 존재하지 않는다.
등록 전에 치른 경기를 나중에 끌어와 공식 기록으로 만들면, 그 클랜만 과거가 생긴다.

```
8/25 18:00 A클랜 무소속 등록
  8/25 17:59 경기 → A클랜 기록 아님
  8/25 18:01 경기 → A클랜 기록 대상
```

**새 컬럼을 만들지 않았다.** `LeagueClan.joinedAt`이 이미 "이 클랜이 이 리그에 참여한 시각"이고,
등록이 곧 리그 참여다. 재구성이 그 값을 읽어 경기 시각과 비교한다
(`ReconstructionLeague.clanJoinedAt`, 미충족 시 `before_registration`).

1부·2부에도 같은 규칙이 적용된다. Beta로 승계된 클랜은 `joinedAt`이 Season 7 때 값이라
Beta 구간(8/20~) 경기가 정상으로 통과한다.

### D-109. 신원 연결은 **닉네임 + 실제 경기 근거**가 함께 있을 때만 한다

D-036("닉네임으로 자동 병합하지 않는다")은 그대로다. 다만 "사람이 하나씩 손으로"만
가능하면 5,000명 규모에서 아무것도 못 한다. 그래서 **근거를 요구하는 자동화**를 만들었다.

연결 조건 세 가지를 **전부** 만족해야 한다.

1. 운영자가 등록한 로스터의 선수 이름과 **정확히** 같다 (유사도 매칭 없음)
2. 그 계정의 **실제 경기 이력에 찍힌 `guild_name`** 이 로스터의 클랜과 같다
3. 일치가 `minEvidence`건(기본 3) 이상이고, 다른 클랜으로 찍힌 비율이 20% 이하다

즉 "이름이 같다"가 아니라 **"이 계정이 실제로 그 클랜으로 뛰었다"** 를 본다.
D-051에서 틀렸던 사례(닉네임으로 찾은 계정의 목록에 그 경기가 없었다)는 2번에서 걸린다.

연결 근거는 `linkReason`에 문장으로 남는다. 사람이 보고 끊을 수 있어야 하기 때문이다.
`pnpm --filter @sacloud/worker nexon identity-link --league <slug>` 는 기본이 미리보기이고,
`--confirm` 을 붙여야 실제로 연결한다.

### D-112. 공개 Beta는 **1경기부터** 래더를 계산한다 (Beta 전용 예외)

배치고사 10경기 정책(3-B 7번)은 **정식 시즌의 규칙이고 그대로 남는다.**
바꾸는 것은 공개 Beta 한 시즌뿐이다.

**왜:** Beta의 목적이 "래더가 실제로 어떻게 움직이는지 보는 것"인데,
10경기를 채우기 전에는 전원 1500이고 랭킹도 비어 있어서 아무것도 검증되지 않는다.

| | Beta Season | Season 8+ |
|---|---|---|
| 래더 계산 시작 | **1경기부터** | 배치고사 10경기 이후 |
| 개인 랭킹 노출 | **1경기부터** | 배치고사 종료 후 |
| 공식 경기만 반영 | 그대로 | 그대로 |

**하드코딩하지 않았다.** `constantsForSeason(base, season, flags)` 한 곳에서 정한다.

```
seasonType === 'beta'  &&  flags.betaImmediateRating
  → { ...base, placementMatches: 0 }
그 외 → base 그대로
```

- `official` · `legacy` · 시즌 미상 → **손대지 않는다**
- 배치고사 말고 다른 상수는 바꾸지 않는다
- 스위치를 끄면(`betaImmediateRating: false`) Beta도 기존 정책으로 돌아간다
- Beta가 끝나도 정식 시즌 정책이 따라 바뀌지 않는다 — 조건이 `seasonType`이기 때문이다

회귀 `packages/rating/src/__tests__/seasonPolicy.test.ts` 9건.
그 중 절반이 **"정식 시즌이 안 깨졌는가"** 를 본다. 예외를 넣을 때 가장 위험한 것이
예외가 본 규칙까지 바꿔 버리는 것이라서다.

### D-113. 래더 재계산은 **시즌 누적 전적도 같이** 쓴다

`nexon:rate`가 rating만 되돌려 쓰고 승패·킬·데스·어시스트를 안 쌓고 있었다.
그래서 경기가 6건 들어왔는데 화면에는 `0승 0패`로 보였다.

replay 도중 확정된 참가자에서 승패와 K/D/A를 함께 누적해
`LeaguePlayer` / `LeagueClan`에 같이 기록한다. 래더와 전적이 **같은 replay**에서 나오므로
서로 어긋날 수 없다.

### D-114. 라플/스나는 **병영수첩 BattleLog의 킬 신호**로 판정한다 (D-097 갱신)

D-097의 결론("넥슨 Open API에 무기가 없어 역할 래더 불가")은 **Open API에 대해서는 그대로**다.
바뀐 것은 **보조 출처가 생겼다**는 것이다.

```
POST /api/BattleLog/GetBattleLogClan/{match_key}/{clan_no}     ← 무기별 킬
POST /api/Match/GetMatchClanDetail/{match_key}/C/{clan_slug}   ← AR/SR 적중 (조건부)
```

#### 실측한 응답 구조 (2026-08-23)

**BattleLog는 집계표가 아니라 이벤트 로그다.** 한 줄에 한 사건이고,
같은 사건이 **가해자·피해자 두 관점으로** 들어온다.

```
{ event_type: 'kill',  user_nexon_sn, user_nick, weapon: 'riple' }
{ event_type: 'death', user_nexon_sn, target_user_nexon_sn, target_weapon: 'sniper' }
```

그래서 `event_type === 'kill'` 행만 센다. 두 관점을 다 세면 **킬이 두 배가 된다.**
실제 확인한 한 경기(90 이벤트 · kill 49 · death 38)에서 선수별로 깨끗하게 갈렸다.

```
째근호 riple 10 · 채운2 sniper 4 · SC3..나실인 riple 13 · 제니 sniper 6 · 천사순수 riple 6
```

#### 판정 규칙

| 신호 | 근거 |
|---|---|
| 킬 신호 | `riple` vs `sniper` 킬 수. **`throw`·`assist`·`close`·`special`·`c4-install` 제외** |
| 적중 신호 | AR vs SR 적중 수 |

- 두 신호가 같으면 그 답
- **어긋나면 `unknown`** — 한쪽을 이기게 하지 않는다
- 하나만 있으면 그것으로 판정, 둘 다 없으면 `unknown`
- **동률이면 `unknown`.** 0킬도 `unknown` (0킬은 무기 근거가 아니다)
- 선수 고정 포지션 금지 — 판정 단위는 **경기 × 선수**
- 헤드샷·딜량으로 추정하지 않는다 (D-097의 금지 규칙 유지)

#### 재현하지 못한 것

전달받은 조사 결과 중 **AR/SR 교차검증(24/24)은 이 세션에서 재현하지 못했다.**
`GetMatchClanDetail` 응답의 `user_battle_info`에 `M_PLAYER_hit_AR_*` 키가 **없었다**
(키 9개 · 중첩 `MatchData`는 빈 배열). 경기·모드에 따라 제공 여부가 다른 것으로 보인다.

그래서 지금 동작하는 것은 **킬 신호 단독 판정**이고, 적중 신호는 값이 올 때만 교차검증에 쓴다.
3rd.supply 30/30 비교도 재현하지 않았다 — 그쪽은 WAF로 막혀 있다.

**구현 상태**: 판정기와 파서는 완성됐고 회귀 18건으로 고정했다
(`packages/nexon/src/__tests__/weapon.test.ts`).
DB 저장(`weapon` 컬럼 채우기)과 라플/스나 버킷 집계는 **아직 붙이지 않았다.**

### D-115. 라플/스나 누적은 **판정된 공식 경기만** 쌓는다

`LeaguePlayerWeaponStat`(이미 있던 모델)을 그대로 쓴다. 새 모델을 만들지 않았다.

| | 규칙 |
|---|---|
| 대상 | **공식 경기만**. 비공식은 통합 기록에도 안 들어간다 (D-080) |
| `unknown` | 어느 버킷에도 넣지 않는다. 통합 기록에는 이미 들어가 있다 |
| deaths | 그 경기 death **전부**를 그 역할 버킷에 넣는다. "무엇에 죽었나"는 역할별 KD와 무관하다 |
| 재작성 | 처음부터 다시 만든다. 두 번 돌려도 값이 두 배가 되지 않는다 |
| 래더 | 무기별 래더는 **만들지 않는다.** 통합 래더가 진실이다 (`CLAUDE.md` 3-B 1·2번) |

화면은 판정된 경기가 하나도 없으면 **패널 자체를 그리지 않는다.**
`0경기 0킬 0데스`는 정보가 아니라 소음이다.

수집은 정상 브라우저가 하고 워커는 그 결과 파일을 읽는다 — Node에서 병영수첩을 부르면
403이고, UA를 위조해 뚫지 않는다.

```bash
pnpm nexon:weapon-import  --file <수집.json> [--confirm]   # 원문 + 근거 (멱등)
pnpm nexon:weapon-apply   [--confirm]                      # 근거 → MatchPlayerStat.weapon
pnpm nexon:weapon-rebuild --league <slug> [--confirm]      # 공식 경기 → 라플/스나 누적
```

판정기를 고쳐도 **외부에 다시 요청하지 않는다.** 저장된 근거에서 다시 계산한다.

### D-116. 공개 화면에는 **시드가 나가지 않는다** — `origin` 한 컬럼으로 거른다

Phase 11 감사에서 확인한 것: **공개 경로 전체가 개발용 시드를 필터 없이 노출하고 있었다.**
조회 계층 12개 파일 어디에도 걸러내는 코드가 한 줄도 없었다.

실측된 노출 범위 (전부 재현 확인)

| 화면 | 무엇이 보였나 |
|---|---|
| 전역 GNB | 시드 리그 3개가 **하드코딩**. 실제 운영 리그로 가는 링크는 사이트에 0개였다 |
| 리그 목록 · 리그 상세 | 시드 리그 4개 |
| 1부/2부/통합/개인 랭킹 | 전부 시드. **베타 배지도 안 붙었다**(시드 시즌이 `official`이라) |
| 통합검색 | 시드 선수 920 · 클랜 60 |
| 게시판 · 홈 인기글 | 시드 글 400건. **공지 게시판까지** |
| 기록실 · 경기 상세 | 시드 경기 3,000건 |
| `/api/infos` | 존재하지 않는 리그의 게시판 탭 3개 |

즉 방문자는 **가짜 리그 3개와 가짜 커뮤니티**를 먼저 보고, 진짜 Beta 리그는 URL을 직접 쳐야 도달했다.

#### 판별자

`origin` 컬럼 하나다. `Match.origin`이 이미 하던 일을 **League · Clan · Player · Board**로 넓혔다.
시드는 `mock`, 그 외는 `sacloud` / `nexon` / `3rd.supply`.

경기 수를 세거나 slug를 하드코딩해 추측하지 않는다. 백필 판별자는 **id가 순수 숫자인가**였다 —
시드는 원본 사이트의 숫자 ID를 흉내낸 결정적 픽스처이기 때문이다. 실측 대조로 확인했다:
League 4/5 · Clan 60/68 · Player 920/943 · Board 400/401 이 숫자 ID였고 **시드 건수와 정확히 일치**했다.

#### 거르는 곳은 한 곳이다

`apps/web/lib/server/queries/publicScope.ts`. 목록은 `publicOriginWhere()`,
단건은 `isPublicRow()`로 판정해 **없는 것처럼 404**를 낸다 — "있지만 숨김"이 아니다.
시드가 존재한다는 사실 자체를 흘리지 않는다.

리그 스코프 경로는 `resolveLeagueId()` / `getLeagueIdBySlug()` **한 곳만 막으면**
랭킹·기록실·매치 상세가 함께 닫힌다.

#### 스위치가 있는 이유

`pnpm compare`(Mock ↔ 실제 API 값 대조)는 **실제 API가 시드를 그대로 돌려주는 것**이 전제다.
그 도구를 죽이지 않으려고 `SACLOUD_PUBLIC_SCOPE=all`로 열 수 있게 뒀다.
**기본값은 감춘다.** 설정을 빠뜨렸을 때 안전한 쪽으로 실패해야 한다.

#### 함께 뒤집은 것 — `API_MODE` 기본값

`resolveApiMode()`의 기본값이 `mock`이었다(fail-open). 배포에서 `NEXT_PUBLIC_API_MODE`를
빠뜨리면 **공개 사이트 전체가 MSW 픽스처로 동작**하고 개발용 역할 전환 위젯까지 떴다.
`NEXT_PUBLIC_*`은 빌드 시점에 인라인되므로 되돌리려면 재빌드가 필요하다.
기본값을 `live`로 뒤집고 `mock`을 명시적 opt-in으로 바꿨다.

#### 지우지 않는다

DB의 시드 행을 삭제하지 않는다. 저장·계산은 그대로 두고 **응답에 넣는가**만 정한다.
(누적 킬뎃 비공개는 다른 축이다 — `visibility.ts` D-107)

### D-117. 리그 선수는 **클랜에 연결돼 있어야** 조회 계층이 성립한다

Phase 11 감사에서 찾은 실제 버그다. 공개 Beta의 **선수 축이 통째로 죽어 있었다.**

`LeaguePlayer.clanId`가 실데이터 리그 11명 **전원 null**이었다.
`rate.ts`가 `LeaguePlayer`를 만들 때 rating·승패·K/D/A만 넣고 `clanId`를 빼먹었기 때문이다.

조회 계층이 "리그 선수는 클랜에 속한다"를 전제로 `clanId → LeagueClan`을 찾으므로 결과는 이랬다.

| 화면 | 증상 |
|---|---|
| 개인 상세 | **11/11 HTTP 404** |
| 개인 기록실 | 빈 배열 (실제로는 7~10경기) |
| 클랜 상세 소속 선수 | **0명** (5승 0패인 클랜에 인원 0) |
| 개인 랭킹 클랜 칸 | 전원 공란 |
| 무기별 기록 패널 | **한 번도 렌더되지 않음** |

정답은 이미 DB에 있었다 — `LeagueRosterMembership` 23행이 전원의 소속을 들고 있었다.
**데이터 문제가 아니라 한 컬럼 전달 누락**이었다.

고친 것

1. `rate.ts` — 현재 유효한 로스터 등록(`leftAt = null`)에서 `LeaguePlayer.clanId`를 채운다.
   로스터에 없으면 **건드리지 않는다**(있던 소속을 null로 지우지 않기 위해서)
2. `rosterSync.ts` — 병영수첩 클랜 멤버 목록은 그 클랜의 공식 명단이므로
   `Player.clanId`(전역 표시용 현재 소속)도 함께 채운다
3. 화면 — 개인 기록실이 **로딩과 "없음"을 구분**하지 않아, 404가 나면 영원히 스켈레톤이 돌았다.
   `isPending`과 `!data`를 나눴다

경기 시점 소속은 `Match`/`MatchPlayerStat`의 division 스냅샷이 따로 들고 있다.
여기서 채우는 `clanId`는 **표시용 현재 소속**이며 래더 계산에 쓰이지 않는다.

mock 픽스처는 전부 `official: true`라 `pnpm compare`로는 **절대 잡히지 않는** 종류의 버그였다.

### D-119. 공용 개발 비밀번호를 **폐기한다** — 새로 정하지 않고 무효화한다

시드가 만든 계정 **42개 전원이 같은 비밀번호 하나**를 썼고 그중 둘이 운영자(role 2)였다.
그 값은 저장소에 평문으로 있었고 시드 실행 때마다 콘솔에도 찍혔다. 로그인에는 시도 제한이 없다.
사이트가 잠깐이라도 외부에 열리면 **누구나 관리자 권한**(시즌 종료·시작 · 경기 공식 전환 ·
클랜 조작)에 도달할 수 있었고, 감사로그에는 정당한 운영자로 기록된다.

#### 새 비밀번호를 "정하지" 않는다

무작위 32바이트를 해시해서 덮고 **원문을 버린다.** 우리도 모르는 값이라 유출될 것이 없다.
"새 공용 비밀번호"를 만들면 같은 문제가 이름만 바꿔 돌아온다.

#### 판별은 소속이 아니라 **실제 값으로** 한다

`origin`이나 id 규칙으로 고르지 않는다. `bcrypt.compare`로 **그 비밀번호가 실제로 맞는
계정만** 무효화한다. 시드 밖에서 같은 값이 쓰였어도 함께 잡히고, 정상 계정은 절대 건드리지 않는다.
멱등하므로 두 번 돌려도 두 번째는 0건이다.

#### 재시드로 되살아나지 않게 한다

`seed.ts`의 기본값을 **무작위(로그인 불가)** 로 바꿨다. 로컬에서 로그인이 필요하면
`SACLOUD_SEED_PASSWORD`를 직접 넣어 실행한다. 콘솔에는 상태만 찍고 원문은 찍지 않는다.

#### 검수 계정은 운영 관리자와 분리한다

`pnpm nexon:accounts --provision-test --email <주소>` — **기본 최소 권한(role 0)** 이고,
비밀번호는 `SACLOUD_TEST_ACCOUNT_PASSWORD` **환경변수로만** 받는다.
인자로 받지 않는다(셸 히스토리에 남는다). 관리자 화면 검수가 필요할 때만 `--admin`을 붙인다.

테스트도 같은 규칙을 따른다 — `adminApi.test.ts`는 자격증명을 env로 받고,
없으면 **조용히 통과시키지 않고 skip**한다.

#### 상시 점검

`pnpm nexon:accounts --audit` 가 공용 비밀번호로 로그인 가능한 계정을 센다.
0이 아니면 **exit 1**이라 자동화에서 바로 걸린다.

> 남은 것: 로그인·가입에 rate limit이 없다. `PUT /api/me/link`는 소유권을 증명하지 않는다.
> 둘 다 외부 공개 전에 처리해야 한다.

### D-120. 인증 경로에 시도 제한을 건다 — **IP 헤더를 함부로 믿지 않는다**

로그인·가입·비밀번호찾기에 서버측 제한이 하나도 없었다. 게시판 글쓰기에만 있었다.
공용 비밀번호(D-119)와 겹쳐 있었을 때는 그 자체로 사고였다.

#### 정상 사용자를 막지 않는 설계

로그인은 **실패만** 센다. 비밀번호를 제대로 넣는 사람은 몇 번이든 로그인할 수 있고,
**성공하면 그 계정의 실패 기록을 즉시 지운다.** 누적 때문에 잠기는 일이 없다.

| 축 | 한도 | 막는 공격 |
|---|---|---|
| 계정(이메일)별 | 15분 5회 | 한 계정을 여러 IP에서 두드리기 |
| IP별 | 15분 20회 | 한 IP에서 계정 갈아 가며 훑기 |
| 가입 IP별 | 1시간 3회 | 대량 계정 생성 |

한도를 넘으면 **비밀번호를 검사하기 전에** 끊는다. 검사까지 가면 bcrypt 비용이
그대로 공격자의 무기가 된다. 응답은 `429` + `Retry-After`(초)다.

#### `X-Forwarded-For`를 믿지 않는 이유

그 헤더는 **클라이언트가 마음대로 넣을 수 있다.** 프록시가 덮어쓴다는 보장이 없으면
공격자가 요청마다 다른 값을 넣어 IP 제한을 통째로 무력화한다.
지금 구조(`next start` + 터널)에서는 소켓 주소가 항상 `127.0.0.1`이라 그것도 못 쓴다.

그래서 **명시적으로 설정할 때만** 헤더를 믿는다.

```
SACLOUD_CLIENT_IP_HEADER=cf-connecting-ip   # 프록시가 덮어쓰는 헤더
SACLOUD_TRUST_FORWARDED_FOR=true            # 차선책. 위 헤더가 없을 때만
```

아무것도 설정하지 않으면 **IP를 모르는 것으로 취급**하고, 훨씬 느슨한 전체 한도
(로그인 15분 300회)를 회로차단기로만 쓴다. 정상 사용자를 막지 않기 위해서다.
**제대로 된 IP 제한을 원하면 헤더를 설정해야 한다.**

#### 저장소

DB의 `RateLimit` 테이블을 쓴다. 메모리 맵이 아니라서 **인스턴스를 늘려도 그대로 동작한다.**
부하가 커지면 Redis 같은 전용 저장소가 낫지만, 공개 Beta 규모에서 행 하나 갱신은 병목이 아니다.

#### 흘리지 않는 것

키에 이메일·IP를 **원문으로 넣지 않는다**(해시만). 429 응답은 남은 시간만 알려 주고
"몇 번 틀렸는지"나 "그 이메일이 있는지"는 말하지 않는다. 로그인 실패 메시지도 예전처럼
아이디 없음과 비밀번호 틀림을 구분하지 않는다.

### D-121. 계정 연동은 **운영자가 승인한다** — 없는 증명을 흉내 내지 않는다

`PUT /api/me/link`가 닉네임만 받으면 그 선수를 곧바로 계정에 붙였다.
닉네임은 공개 정보이므로 **먼저 입력한 사람이 임자**였고, 랭킹 상위 선수의 신원을
아무나 선점할 수 있었다. 코드 주석이 스스로 "운영에 노출하면 안 된다"고 적어 둔 채였다.

#### 자동 검증이 불가능하다는 결론

넥슨 Open API 엔드포인트는 `id` · `user/basic` · `user/rank` · `user/tier` ·
`user/recent-info` · `match` · `match-detail` 이 전부이고, **모두 닉네임으로 조회하는
공개 정보**다. OAuth도 사용자 동의 흐름도 없다.

"게임 안에서 무언가를 바꾸고 우리가 읽어 확인한다"는 방식도 성립하지 않는다.
닉네임 변경은 유료·파괴적이고 그 닉네임이 곧 우리가 매칭하는 키다. 클랜 이동은 남에게 영향을 준다.
"지금부터 한 판 해라" 같은 도전은 **기다렸다가 남의 활동을 자기 것이라 우기는 것**을 막지 못한다.

그래서 **확인할 수 없는 것을 확인한 척하지 않기로 했다.** 그럴듯한 절차를 만들어
"인증됨"이라고 표시하면 없는 보증을 있는 것처럼 파는 셈이다.

#### 지금 구조

```
사용자  PUT /api/me/link          → PlayerLinkClaim(pending) 생성. 연결되지 않는다
운영자  GET  /api/admin/link-claims
        PATCH /api/admin/link-claims/{id}  {action: approve|reject}  ← 연결은 여기서만
```

안전장치

1. 이미 다른 계정에 연결된 선수는 **신청조차 받지 않는다**
2. 한 사람에게 열린 신청은 하나뿐이다
3. 닉네임은 **정확히 일치**할 때만 찾는다. 동명이인이면 임의로 고르지 않고 사람에게 넘긴다
4. 시드 선수는 연동 후보가 아니다 (D-116)
5. 승인은 트랜잭션 안에서 하고, 최종 보증은 `UserPlayerLink.playerId` **유니크 제약**이다 —
   동시에 두 신청이 승인돼도 DB가 한쪽만 통과시키고, 그 실패를 삼키지 않고 사유로 돌려준다
6. 승인·거부는 전부 `AdminAuditLog`에 남는다

> 나중에 넥슨이 사용자 인증 수단을 제공하면 그때 자동 검증을 붙인다.
> 그전까지 이 경로는 **사람이 판단하는 큐**다.

### D-122. SACLOUD 서플라이 리그는 **제3보급창고 5vs5만** 인정한다

원본 3rd.supply 리그홈 실측값 (2026-08-23, 정상 브라우저):

```
48개의 클랜 참여중
리그맵     제3보급창고
대전인원   5 vs 5   6 vs 6
```

즉 원본에는 6vs6이 **정식으로 존재한다.** 그럼에도 SACLOUD는 5vs5만 기록한다
(사용자 확정 정책. 이 결정이 이전 해석보다 우선한다).

#### 6vs6은 "비공식"이 아니라 **대상 외**다

이 구분이 핵심이다.

| 상태 | 뜻 | 기록실 | 래더 |
|---|---|---|---|
| `eligible` → official | 리그 경기 | 10명 전원 | 반영 |
| `eligible` → unofficial | 리그 경기지만 본클랜원 부족 | 10명 전원 | 미반영 |
| **`out_of_scope`** | **리그 대상이 아님** (다른 맵 · 6vs6) | **넣지 않음** | 없음 |
| `incomplete` | 대상이지만 참가자를 덜 복원함 | 보류 | 없음 |

6vs6을 `unofficial`로 두면 기록실에 6인전이 남고 "왜 점수가 없나"라는 질문이 생긴다.
아예 리그 밖이다.

#### 맵 판정은 **정확 일치**다

`contains('보급')` 같은 느슨한 매칭을 쓰지 않는다. 실제 스테이징에
`3보급-개인전`(일반전)이 있어서 그런 필터는 전혀 다른 모드를 통과시킨다.

**넥슨이 이 맵을 어떤 문자열로 주는지는 아직 관측되지 않았다.**
수집된 클랜전 15,879건 중 제3보급창고는 **0건**이다
(관측된 클랜전 맵: 올드타운 · 데저트2 · 드래곤로드 · 크로스포트 · 시티캣 · 프로방스).
그래서 별칭을 **추측해서 넣지 않았다.** 실제 표기가 관측되면 근거와 함께 추가한다.

> 지금 Beta에 들어 있는 10경기는 **전부 대상 외 맵**이다.
> 사용자 지시에 따라 아직 제거하지 않았다 — 실제 제3보급창고 5vs5를 확보한 뒤 전환한다.

### D-123. 참가자는 **버리지 않는다** — 신원을 모른다고 기록을 지우지 않는다

Phase 12 감사에서 찾은 가장 큰 데이터 결함이다.

`match-detail`은 참가자 10명 전원을 K/D/A까지 정상적으로 준다. 그런데
`resolveParticipant`가 **이미 아는 닉네임**만 `resolvedPlayerId`로 붙였고,
`projectionRule`이 미해석 참가자가 하나라도 있으면 **경기 전체를 버렸다.**

실측: `NexonMatchParticipant` 668건 중 resolved **7건(1.0%)**.
그래서 원본에 10명이 있는 경기가 화면에 4명으로 나왔다.

#### 참가자 **존재**와 신원 **확정**은 다른 문제다

실제로 뛴 사람이면 기록은 남긴다. 다만 그 사람이 **누구인지**는 근거가 있을 때만 말한다.

우선순위
1. 확정된 신원 (`NexonIdentity` → `playerId`)
2. 병영수첩 계정 번호 (`user_nexon_sn`) — 닉변에도 안 흔들리는 강한 키
3. **관측 전용 Player** (`OBS-<닉네임 해시>`)

3번은 "같은 사람"이라는 주장이 **아니다.** "같은 닉네임으로 관측됐다"는 주장이다.
기존 Player와 **합치지 않고**, `NexonIdentity`·`UserPlayerLink`도 만들지 않는다
(D-036 · D-100). 동명이인·닉변은 이 구조로 해결되지 않으며, 해결됐다고 표시하지도 않는다.
강한 근거가 생기면 그때 운영자가 병합한다.

#### 결과

```
before  668건 중 resolved 7건 (1.0%)   · 미해석 661건
after   668건 전원 신원 부여           · 미해석 0건
        resolved 140 · observed 528
```

대상 경기 `260821194726124001` 검증: 참가자 10명 전원 복원, K/D/A 보존,
아는 사람 3명은 `resolved`, 모르는 7명은 `observed`.

#### `nexon:reresolve`

`--reproject`는 `pending`/`skipped`만 보기 때문에 **이미 투영된 경기의 참가자는
영원히 재해석되지 않았다.** 그 구멍을 메우는 전용 명령을 추가했다.
투영 상태와 운영 `Match`를 건드리지 않아, 공개된 경기를 지우지 않고 신원만 채운다.

### D-124. 공식 참가 클랜은 **확인된 수만** 쓴다 — 48이라고 표시하지 않는다

원본 리그홈은 `48개의 클랜 참여중`이라고 표시한다.
공개 경로에서 실제로 확인한 것은 **44개**다.

| 경로 | 얻은 것 |
|---|---|
| `/league/supply/rank/clan/1` | 1부 상위 20 |
| `/league/supply/rank/clan/2` | 2부 상위 20 |
| `/league/supply/home/info` | 참여 클랜 20 (랭킹 밖 4개 추가 확보) |

합집합 **44개**. 나머지 4개는 커서 페이지네이션 뒤에 있고 그 API는 직접 접근이 **403**이다.
페이지에 더보기·무한스크롤도 없다. **차단을 우회하지 않았고, 4개를 만들어 채우지도 않았다.**

화면에는 `44개의 클랜 참여중`이라고 쓴다. 모르는 것을 아는 척하지 않는다.

#### 경기에서 본 클랜은 참가 클랜이 아니다

클랜 상세의 상대전적에서 클랜 22개를 더 찾았다. 넣지 않았다.
`guild_name`에 등장 · 상대전적에 존재 · 이름 유사 — 어느 것도 **공식 참가 근거가 아니다**.

#### 원본 rating을 가져오지 않는다

스냅샷에는 원본의 rating·승패가 들어 있지만 옮기지 않았다.
SACLOUD Beta는 전원 같은 출발점에서 시작한다(D-101). 원본 점수를 옮기면
베타가 원본의 연장이 되어 버린다. 가져오는 것은 **정체성**(id·이름·slug·부리그·마크)뿐이다.

#### slug 정규화와 링크 보존

dev 발판이 만든 `real-` 접두사를 실제 slug로 바꿨다
(`real-ulsan-cian` → `ulsanulsan`). 옛 slug는 `ClanAlias`로 남겨 기존 링크가 죽지 않는다.

#### 지울 수 없는 것은 **비활성**으로 뺀다

공식 목록 근거가 없는 dev 잔존 클랜 4개(전설 · Xenics-Storm · 해적 · 악마)는
경기가 걸려 있어 삭제하면 그 경기까지 cascade로 지워진다.
그래서 `Clan.active = false`로 두었다 — 스키마 주석이 말하는 "삭제 대신 쓰는 값"이다.

그런데 **공개 조회 계층이 `active`를 보지 않고 있었다.** 반영하지 않으면
확인된 44개에 잔존 4개가 섞여 화면에 48처럼 보인다. 목록·랭킹·집계에 조건을 넣었다.

### D-125. 제3보급창고 경기는 **넥슨 수집 경로에서 아직 한 건도 나오지 않았다**

로스터/관측 seed를 실제 서플라이 공식 클랜 선수로 확대한 뒤에도 결과는 같았다.

#### 확대한 것

| 단계 | 결과 |
|---|---|

그리고 더 중요한 사실 — **순수 `클랜전` 유형이 24,772건 중 0건이다.**
관측된 클랜 계열은 `퀵매치 클랜전`(7,304)과 `클랜 랭크전`(243)뿐이다.

#### 가장 그럴듯한 설명 (아직 확정 아님)

`퀵매치 클랜전`은 **6종 맵 로테이션의 픽업 매치**로 보인다 —
실제로 한 경기에 7개 클랜이 섞여 있는 것을 확인했다(D-123).
반면 서플라이 공식리그는 **약속 대전(`클랜전`)을 제3보급창고에서** 하는 것으로 보이며,
그 모드가 넥슨 Open API 매치 목록에 아직 한 번도 등장하지 않았다.

**확정하지 않는다.** 상세를 받은 것은 클랜 계열 10,086건 중 86건(0.85%)뿐이다.
가능성은 셋이고 아직 어느 것도 배제되지 않았다.
1. `클랜전` 모드가 Open API 매치 목록에 노출되지 않는다
2. 노출되지만 우리가 seed로 잡은 선수들이 그 기간에 하지 않았다
3. 맵 이름이 우리가 아는 표기와 다르다 (그래서 별칭을 추측해 넣지 않았다 — D-122)

#### 그래서 하지 않은 것

**기존 Beta 10경기를 지우지 않았고 replay도 하지 않았다.**
전환 조건("실제 제3보급창고 5vs5 최소 1건")이 충족되지 않았기 때문이다.
조건이 충족되지 않았는데 전환하면 공개 Beta가 빈 화면이 된다.

#### 병영수첩 로스터는 막혀 있다

서버측 호출은 **403**, 브라우저에서도 클랜 멤버 목록(`GetClanUserList`)은
`rtnCode -999`로 막힌다(로그인 게이트로 보인다). 인증·우회를 하지 않았다.
대신 **3rd.supply 클랜 선수 목록**이라는 정상 공개 경로로 우회 없이 닉네임을 얻었다.

### D-126. 공식리그 경기는 Open API에 **정상적으로 존재한다** — 놓친 원인은 seed 범위였다

D-125에서 "제3보급창고 0건"을 확인하고 표본을 늘리는 대신, **정답 샘플 1건**을 먼저 확보했다.
결과적으로 그게 옳았다 — 표본을 늘렸어도 원인을 못 찾았을 것이다.

#### 기준 경기 확보 (정상 공개 브라우저)

3rd.supply 클랜 상세(`/league/supply/clan/ulsanulsan`)의 최근매치에서 실제 경기를 찾았다.
화면에 `제3보급창고 · 5 vs 5 · 선레드 · 래더 -8점 · UlsaN_CIaN vs Iatency-`가 그대로 있고,
렌더된 HTML에 **Nexon 형식 18자리 match_id**가 들어 있다.

#### Open API 직접 대조 — 5건 전부 존재

```
260818140312124001  type="퀵매치 클랜전"  mode="폭파미션"  map="제3보급창고"  참가자 8명
260724214851125001  type="퀵매치 클랜전"  mode="폭파미션"  map="제3보급창고"  참가자 10명 ← 5v5 완전
260724213834125001  type="퀵매치 클랜전"  mode="폭파미션"  map="제3보급창고"  참가자 5명
260603164839124001  type="퀵매치 클랜전"  mode="폭파미션"  map="제3보급창고"  참가자 7명
260508214956124001  type="퀵매치 클랜전"  mode="폭파미션"  map="제3보급창고"  참가자 6명
```

확정된 것

| 항목 | 실측값 |
|---|---|
| `match_type` | **`퀵매치 클랜전`** — 우리가 **이미 수집하는 타입**이다 |
| `match_mode` | `폭파미션` — 이미 수집한다 |
| `match_map` | **`제3보급창고`** — D-122의 canonical과 **정확히 일치**. 별칭이 필요 없다 |
| 참가자 | 8 · 10 · 5 · 7 · 6 — **5건 중 1건만 10명** (D-044 재확인) |

#### 그래서 원인은 무엇이었나 — **Case 1: seed 범위**

필터가 아니었다. 타입·모드·맵 전부 우리가 이미 다루는 값이다.

증명: 그 경기 참가자 4명(`hutgaesoo` `원포인트레몬` `MacBookAir` `래띠`)의 신원을 붙이고
목록을 수집하자 **즉시 3건이 잡혔다**(나머지 2건은 그 계정들의 목록 창 밖이다).

우리가 못 본 이유는 단순하다 — **그 경기를 뛴 사람이 우리 seed에 없었다.**
기존 26개 신원은 공식리그 선수와 거의 겹치지 않았다.

#### 또 하나 — 목록에는 맵이 없다

`/match` 목록 응답에는 `match_map`이 **없다.** 맵은 `/match-detail`에만 있다.
그래서 스테이징 클랜전 10,086건 중 7,470건의 `matchMap`이 `null`이었고,
"맵 분포에 제3보급창고가 없다"는 관측은 **상세를 받은 86건만의 이야기**였다.
맵으로 거르려면 상세를 받아야 한다 — 이건 수집 설계에 그대로 반영해야 한다.

#### 다음 수집 계획 (근거가 생겼으므로 확정 가능)

1. seed를 **44개 공식클랜의 실제 선수**로 채운다 (3rd.supply 클랜 선수 목록 = 공개 SSR)
2. `퀵매치 클랜전` 목록을 모은다 (타입 변경 불필요)
3. 그 목록의 **상세를 받아야** 맵을 알 수 있다 — 맵 선필터는 불가능하다
4. `map === '제3보급창고' && 5vs5 && 참가자 10명`만 리그에 투영한다 (D-122)
5. 참가자 10명은 여러 관측을 합쳐 채운다 (D-044 · D-123)

### D-127. 공식리그 경기 발견은 **선수 목록 무차별 수집으로 안 된다**

파일럿에서 확정한 것이다. 파이프라인은 정상 동작하지만 **발견 경로가 틀렸다.**

#### 호출량은 1/4로 줄일 수 있다 (적용함)

기준 경기의 `match_type`이 `퀵매치 클랜전`, `match_mode`가 `폭파미션`으로 확정됐고,
Open API `/match`는 `match_type` 필터를 지원한다. 스테이징 실측도 같은 방향이다 —
`퀵매치 클랜전` 12,152건 중 12,134건이 `폭파미션`이다.

그래서 공식리그 discovery는 **선수당 1회**(`폭파미션` + `퀵매치 클랜전`)면 된다.
4모드 전수 조회는 필요 없다. 실행으로 확인했다 — 신원 36명에 `listCalls=36`.

#### 그런데 상세를 116건 받아도 제3보급창고는 0건이었다

```
올드타운 25 · 데저트2 20 · 드래곤로드 20 · 크로스포트 19 · 프로방스 16 · 시티캣 15
제3보급창고 0
```

이유는 분명하다. 선수의 매치 목록은 **최신순 수천 건**이고 그 대부분이
6종 로테이션 맵의 픽업 매치다. 제3보급창고 공식 경기는 그 안에 드물게 섞여 있다.
최신 N건만 상세를 받으면 **영원히 안 걸린다.**
10,086건을 전부 받으면 언젠가 걸리지만 그건 호출 낭비다.

#### 올바른 발견 경로 — 3rd.supply가 match_id를 준다

3rd.supply 클랜 상세의 최근매치에는 **공식 경기의 18자리 match_id가 그대로 있다**(D-126).
그 id로 `/match-detail`을 직접 부르면 정확히 그 경기가 온다.

```
3rd.supply 클랜 최근매치  →  공식 경기 match_id
                          →  Nexon /match-detail  (1건당 1회)
                          →  맵·참가자·K/D/A
```

실행으로 확인했다. 목록 무차별 수집 대신 **id 3건을 지정해 상세 3회**를 부르자
제3보급창고 3건이 곧바로 스테이징에 들어왔다.

즉 **discovery는 3rd.supply, enrichment는 Nexon**이다.
넥슨 Open API만으로 공식리그를 자동 발견하려던 설계는 비용이 맞지 않는다.

#### 판정 결과 — 파이프라인은 정상이다

```
260724214851125001  5v5  신원 10/10  → eligible      ← qualifying
260818140312124001  5v3  신원  8/8   → incomplete
260724213834125001  5    신원  5/5   → incomplete
```

`eligible` 1건이 실제로 나왔다. 맵 판정·인원 판정·신원 부여(D-123)가 전부 동작한다.

Beta 시작은 2026-08-19이고 확보된 경기는 8/18 · 7/24 · 7/24다.
**Beta 전환에 쓸 수 있는 경기가 아직 0건이다.**

`260724214851125001`의 10명은 8개 클랜에 흩어져 있다

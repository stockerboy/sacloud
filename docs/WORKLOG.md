## Phase 7 — DB + 실제 API (2026-08-21)

### 한 일

**기반**
- `packages/db` 신설. Prisma 스키마를 계약(Zod)을 채울 수 있는 형태로 설계하고,
  `CLAUDE.md` 3-A(마이그레이션 절대 규칙)를 **스키마 수준에서 강제**했다.
  `RawImport`(원본 응답 보존) · `SourceMapping`(원본 ID 보존) · `ImportJob`/`ImportFailure`
  (중단 후 재개, 실패 기록) · `MigrationCheck`(숫자 대조) · 경기 시점 division 스냅샷 ·
  래더 재현 정보 · 무기별 분리 · 시즌 스냅샷 · `RatingConfig`.
- 로컬 PostgreSQL을 `embedded-postgres`로 띄웠다 (Docker·PostgreSQL 미설치 환경).
  한국어 Windows에서 `initdb`가 두 번 막혔고 둘 다 원인을 찾아 우회했다 (D-022).
- Mock과 **같은 결정적 픽스처**를 DB에 적재하는 시드 + 자가 점검(`pnpm db:check`).

**API**
- 계약 엔드포인트 전량을 Prisma 기반 Route Handler로 구현 (57개 라우트).
- 쓰기가 **실제로 저장된다**: 글·댓글·추천·설정 변경. 서버 측 새니타이즈 · rate limit ·
  권한 검사 · 비로그인 글 비밀번호 해시.
- 인증은 `jose`(JWT) + `bcryptjs`로 직접 구현. httpOnly 쿠키 + 리프레시 토큰 rotation.
  계획 문서의 Auth.js와 다른 선택이라 사유를 남겼다 (D-025) — **사용자 확인 필요**.

그래서 스키마·계약·UI를 전부 nullable로 넓혔고, `false`도 쓰지 않기로 했다 (D-034).

## Phase 8 — 실응답 소량 검증 (2026-08-21)

닉네임 1명, **총 15회 호출**. 429·403 없음. 테스트 키(`test_`)로 서든어택 API가 정상 동작한다.

### 스펙이 틀렸던 곳

1. 참가자 클랜명은 `clan_name`이 아니라 **`guild_name`** (D-043). 스키마·정규화를 실제 기준으로 고쳤다.
2. **한 경기 응답에 양 팀이 함께 오지 않는다** (D-044). 5경기 전부 그랬다.
   승리 팀 전원 + (졌으면) 본인. 상대 팀 라인업이 없으니 클랜 vs 클랜 경기를 재구성할 수 없다.
   투영 규칙이 틀린 게 아니라 **입력이 부족한 것**이다. Phase 9의 선결 과제로 올렸다.

### 확인된 형식

`ouid` 32자리 hex · `match_id` **18자리 숫자**(3rd.supply와 같은 형식) · `date_match` 밀리초 포함 UTC ·

## Phase 9 준비 — 래더 공식 조사 (2026-08-22)

**공식을 확정하지 않았다.** production에 아무것도 적용하지 않았다.
운영 DB의 점수 필드에 쓰지 않았고, 스키마도 바꾸지 않았다.

### 왜 합성 데이터를 썼나

실제 경기로 시뮬레이션하려 했지만 쓸 수 있는 데이터가 없었다.
재구성된 넥슨 경기는 **0건**(로스터가 비어 있다), mock 시드 3,000경기는 래더 값까지 가짜다.
그래서 숨은 실력값을 가진 합성 모집단을 만들고 "래더가 그 실력을 얼마나 맞히는가"로 비교했다.
난수는 seed 고정이라 결과가 재현된다.

### 가장 큰 수확 — 역추적된 파라미터가 옳다는 증거

스펙 §1·§2 구조를 그대로 계산하면 §8의 관측 앵커가 **네 개 모두 재현됐다.**
특히 "div1 승리에 +11·+19가 나오지 않는다"는 관측이 **2단계 반올림에서 자동으로 따라 나온다.**

```
round(9 × 1.15) = 10 · round(10 × 1.15) = 12   → 11이 건너뛰어진다
round(16 × 1.15) = 18 · round(17 × 1.15) = 20  → 19가 건너뛰어진다
```

우연히 맞을 수 있는 종류의 일치가 아니다.

### 미확인 항목이 하나 줄었다

스펙 §3 "0.6을 K에 곱하는지, 최종 증감에 곱하는지, 양쪽 모두인지" 중
**양쪽 모두(P-C)는 탈락했다** — 관측 -7 대신 -4가 나온다.

남은 둘(P-A·P-B)은 **패배 앵커가 전부 같아** 관측으로 구분되지 않는다.
교차 division **승리**에서만 15%가 1점씩 다르다. 실표본 20건이면 갈린다.

### 발견한 구멍 (전부 원본 공식의 성질이다)

1. **양학이 막히지 않는다.** D=3400이라 800점 차에서도 기대승률이 0.63이다.
   1,000점 상대만 300경기 이기면 1800 → 3555. 마지막까지 +3/경기가 붙는다
2. **승률 왜곡이 통한다.** 약체만 골라 86% 승률(2874)이 강자와 55%(2679)보다 높다
3. **div1은 제로섬이 아니다.** 동급 경기당 +5가 주입된다(승 +17 / 패 -12).
   승률 50%로 200경기만 해도 +158점. div2는 정확히 제로섬이다

정상 동작도 확인했다 — 업셋 보상 방향, 이겨서 잃는 구간 없음, 반복 대전 발산 없음,
신규 유저 78경기 안착, 배치고사 0점.

### 클랜 래더는 결합 방식부터 미확인이다

후보 셋을 비교했다. **C-2(개인 증감 평균)는 라인업 조작에 직접 노출된다** —
같은 상대를 약한 5명으로 이기면 +19, 강한 5명으로 이기면 +12다.
C-1(team-elo)을 권장하되, 세 후보 모두 관측된 클랜 래더 폭(987~1,840)보다 넓게 나온다.
→ **클랜은 개인과 다른 상수를 쓴다고 보는 것이 맞다.** 값은 추정하지 않았다.

## Phase 9 — 래더 엔진 구현 (2026-08-22)

사용자가 정책을 확정했다(`DECISIONS.md` D-057 ~ D-068). 그 기준으로 실제 구현했다.

### 정책이 바꾼 것 두 가지가 컸다

**1) 경기 인정 기준 — 전원 복원 → 양측 3명 이상**

Phase 8.2는 "양 팀 전원을 복원했을 때만 인정"이었다. 넥슨이 참가자 전원을 주지 않는 이상
(D-044) 그 기준으로는 대부분의 경기가 영원히 인정되지 않는다.
`A 4명 · B 3명 → 인정`, `A 5명 · B 2명 → 인정 안 함`으로 바뀌었다.

대신 **확인 수준을 숨기지 않는다.** `5v4` 같은 문자열과 근거별 인원 수를 스테이징·운영
매치·화면까지 그대로 들고 간다. 경기를 인정하는 것과 그 경기의 전력을 계산하는 것을 분리했다.

**2) division을 공식에서 뺐다**

원본은 1부에 `K=24 · 배수 1.15`, 2부에 `K=30 · 배수 1.00`, 교차 시 1부만 `×0.6`이었다.
그대로 두면 **1부는 동급 경기마다 +5씩 점수가 주입된다**(승 +17 / 패 -12).
승률 50%로 200경기만 해도 +158점이 오른다 — 순위가 실력이 아니라 경기 수로 정해진다.

세 군데를 바꿔 제로섬으로 만들었다.
승리 배수 1.0 · 패배도 같은 `K(R)` 사용 · `D` 3400 → 800.
결과: 동급 경기 증감 합 **정확히 0**, 리그 100명 5,000경기 평균 이동 **+1.4점**.

### `D = 3400`이 진짜 문제였다

원본 값으로는 800점 낮은 상대를 잡아도 기대승률이 0.63에 그친다. 그래서 약체만 300경기
잡으면 1800 → 3555까지 올라갔다(Phase 9 준비 조사). `D=800`으로 바꾸고 점수차 보상 감쇠를
넣자 같은 시나리오가 **1500 → 1496**이 됐다. 양학으로는 오르지 않는다.

상수는 임의로 정하지 않았다. 후보 12세트 × 기준 11개로 채점하고, 기준으로 갈리지 않는
상수는 파라미터별 변별 지표(클랜 폭 · 양학 마진 · 억제율 · 전력 상관)로 골랐다.
근거는 전부 `docs/LADDER_TUNING_REPORT.md`에 숫자로 남겼다.

| | |
|---|---|
| `packages/rating/` | 래더 엔진. **순수 함수만.** 시뮬레이션과 운영이 같은 코드를 쓴다 |
| `jobs/rate.ts` | 도메인 반영. 매번 **처음부터 다시 계산**한다(결정적 replay) |

### 증분 반영을 하지 않은 이유

"이번에 들어온 경기만 더한다"로 짜면 경기가 도착한 순서에 따라 결과가 달라진다.
넥슨 수집은 순서를 보장하지 않는다 — 어제 경기가 오늘 경기보다 늦게 들어온다.
그래서 `nexon:rate`는 리그 전체를 `startAt` 순으로 **다시 계산**한다. 느리지만 결과가 하나다.

### 무기별 분리는 하지 않았다

넥슨이 무기를 주지 않는다(D-034). 그래서 증감을 전량 `baseRating`에 누적하고 무기 delta는
0으로 둔다. `통합 = base + sniper + rifle` 불변식이 깨지지 않는다.

## Phase 9 최종 audit (2026-08-22)

사용자 검수에서 나온 모순·버그를 잡고, 그 과정에서 정책이 여러 건 바뀌었다.

### 공식전 빈페이지 버그 — 원인은 **ID 한 글자 차이**

`/player/500013135`에서 공식전 카드를 누르면 빈 화면이 나왔다.

```
카드가 만든 경로  /league/officialmain/player/6115        ← league_player_id
API가 받는 경로   /leagues/:leagueSlug/players/:playerId  ← playerId
```

`league_player_id`(리그 참가 레코드 ID)와 `playerId`가 **둘 다 숫자 문자열**이라
타입으로는 걸리지 않았다. API는 404를 돌려주고 화면은 조용히 비었다.

경로 조립을 `packages/ui/src/common/paths.ts` 한 곳으로 모으고, 인자 이름으로 무엇을 넣어야
하는지 못박았다. 회귀 테스트 2종을 붙였다 — 순수 경로 테스트 6건 + 실서버 계약 테스트 1건
(카드가 가리키는 경로가 실제로 200인지, 그리고 `league_player_id`로는 404인지).

브라우저에서 실제 클릭으로 재현 → 수정 → 재검증했다. 세컨드 카드도 같이 확인했다.

### "cap이 업셋까지 죽인다"는 지적은 사실이 아니었다 — 하지만 다른 문제가 있었다

감쇠는 처음부터 `본인 − 상대`라는 **부호 있는 값**으로 걸려서 업셋은 감쇠되지 않았다
(`1200이 2600을 이김 → +30`, `2600이 1200을 이김 → +0`). 그 자체는 정상이다.

진짜 문제는 다른 곳이었다. **승리만 깎고 패배는 그대로 두면 기댓값이 뒤집힌다.**
격차 600에서 기대대로 이겨도 1경기 기댓값이 `-2.08`이었다 — 정직하게 이겨도 점수가 준다.
감쇠 시작을 300 → 600으로 물려 그 구간을 없앴다.

### "300승 후 1496"은 300승이 아니었다

보고서가 그 시나리오를 "300경기 승"으로 적었는데, 실제로는 **90% 승률 300경기**(270승 30패)였다.
표기가 틀렸다. 실제 300**연승**은 `1500 → 1938`이고 최소 승리 증감은 `+1`이다.

그래도 지적 덕분에 실제 문제(위의 기댓값 역전)를 찾았고, cap 조정 후 같은 90% 시나리오가
`1484 → 1638`이 됐다. **승리 증감이 음수가 될 수 없다는 것**을 코드로 못박고 전 구간 테스트로 고정했다.

### 반복 대전 감쇠는 껐다 — 켜도 결과가 같았다

멸망전은 SACLOUD의 정상 문화다. 그런데 측정해 보니 감쇠를 켜도 **한 점도 달라지지 않았다.**

```
900 낮은 상대 20연승      켬 1820 · 끔 1820
비슷한 상대 멸망전 20연승   켬 1817 · 끔 1817  (새 상대 20연승과도 동일)
```

격차 보상 감쇠가 이미 farming을 막고 있어서 반복 감쇠가 손댈 여지가 없었다.
기능은 남기되(격차 600 초과에서만 동작) 기본값을 껐다.

### 정책 변경 — 용병과 시즌

작업 도중 사용자가 두 가지를 바꿨다.

**1) 공식전 인정은 본클랜원 3+3, 용병은 못 채운다.** 대신 인정된 뒤에는 **출전이 확인된
전원이 개인 기록과 개인 래더를 받는다.** 용병도 받는다. 용병의 **원소속 클랜 래더는 불변**이다.

여기서 필요해진 것이 "원소속"과 "이 경기에서 뛴 팀"의 분리다. 팀 배정은 추측하지 않는다 —
본클랜원 다수 결과로 두 팀의 승패를 정하고, 나머지는 자기 승패와 같은 팀으로 배정한다.
승자가 하나뿐이므로 **승패가 곧 팀을 가리킨다.**

부수 효과로 "등록은 A인데 B 결과로 관측된 1명" 때문에 경기를 통째로 버리던 문제도 사라졌다.
이제 그 사람은 B팀 용병으로 기록된다.

**2) 시즌 soft reset 폐기.** 새 시즌에는 개인·클랜 **전원이 1500에서** 시작한다.
`seasonCarryRate`를 설정에서 제거했다. 지난 시즌 기록(경기·시즌 통계·랭킹)은 그대로 둔다.
시즌 전환은 **운영자가 부를 때만** 일어나고, 경기의 시즌 귀속은 **실제 경기 시각**으로 정한다.

### 검증

- typecheck / lint / build(37페이지) 통과
- test **432 passed / 1 skipped** (경로 6 + 용병/시즌 케이스 포함)
- 오프라인 스모크 **108항목** (용병 기록·원소속 불변·새 시즌 baseline 포함)
- `pnpm nexon:check` 15항목 · `pnpm db:check` 23항목
- **`pnpm compare` 25/25 일치** — 게시판 like_count 드리프트는 재시드로 정상화했다

## Phase 9 정책 동기화 — 공식/비공식 경기 분리 (2026-08-22)

정책이 다시 바뀌었다. 이번 변경의 핵심은 **경기를 버리지 않는 것**이다.

### AND → OR

기존: 양 팀 **모두** 본클랜원 3명 이상이어야 인정.
현재: **한쪽이라도** 3명이면 공식 경기.

`클3+용2 vs 클0+용5`도 공식이다. 한 팀이 자기 클랜원을 제대로 냈으면 그 경기는 의미가 있다.

### 인정 못 해도 지우지 않는다

양쪽 다 3명 미만이면 **비공식 경기**으로 남긴다. 기록실에 참가자·K/D/A·맵·결과가 그대로 보이고,
`Match.official = false`로 표시돼 시즌 통계·래더·랭킹에서만 빠진다.

이 구분이 열산·열빡 문제도 상당 부분 처리한다 — 넥슨 API로 그 형식을 확실히 구분할 수 없으니
**추측으로 분류하지 않고**, 클랜원이 모이지 않은 경기가 자동으로 비공식 경기이 되게 뒀다.

### 클랜 래더만 반영률 차등

같은 공식 경기라도 팀마다 다르다. 본클랜원 3명↑ 100% · 2명 70% · 1명 40% · 0명 0%.
`+20 / -20`이 `+8 / -20`이 될 수 있다 — **한 경기의 합이 0이 아니다.**

그래서 시즌 시뮬레이션을 따로 돌렸다(`lab/clanWeightSim.ts`). 40클랜 4,000경기 기준
평균 이동 최대 **-4.0**, 하한(0점) 집중 **0건**, 실력 상관 **0.979 이상**.
인플레이션도 분포 붕괴도 나타나지 않아 **숨은 보정을 넣지 않았다.**

개인 래더에는 차등이 없다. 용병도 100% 받는다 — 개인 래더가 평가하는 것은
"그 사람이 실제로 누구를 상대로 어떤 결과를 냈는가"이기 때문이다.

### 팀 식별에 상세 클랜명을 쓰기 시작했다

`클0+용5`처럼 한 팀이 자기 클랜원을 한 명도 안 낸 경우, 로스터만으로는 그 팀이 어느 클랜인지
알 수 없다. 그래서 넥슨 상세의 `guild_name`이 리그 클랜명과 **정확히 일치**할 때 그것을
1차 근거로 쓴다. 비슷한 이름은 쓰지 않는다 — 자동 병합 금지(D-088)와 같은 이유다.

### 관리자 기능은 CLI로 냈다

`nexon:season`(상태·종료·시작·승강), `nexon:clan`(등록·이름변경·리그참여·병합).
시즌 종료 시 최종 랭킹을 `RankSnapshot`으로 굳힌 뒤에야 점수를 초기화한다.
**웹 관리자 화면은 만들지 않았다.** 남은 작업으로 남긴다.

### 검증

- typecheck / lint / build(37페이지) 통과
- test **435 passed / 10 skipped** (CASE 1~11 포함)
- 오프라인 스모크 **112항목** (공식/비공식 분기 · 용병 · 시즌 baseline)
- `nexon:check` 15항목 · `db:check` 23항목 · `compare` 25/25

## Phase 10 — 베타 운영 준비 (2026-08-22)

### 관리자 화면을 만들었다

지금까지 운영 기능은 CLI에만 있었다. 운영자가 터미널 없이 사이트에서 직접 운영할 수 있어야
베타를 열 수 있다. `/admin` 아래에 대시보드·클랜·시즌·경기 네 화면을 붙였다.

**로직을 복사하지 않았다.** 시즌·클랜·로스터 조작을 `packages/db/ops/`로 옮기고
CLI와 웹이 같은 함수를 부르게 했다. 두 경로가 갈라지면 "CLI로는 되는데 화면은 다른" 사고가 난다.

권한은 서버에서 판정한다. 비로그인 요청으로 시즌 종료·클랜 수정·로스터 변경을 시도하면
전부 403이라는 것을 테스트로 고정했다. 버튼을 감추는 것은 보안이 아니다.

### 파괴적 작업에는 미리보기를 뒀다

시즌 종료·시작은 `confirm` 없이는 실행되지 않는다. 무엇이 바뀌는지 — 스냅샷 몇 건,
어느 클랜이 승격·강등되는지, 몇 명이 초기화되는지 — 를 먼저 보여 준다.
실행은 트랜잭션이라 "시즌 7은 닫혔는데 8이 없는" 중간 상태가 생기지 않는다.

### 실데이터 E2E — 예상과 다른 결과가 나왔고, 그게 맞았다

이미 수집해 둔 실제 넥슨 응답으로 전 구간을 통과시켰다(**새 API 호출 없음**).

실제 `퀵매치 클랜전` 5건을 열어 보니 **참가자가 전부 다른 클랜 소속**이었다.
7명이 6개 클랜에 흩어진 경기도 있었다. 즉 실전 데이터에서 이 매치 타입은
**클랜전이라는 이름의 픽업 경기**인 경우가 많다.

그래서 E2E 결과는 `비공식 경기`이었다 — 어느 팀도 본클랜원 3명을 채우지 못했다.
개인·클랜 래더 모두 미반영, 기록실에는 그대로 표시, 배지와 팀별 반영률(2명 70% / 1명 40%)까지
화면에서 확인했다. **공식 인정 기준이 의도대로 걸러 냈다.**

이 결과가 없었다면 "5v5 클랜전이 당연히 들어온다"고 가정한 채 베타를 열었을 것이다.

### 검증 도구가 실운영 데이터에 깨졌다 — 그것도 수확이었다

실제 리그·클랜을 하나 만들자 `db:check`·`nexon:check`·`compare`·오프라인 스모크가 줄줄이 실패했다.
전부 **"DB에 mock 시드만 있다"** 는 낡은 전제 때문이었다.

| 도구 | 낡은 전제 | 고친 방식 |
|---|---|---|
| `db:check` | 전체 개수 = 픽스처 개수 | 픽스처가 만든 **행만** 센다 |
| `nexon:check` | 참가자 전원이 로스터 근거를 가진다 | **본클랜원만** 검사 (용병은 원래 아니다) |
| `nexon:check` | 양 팀 인원이 같다 | 검사 삭제 (확인 수준은 원래 다르다) |
| `nexon:check` | 인정 기준이 AND | **공식 경기만** OR 검사 + 비공식 경기 래더 미반영 검사 추가 |
| `compare` | 리그 목록 길이가 같다 | **픽스처 항목만** 골라 대조 |
| 스모크 | 전역 `origin=nexon` 개수 | 스모크 리그로 범위 제한 (D-045와 같은 실수, 네 번째) |

검사가 정상적인 운영 데이터에 반응해 실패하면 진짜 문제와 구분할 수 없다. 전부 고쳤다.

### 하지 않은 것

- **Season 8을 시작하지 않았다.** `supply` 리그는 Season 7 활성 그대로다
- 넥슨 API를 부르지 않았다 (실호출 누계 22회 그대로)
- 새 래더 공식을 만들지 않았다. Phase 9 정책 그대로다
- 열산/열빡을 추측으로 분류하지 않았다

### 검증

- typecheck / lint / build(46페이지 — 기존 37 + 관리자 9) 통과
- test **457 passed / 2 skipped** (관리자 API 13건 추가)

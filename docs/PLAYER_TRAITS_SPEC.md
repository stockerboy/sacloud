## 1. 데이터 출처 — 병영수첩 BattleLog

### 접근 방법 (중요)

Node/서버에서 병영수첩을 부르면 **403** 이다 (AWS WAF 봇차단). 실측 확인했다.
UA 를 위조해 뚫지 않는다 — `CLAUDE.md` 3-A 5번.

**대신 사용자의 로그인된 Chrome 을 자동화해서 받는다.** 브라우저 자동화 도구로
페이지 컨텍스트에서 `fetch` 를 호출하면 정상 동작한다 (2026-08-28 실측).
이건 우회가 아니라 **사용자 자신의 브라우저가 하는 정상 요청**이다.

### 엔드포인트 (실측)

```
POST /api/Match/GetMatchList/
  본문(첫 페이지)  {"user_nexon_sn":"<str_usn>","mode_flag":"ALL"}
  본문(다음 페이지) {"user_nexon_sn":"<str_usn>","mode_flag":"ALL",
                    "seq_no":"<직전 응답의 message>","min_seq_no":"0"}

  ⚠ `seq_no` 나 `min_seq_no` 에 **빈 문자열을 보내면 `rtnCode:-999 Exception`** 이다.
    생략하거나 `"0"` 을 보내야 한다. 이것 때문에 첫 수집이 통째로 실패했다.

  응답  { rtnCode:20, message:"<다음 커서>", result:[ {
           match_key, map_name, match_name, match_type, match_time_date,
           kill_cnt, death_cnt, assist_cnt, damage_cnt, head_cnt, save_cnt, ...
         } ] }

POST /api/BattleLog/GetBattleLog/<match_key>/<str_usn>
  응답  { battleLog:[ ... ] }
  ⚠ 이 응답에는 **`rtnCode` 가 없다.** 그걸 검사하면 전부 실패로 처리된다 (실제로 그랬다).
```

### BattleLog 이벤트 필드 (실측)

```
round            라운드 번호
event_time       "MM:SS" — **경기 전체 누적 시간**이다. 라운드 기준이 아니다
event_type       kill | death | bomb | g_death
weapon           riple | sniper | throw | assist | close | c4-install
kill_x, kill_y   죽인 사람이 서 있던 위치
death_x, death_y 죽은 사람이 서 있던 위치
str_usn          이 로그의 주인 (그 선수)
user_nick / user_nexon_sn            죽인 사람
target_str_usn / target_user_nick    죽은 사람
```

**한 로그에는 그 선수 본인이 얽힌 이벤트만 온다.** 팀원 전체 이벤트는 없다.
그래서 한 라운드에서 그 선수의 이벤트는 **중앙값 1개**(평균 1.5개)뿐이다 —
이동 경로를 복원할 수 없다. 뒤의 `[미확인]` 절 참조.

## 2. 구역 정의

사용자가 좌표 산점도 위에 형광펜으로 직접 칠해 주었고, 그 이미지에서 픽셀로 추출했다.
격자 10 단위 셀 집합으로 저장한다 (`zonemap.json`).

```
B        x 130~320 · y 300~500   (노랑)
2층      x 170~320 · y 310~440   (보라)
숏(A)    x 190~430 · y 230~360   (하늘)
스나싸움  x 140~410 · y 270~560   (빨강) — 뱃지 전용, 위 셋과 겹쳐도 된다
```

**겹칠 때 우선순위는 2층 > B > 숏.** 사용자가 2층·B 표시는 "완벽에 가깝다"고 했고
숏만 다시 칠했기 때문이다.

> ⚠ **2층은 A 의 위층이라 미니맵 x/y 가 겹친다.** 좌표만으로는 2층과 숏을 못 가른다.
> 실제로 2층 선수 5명 전원이 "숏이 최다 구역"으로 나왔다. 그래서 구역 비율이 아니라
> **분포 전체를 학습**하는 방식을 쓴다 (3절).

## 3. 포지션 자동 판정

원본은 선수가 **직접 등록**한다. 우리는 **배틀로그로 자동 판정**한다 — 다른 기능이다.
원본에서 가져온 `Player.position`(숫자 코드)과 **섞지 않는다.**

### 방법

선수별로 좌표를 20 단위 격자 히스토그램으로 만들고, 정답 표본의 중심과 코사인 유사도를
비교한다. 검증은 **한 명씩 빼고 학습해 그 사람을 맞히는 방식**(leave-one-out)으로 한다.

### 실측 정확도 (정답 20명 · 선수당 30경기)

| 조건 | 정확도 |
|---|---|
| 손으로 그린 3구역의 최다 구역으로 판정 | 45% |
| 격자 히스토그램 학습 (4분류) | 75% |
| **+ 스나 든 판 제외** | **80%** |
| **+ B와 리베 통합 (3분류)** | **85%** |

**스나 든 판은 뺀다.** 사용자 확인: 정답 20명 중 스나수는 없다.
한 경기에서 스나 킬이 하나라도 있으면 그 경기를 통째로 제외한다.
이것만으로 75% → 80% 가 됐다 (2층 선수 2명이 스나 판 7~9개 때문에 오판되고 있었다).

### B vs 리베 — 구분 가능하다

사용자가 준 단서와 그 검증 결과:

| 단서 | 검증 결과 |
|---|---|
| "리베는 B포지보다 **뒤에서** B를 지킨다" | ✅ B 구역 안 평균 x — B포지 169.6~180.4 / 리베 178.2~190.6. **거의 안 겹친다** |
| "블루때 A 백업을 가장 먼저 온다" | ✅ 숏 구역 교전 비율 — B포지 23.7% / 리베 46.3% |
| "이동량이 제일 많다" | ✅ 좌표 흩어짐 — 리베 91.6 / B 88.9 / 숏 82.5 / 2층 79.5 |

세 신호 모두 방향이 맞다. **다만 리베 정답이 3~4명뿐이라 경계값을 확정하지 않았다.**
표본을 100경기로 늘린 뒤 재검증한다.

## 4. 뱃지 (선수 특성)

대상은 **통합랭킹 1~50위**다.

| 뱃지 | 정의 | 계산 가능? |
|---|---|---|
| **압도적 킬데스** | 50명 중 스나 킬뎃 상위 3명, 라플 킬뎃 상위 3명 (각각 따로 · 승률 무관) | ✅ 우리 DB `MatchPlayerStat` 에 `weapon`·`kill`·`death` 130만 행 전부 있다 |
| **압도적 샷발** | 같은 팀 **라플 중** 딜량 1등을 유독 자주 한다 (라플 고유) | ✅ `damage`·`weapon` 전부 있다 |
| **압도적 스나싸움** | 스나싸움 구역에서 상대 스나를 잡은 횟수가 유독 많다 (스나 고유) | ⚠ 아래 참조 |
| **세이브머신** | 세이브(1대1~1대5, 혼자 남아 라운드를 따냄)가 유독 많다 (무기 무관) | ⚠ `save_cnt` 가 경기목록 응답에 있다. 우리 DB 에는 없어 수집이 필요하다 |
| **매치의사나이** | 매치라운드(플레이시간 20분 초과 경기의 **마지막 라운드**)에서 딜을 가장 많이 넣는다 | ❌ 아래 참조 |
| **어태커** | 라운드 초반에 유독 많이 죽는다 | ⚠ 아래 참조 |

### 확정된 정의 (2026-08-28 사용자 지시)

**압도적 스나싸움**

배틀로그만 보면 "죽은 상대가 스나였는지" 를 모른다고 판단했는데 **틀렸다.**
킬로그가 **누가 누구를 어디서 죽였는지**를 주고, 우리 DB 의 `MatchPlayerStat` 에
그 경기 **모든 참가자의 `weapon`** 이 130만 행 전부 들어 있다.
피해자 닉네임/식별자로 조회하면 그 경기에서 스나를 들었는지 알 수 있다.

```
스나싸움 구역(에이롱·비롱, 빨간 표시) 안에서
  승   내가 스나로 죽인 상대가 그 경기에서 스나를 든 선수였다
  패   그 구역에서 내가 스나에게 죽었다   (death + weapon=sniper 로 바로 안다)

  스코어 = 승 − 패.  이 값이 유독 높으면 뱃지.
```

**매치의사나이** (2026-08-28 최종)

```
플레이시간 20분 초과 경기의 **마지막 라운드에서 세이브를 한 사람.**
그 사람이 그 경기의 매치의 사나이. 이걸 자주 하는 선수에게 뱃지.
```

앞서 "세이브가 없으면 최다 킬" 이라는 안이 있었으나 사용자가 **세이브 하나로 단순화**했다.

**세이브 판정** — 1대1부터 세이브로 친다

경기목록 응답의 `save_cnt` 는 **넥슨 기준이라 1대3 이상만 센다.** 그걸 쓰면 안 된다.
1대1 세이브를 잡으려면 **그 경기 10명 전원의 배틀로그**로 라운드별 생존자를 복원해야 한다.
배틀로그는 선수 한 명 단위로만 오기 때문이다.

> ⚠ **비용 실측 (2026-08-28)**
> ```
> 상위 50명(래더 3,432~3,007)의 최근 300경기 = 중복 빼고 6,554경기
> 10명 전원 배틀로그 → 65,540 요청 → 0.32초 간격이면 약 5.8시간
> 그 경기 참가자 중 상위 50명은 26%뿐이라 74%는 새로 받아야 한다
> 최근 100경기로 줄이면 크게 준다
> ```

**어태커** (2026-08-28 최종)

`압도적 샷발` 과 **같은 조건 틀**을 쓴다 — 라플 전용 · 같은 팀 안에서 비교 · 같은 임계값 방식.
지표만 다르다: **라운드 초반 사망**.
(사용자 문구가 "샷발이랑 똑같은 뱃지인데 이름만 다름" 이라 두 갈래로 읽혔다.
 앞서 "라운드 초반에 많이 죽는 사람" 이라고 지시했으므로 지표는 그대로 두고 조건 틀만 맞췄다.
 완전히 같은 뱃지를 뜻한 것이라면 되돌리면 된다.)

**어태커** — "라운드 초반"을 재려면 라운드 시작 시각이 필요한데,
`event_time` 이 **경기 누적 시간**이라 라운드 시작을 정확히 모른다.
한 라운드에 그 선수 이벤트가 중앙값 1개뿐이라 "라운드 첫 교전"을 기준점으로 쓰기도 어렵다.
→ 상대 비교(같은 라운드 번호끼리 죽은 시각 비교)로 근사할 수는 있다. 정확도 검증 필요.

### 부여 규칙 (2026-08-28 사용자 지시)

```
대상      통합랭킹 1~50위  **그리고** 그 시즌 30경기 이상
회수      순위가 50위 밖으로 밀리면 **자동 회수**
개수      50위 안의 모든 선수가 **1개 이상 3개 이하**를 갖도록 설계한다
```

마지막 조건이 임계값을 정한다. **고정된 절대 기준을 지어내지 않는다.**

1. 뱃지마다 지표를 계산하고 **그 50명 안에서 순위(백분위)** 를 매긴다
2. 각 뱃지의 상위 몇 명에게 후보 자격을 준다
3. **0개인 사람**에게는 그 사람이 가장 잘하는 뱃지 하나를 준다 (백분위가 가장 높은 것)
4. **4개 이상인 사람**은 백분위 상위 3개만 남긴다

무기 전용 뱃지(`압도적 샷발`=라플, `압도적 스나싸움`=스나)는 자격이 없는 선수에게
후보로 올리지 않는다. 3번 규칙이 그런 선수도 최소 1개를 받게 보장한다.

임계값과 각 뱃지의 정원은 **상수 하나로 모은다** (`CLAUDE.md` 3-B 6번의 취지).
값을 바꾸면 재수집 없이 재계산만 하면 되게 한다.

### 수집 범위

**최근 300경기로 자른다** (사용자 지시). 전체 기록은 4~13시간이라 현실적이지 않다.

## 5. 수집 규모

```
포지션 판정용 (정답 20명)      20명 × 100경기 = 최대 2,000 요청 · 약 30~40분
뱃지용 (상위 50명)             1인당 참여 경기가 1,000~3,000건이라
                              전체를 받으면 5만~15만 요청 = 4~13시간
                              → **최근 300경기로 자르면** 1.5만 요청 · 약 1시간 20분
```

요청 간격은 320ms 를 지킨다. 원본에 대한 예의다 (`CLAUDE.md` 3-A 5번).

**원문(raw)을 버리지 않는다** (3-A 1번). 구역이나 판정 기준을 고쳐도
배틀로그를 다시 받지 않고 재계산만 하면 되게 저장한다.

## 6. MVP 선정 기준 변경 (2026-08-28 사용자 지시)

지금 MVP 는 원본이 준 `mvp_player_id` 를 그대로 쓴다 (사실상 최다킬 기준으로 보인다).
여기에 **예외 하나**를 얹는다.

```
플레이시간 20분 초과 경기에서
  마지막 라운드(= 매치라운드)에 **세이브를 한 선수가 있으면**
  그 선수가 MVP 다.  (최다킬보다 우선)

세이브가 없으면 기존 기준(원본 값) 그대로.
```

> ⚠ 이건 **원본과 달라지는 지점**이다. 원본 3rd.supply 는 자기 기준으로 MVP 를 정하고
> 우리는 그 값을 미러링해 왔다 (`Match.mvpPlayerId` · `MatchPlayerStat.mvp`).
> 이 규칙을 적용하면 **같은 경기의 MVP 가 원본과 달라진다.**
> 그래서 원본값을 덮어쓰지 않는다 — 원본값은 그대로 두고 우리 판정을 **따로 저장**한다
> (`CLAUDE.md` 3-A 2번: 과거 기록을 추정으로 덮어쓰지 않는다).
> 화면에 무엇을 보여줄지는 별도 결정 사항이다.

세이브 판정은 4절과 같다 — 1대1부터 인정하므로 **그 경기 10명 전원의 배틀로그**가 필요하다.

## 7. 시즌7 랭킹도 무기별로 나눈다 (2026-08-28 사용자 지시)

가져온 시즌7 기록의 개인랭킹을 **통합 / 스나 / 라플** 로 분류한다.

```

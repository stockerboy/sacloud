## 1. 데이터 출처 — 병영수첩 BattleLog

### 접근 방법 (중요)

Node/서버에서 병영수첩을 부르면 **403** 이다 (AWS WAF 봇차단). 실측 확인했다.
UA 를 위조해 뚫지 않는다 — `CLAUDE.md` 3-A 5번.

**대신 사용자의 로그인된 Chrome 을 자동화해서 받는다.** 브라우저 자동화 도구로
페이지 컨텍스트에서 `fetch` 를 호출하면 정상 동작한다 (2026-08-28 실측).
이건 우회가 아니라 **사용자 자신의 브라우저가 하는 정상 요청**이다.

### 엔드포인트 (실측)

```
POST /api/Match/GetMatchList/
  본문(첫 페이지)  {"user_nexon_sn":"<str_usn>","mode_flag":"ALL"}
  본문(다음 페이지) {"user_nexon_sn":"<str_usn>","mode_flag":"ALL",
                    "seq_no":"<직전 응답의 message>","min_seq_no":"0"}

  ⚠ `seq_no` 나 `min_seq_no` 에 **빈 문자열을 보내면 `rtnCode:-999 Exception`** 이다.
    생략하거나 `"0"` 을 보내야 한다. 이것 때문에 첫 수집이 통째로 실패했다.

  응답  { rtnCode:20, message:"<다음 커서>", result:[ {
           match_key, map_name, match_name, match_type, match_time_date,
           kill_cnt, death_cnt, assist_cnt, damage_cnt, head_cnt, save_cnt, ...
         } ] }

POST /api/BattleLog/GetBattleLog/<match_key>/<str_usn>
  응답  { battleLog:[ ... ] }
  ⚠ 이 응답에는 **`rtnCode` 가 없다.** 그걸 검사하면 전부 실패로 처리된다 (실제로 그랬다).
```

### BattleLog 이벤트 필드 (실측)

```
round            라운드 번호
event_time       "MM:SS" — **경기 전체 누적 시간**이다. 라운드 기준이 아니다
event_type       kill | death | bomb | g_death
weapon           riple | sniper | throw | assist | close | c4-install
kill_x, kill_y   죽인 사람이 서 있던 위치
death_x, death_y 죽은 사람이 서 있던 위치
str_usn          이 로그의 주인 (그 선수)
user_nick / user_nexon_sn            죽인 사람
target_str_usn / target_user_nick    죽은 사람
```

**한 로그에는 그 선수 본인이 얽힌 이벤트만 온다.** 팀원 전체 이벤트는 없다.
그래서 한 라운드에서 그 선수의 이벤트는 **중앙값 1개**(평균 1.5개)뿐이다 —
이동 경로를 복원할 수 없다. 뒤의 `[미확인]` 절 참조.

## 2. 구역 정의

사용자가 좌표 산점도 위에 형광펜으로 직접 칠해 주었고, 그 이미지에서 픽셀로 추출했다.
격자 10 단위 셀 집합으로 저장한다 (`zonemap.json`).

```
B        x 130~320 · y 300~500   (노랑)
2층      x 170~320 · y 310~440   (보라)
숏(A)    x 190~430 · y 230~360   (하늘)
스나싸움  x 140~410 · y 270~560   (빨강) — 뱃지 전용, 위 셋과 겹쳐도 된다
```

**겹칠 때 우선순위는 2층 > B > 숏.** 사용자가 2층·B 표시는 "완벽에 가깝다"고 했고
숏만 다시 칠했기 때문이다.

> ⚠ **2층은 A 의 위층이라 미니맵 x/y 가 겹친다.** 좌표만으로는 2층과 숏을 못 가른다.
> 실제로 2층 선수 5명 전원이 "숏이 최다 구역"으로 나왔다. 그래서 구역 비율이 아니라
> **분포 전체를 학습**하는 방식을 쓴다 (3절).

> ### 2026-08-30 사용자 확정 — 포지션 4개 · **팀 구성이 고정이다** (D-199)
>
> > "포지션은 개인기록카드에 포지션: 숏 이런식으로 우리가 로그 통해서 판단한걸로 넣되
> >  유저가 바꿔달라고 하거나 직접 바꾸면 유저권리먼저 보장해준다.
> >  그리고 포지션은 매 기록마다 로그를 분석해서 경기상세에 유저별로 포지션을 어디 봤는지
> >  기록해준다. 숏 이층 스나 B리베 총4개의 포지이고 **B리베는 팀당 두명이다**"
>
> #### ① 포지션은 4개이고 **한 팀의 구성이 정해져 있다**
>
> ```
> 숏 1명 · 2층 1명 · 스나 1명 · B리베 2명   = 5명
> ```
>
> **이것이 가장 중요한 정보다.** 지금 판정기는 선수를 한 명씩 따로 분류한다 —
> 그래서 한 팀에 2층이 셋 나오는 것도 막지 못한다.
> 구성이 고정이면 **한 팀 다섯 명을 한꺼번에 배정하는 문제**가 되고, 경우의 수도
> 스나를 뺀 4명을 숏1·2층1·B리베2 로 나누는 **12가지뿐**이라 전부 따져 볼 수 있다.
> 게다가 스나는 무기 판정(D-195 · 정확도 99.9%)으로 거의 확실하게 정해진다.
>
> → 독립 분류 91.3% 보다 **더 올라갈 여지가 크다.** 실측해서 확인한다.
>
> #### ② `B` 와 `리베` 를 합쳐 **`B리베`** 한 자리로 부른다
>
> D-189 에서 리베를 없애고 B 에 흡수했는데, 그 자리는 **팀당 두 명**이다.
> 이름도 `B` 가 아니라 `B리베` 다.
>
> #### ③ 우선순위 — **사람이 정한 값이 이긴다**
>
> ```
> 1. 선수가 직접 등록/수정한 값     ← 언제나 이긴다
> 2. 우리가 로그로 판정한 값
> 3. 둘 다 없으면 비운다 (지어내지 않는다)
> ```
>
> 자동 판정이 사람을 덮어쓰지 않는다. "바꿔달라" 는 요청도 같은 취급이다.
>
> #### ④ **경기마다** 포지션을 남긴다
>
> 지금은 선수 한 명당 누적 판정 하나뿐이다. 앞으로는 **경기 × 선수** 단위로 판정해
> 매치 상세에서 "이 경기에서 이 선수는 어디를 봤다" 를 보여준다.
> 한 선수가 경기마다 다른 자리를 설 수 있다는 뜻이기도 하다 —
> 누적 판정은 그 경기별 판정들을 모아서 낸다.
>
> ⚠ 아직 **구현 전이다.** 지금 있는 것은 선수 단위 누적 판정(517명 · 91.3%)뿐이고,
> 팀 구성 제약도 경기별 기록도 들어가 있지 않다.

## 3. 포지션 자동 판정

원본은 선수가 **직접 등록**한다. 우리는 **배틀로그로 자동 판정**한다 — 다른 기능이다.
원본에서 가져온 `Player.position`(숫자 코드)과 **섞지 않는다.**

### 방법

선수별로 좌표를 20 단위 격자 히스토그램으로 만들고, 정답 표본의 중심과 코사인 유사도를
비교한다. 검증은 **한 명씩 빼고 학습해 그 사람을 맞히는 방식**(leave-one-out)으로 한다.

### 실측 정확도 (정답 20명 · 선수당 30경기)

| 조건 | 정확도 |

### 대상 — **모든 선수**

상위 50명 같은 제한을 두지 않는다. 개인 기록 화면이면 누구에게나 육각형이 있다.

**데이터가 모자란 선수에게는 작은 정육각형을 그리고 `전투력 측정중` 이라고 적는다.**
그 정육각형은 **심장처럼 조금 커졌다 작아졌다** 움직인다. 값을 0으로 그리지 않는다 —
0은 "못한다" 는 뜻이고 지금은 "아직 모른다" 이기 때문이다 (D-106 과 같은 원칙).

### 넓이를 정하는 방법

각 축은 **같은 무기끼리 견준 백분위**다. 절대 기준을 지어내지 않는다.

```
그 선수의 지표값  →  같은 무기(스나/라플) 선수들 안에서 몇 %인가  →  0~100 넓이
```

스나가 라플보다 킬뎃이 높은 것은 무기의 성질이지 실력이 아니다.
그래서 **스나는 스나끼리, 라플은 라플끼리** 줄 세운다.

#### 1. 세이브

세이브 확률 = 혼자 남아서 이긴 라운드 / 혼자 남은 라운드
```

#### 2. 스나싸움(스나) · 샷싸움(라플)

- **스나싸움** — 스나싸움 구역(`data/barracks/sniper-lane.json`)에서 상대 스나와 벌인 교전의 성과.

  (우리 DB `MatchPlayerStat.weapon` 에 전 참가자 무기가 있다).
- **샷싸움** — 라플수 중 **딜량**이 유독 높으면 넓다.

> **탈주판은 딜량 평균에서 뺀다** (D-209). `MatchPlayerStat.damage = 0` 은 "0딜을 넣었다" 가
> 아니라 **결측이 0 으로 저장된 것**이다 — 실측으로 그런 행의 98.4% 가 탈주였고 같은 행에서
> `assist` · `headshot` 도 전원 0이었다. 넣고 세면 이 축이 딜량이 아니라 **팀의 탈주 빈도**를
> 절반쯤 재게 된다 (라플 판당딜 중앙값이 919.7 로 찍혔다 · 실제 1,400대).
>
> 그래서 딜량은 `damage > 0` 인 판만 세고, **그 판수에도 `TRAIT_MIN_GAMES` 를 따로 건다.**
> 못 넘기면 이 축만 `경기 부족` 이다 — 캐리력은 킬 판수를 쓰므로 그대로 재진다.
> 조건의 단일 정의는 `apps/web/lib/server/queries/dropoutScope.ts` 다.

#### 3. 캐리력

판당 평균 킬. **무기별로 따로 줄 세운다.** 킬·데스는 결측이 없어 (경기당
`sum(red kill)` 과 `sum(blue death)` 가 97.0% 에서 정확히 일치) **탈주판도 그대로 센다** (D-209).

#### 4. 미정 — **비어 있다** (2026-08-30 · D-206)

무엇을 잴지 **아직 정하지 않았다.** 값이 없고 꼭지점에 `미정` 이라고만 적는다.
꼭지점은 그대로 여섯 개다 — 오각형으로 만들지 않는다
(사용자: *"육각그래프는 꼭 쓰고싶은데"*).

`미정` 은 `측정중` 과 **다른 상태**다. `측정중` 은 재료가 들어오면 채워지고,
`미정` 은 사람이 정하기 전에는 채워지지 않는다. 그래서 `측정중 N항목` 요약에서도 뺀다.

### 화면에는 **우리 MVP** 를 보여준다 (2026-08-29 사용자 확정)

> "원본이 3rd.supply 를 말하는 거라면 당연히 원본과 다른 방식으로 MVP 를 선정하기 때문에
> 우리가 선정한 MVP 를 보여줘야 한다."

- **화면 = 우리 판정.** 원본 MVP 는 화면에서 쓰지 않는다
- **저장 = 둘 다.** 원본값(`Match.mvpPlayerId` · `MatchPlayerStat.mvp`)은 **한 줄도 안 고친다.**
  우리 판정은 새 칸에 따로 담는다 — 어느 쪽이든 나중에 되짚을 수 있어야 한다
- 우리 판정을 **아직 계산할 수 없는 경기**(라운드 복원이 안 되는 경기)는 우리 값이 `null` 이다.

> `[미확인]` 기록실·매치 상세의 **과거 경기**도 우리 MVP 로 다시 보여줄지,
> 아니면 앞으로 쌓이는 경기부터인지 확정 필요. 과거 13만 경기는 라운드 복원이 안 되므로
> 실질적으로는 대부분 `알수없음` 이 된다.

세이브 판정은 4절과 같다 — 1대1부터 인정하므로 **그 경기 10명 전원의 배틀로그**가 필요하다.
→ 그 조건은 **클랜 단위 배틀로그로 충족됐다** (D-184 · D-194). 막고 있는 것은 자료가 아니라

## 8. 플레이스타일 바 (2026-08-29 사용자 지시)

육각형 **바로 아래**에 **바 두 줄**로 그린다. 육각형이 "얼마나 잘하나" 라면
이것은 **"어떻게 하나"** 다. 잘하고 못하고를 뜻하지 않는다 — 가운데(`정석`)가 나쁜 것이 아니다.

```
블루   안전함  <<<<<<  정석  >>>>>>>>  변칙적
레드   느린전개 <<<<<  정석  >>>>>>>>  빠른전개
```

### 블루·레드는 **팀 진영**이다 (2026-08-29 사용자 확정)

> "플레이스타일 바는 블루 레드가 수비 공격이다."

```
블루 = 수비   안전함  ↔  변칙적
레드 = 공격   느린전개 ↔  빠른전개
```

바 두 줄의 색 이름이 아니다. **그 진영으로 뛴 라운드만 골라서 잰다.**
수비 라운드의 움직임으로 공격 성향을 재면 거짓이 된다.

> ⚠ 그래서 **라운드마다 그 선수가 어느 진영이었는지**를 알아야 한다.
> 폭파미션은 전반·후반에 진영이 바뀐다. `Match` 의 red/blue 클랜은 **경기 단위** 값이라
> 그것만으로는 라운드별 진영을 알 수 없다.
>
> `[미확인]` **진영이 바뀌는 라운드를 어떻게 아는가.** 배틀로그 이벤트에 진영 표시가 없다.
> 후보: ① 라운드 수의 절반에서 바뀐다고 보기 ② 스코어 진행에서 되짚기 ③ 원본에 없으니 포기.
> **추측해서 절반으로 자르지 마라** — 연장·조기종료가 있으면 어긋난다. 먼저 재고 결정한다.

**남은 것은 두 가지다 — 좌표를 그 구역들에 붙이는 판정, 그리고 바 값의 계산.**

상수로 돌려준다. 화면 자리와 `측정중` 표시만 있다. **가운데(`정석`)로 채우지 않는다** —
`정석` 은 "재 봤더니 가운데" 라는 뜻이라 모르는 것을 그렇게 적으면 거짓이 된다.

> ⚠ 코드 주석(`packages/contract/src/traits.ts` · `buildPlayerPlaystyle`)에 아직
> "클랜 단위 배틀로그 수집분이 아직 0건이다" 가 남아 있다. **낡은 서술이다** —
> 2,760행이 들어와 있다. 계산을 붙일 때 함께 고친다.

## 10. 오늘 퍼포먼스 (2026-08-29 사용자 지시)

```
6전 2승 4패로 승률은 47퍼, 킬데스 42퍼로 폼이 하락중입니다
```

### 하루의 경계는 **오전 7시 KST** 다 (2026-08-29 사용자 확정 · D-186)

자정이 아니다. 클랜전은 밤에 열려 새벽까지 이어지므로, 자정에 자르면 한 번 앉아서 뛴
판들이 이틀로 쪼개진다.

```
오늘 = 오늘 07:00 KST ~ 내일 07:00 KST
지금이 오전 7시 전이면 아직 "어제" 안이다 — 시작은 어제 07:00 KST
```

코드: `DAY_START_HOUR_KST = 7` (`packages/contract/src/todayPerformance.ts`).

### `최근 폼`(D-167)을 **대체한다** (2026-08-29 사용자 확정 · D-186)

뒤 절의 `[미확인]`(대체인가 병기인가)은 **해소됐다.** 6개월 꺾은선 `최근 폼` 을 빼고
그 자리를 오늘 기록이 이어받는다. 컴포넌트와 계약 필드는 남겨 뒀다.

### 폼은 **킬데스만** 으로 정한다

**그날의 승률은 폼을 결정하지 않는다.** 문구에는 적지만 판정에는 쓰지 않는다.

```
기준   그 선수의 시즌 평균 킬데스
비교   오늘 킬데스

|오늘 − 시즌평균| ≤ 2%p   →  폼 유지중
오늘이 그보다 낮으면        →  폼 하락
오늘이 그보다 높으면        →  폼 상승
```

예: 시즌 422전 222승 200패 · 킬데스 61% 인 선수라면
**59~63% 는 유지**, 그 밖으로 벌어지면 하락 또는 상승.

오늘 경기가 하나도 없으면 ~~`오늘 경기기록 없음`~~ → **`미접속`** 이라고만 적는다
(2026-08-29 사용자 확정 · D-186 · `NO_GAMES_TODAY`). 폼을 판정하지 않는다.
`0승 0패` 는 결과처럼 읽히므로 쓰지 않는다.

### 폼은 **3판부터** 본다 (2026-08-29 사용자 확정)

오늘 K/D 를 아는 경기가 **3판 미만**이면 전적과 킬데스는 그대로 보여주되 **폼은 판정하지 않는다.**

한 경기(20라운드) 킬데스의 이항 표준오차가 **≈11%p** 다. `±2%p` 경계는 한 판짜리 표본에서
거의 항상 넘어가므로, 그대로 두면 1경기 뛴 선수는 `유지중` 이 나올 수가 없고
**상승 아니면 하락으로만** 뜬다. 그건 폼을 읽는 것이 아니라 난수를 읽어 주는 것이다.

모자랄 때 `유지중` 으로 뭉개지 않는다 (D-106). 문구는 이렇게 나간다.

```
2전 1승 1패로 승률은 50퍼, 킬데스 58퍼입니다 (3판부터 폼을 봅니다)
```

> ~~`[미확인]` 이 문구가 기존 `최근 폼`(최근 10경기 vs 직전 30경기 · D-167)을 **대체하는지**,
> 아니면 나란히 두는지 확정 필요.~~ → **해소됨. 대체한다** (2026-08-29 · D-186).

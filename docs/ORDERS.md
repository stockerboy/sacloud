# ORDERS.md — 지시서 창구

> **A(기획 세션)가 쓰고, B(실행 세션)가 읽는 곳이다.**
> 사장님은 A와 회의만 하시면 된다. 여기에 직접 안 쓰셔도 된다.
>
> 만든 날 2026-09-02. 만든 이유는 아래 「왜 이 파일이 있나」.

---

## 규칙 (짧다)

```
A 가 하는 일   사장님과 회의 → 여기에 지시서 한 칸을 새로 적는다 → B 에게 "썼다" 한 줄
B 가 하는 일   맨 위 「대기」 칸을 읽는다 → 만든다 → 검증한다 → 상태를 「끝」으로 바꾼다
사장님이 하실 일  A 와 대화만. 나머지는 둘이 알아서
```

- **새 지시는 맨 위에 쌓는다.** 아래로 내려갈수록 오래된 것이다
- **한 칸에 한 가지만.** 두 가지면 칸을 두 개 만든다
- **끝난 칸은 지우지 않는다.** 상태만 바꾼다 (`CLAUDE.md` 10-4)
- B 는 지시서에 없는 일을 하지 않는다. 필요하면 A 에게 되묻는다

## 상태 표시

| 표시 | 뜻 |
|---|---|
| `대기` | A 가 적었고 B 가 아직 안 잡았다 |
| `진행` | B 가 하고 있다 |
| `막힘` | B 가 하다 막혔다. 아래 「막힌 이유」를 A 가 읽고 다시 정한다 |
| `끝` | 검증까지 끝났다. 「어떻게 확인했나」에 숫자가 적혀 있어야 한다 |

## Part 단위로 일한다 (2026-09-02 사장님 확정 · 이 절이 위 규칙보다 우선한다)

### Part 가 끝났다는 뜻

```
사장님이 직접 보고 「생겼구나 / 바뀌었구나 / 좋아졌구나」 할 수 있는
기능 또는 UI 결과물이 최소 1개 나왔을 때   ← 이때만 Part 하나가 끝난 것이다
```

| 끝난 것으로 본다 | 끝난 것으로 안 본다 |
|---|---|
| 새 화면이 실제로 생김 | 코드만 정리 |
| 기존 화면이 눈에 띄게 좋아짐 | 내부 구조만 바꿈 |
| 새 기능이 실제로 동작함 | 조사만 끝냄 |
| 기존 기능이 눈에 보이게 좋아짐 | 계획만 세움 |
| 사장님이 직접 눌러 볼 결과물이 생김 | 아직 볼 것이 없음 |

### Part 안에서는 자율이다

- A 는 기획·판단·작업분해·검수 총괄. B 는 코드·구현·테스트
- 서브에이전트를 자유롭게 쓴다. 병렬로 나눌 수 있으면 나눈다
- **중간 승인을 받지 않는다.** 문제가 있으면 사장님을 부르기 전에 우리끼리 고친다
- 순서: 목표 확정 → 세분화 → 병렬 분배 → 구현 → **자체 검수** → 증거 확보(스크린샷·수치·테스트)
- 속도 · 정확도 · 효율이 우선이다. 방법은 우리가 고른다

### 사장님을 부르는 때 — 둘뿐이다

**A. Part 가 완전히 끝났을 때.** 보고 형식은 이대로:

```
Part 번호 / 이름
이번 Part 의 목표
새로 생기거나 바뀐 것
사장님이 바로 확인해야 할 것
테스트 결과
남은 문제
다음 Part 후보
```
가능하면 **스크린샷 · 수치 · 테스트 결과**를 같이 붙인다.

**B. 사람 판단 없이는 못 가는 때.** 선택지가 여럿이라는 이유로는 부르지 않는다.
제품 방향이 달라지는 것만 — 기능을 없앨지 / 유료·무료 / 핵심 흐름 변경 /
브랜드·디자인 방향 전환 / 데이터 정책 / 되돌리기 어려운 중대 결정.

### 사장님이 불만족하실 때 — 6칸 구조

사장님 피드백은 **A 가 다시 쓰지 않아도 그대로 B 의 작업지시서가 되게** 만든다.

```
1 지금 뭐가 마음에 안 드는가
2 원하는 결과
3 반드시 유지할 것
4 반드시 바꿀 것
5 건드리지 말 것
6 완료 조건 (무엇을 보면 완료로 인정하는가)
```

사장님이 짧게 말씀하셔도 A 가 **속으로 이 6칸으로 옮긴다.**
「이렇게 이해했는데 맞습니까」로 되묻지 않는다 — 뜻이 충분하면 그대로 B 에게 보낸다.
잘못 이해하면 큰일 나는 때만 묻는다.

처리 순서: 구조화 → 애매한 말을 개발 가능한 조건으로 → 기존 Part 목표와 충돌 확인
→ B 에게 전달 → 수정 → 자체 검수 → **완성됐을 때만** 다시 부른다.

### `prpt` — 즉시 실행 명령

사장님 메시지가 `prpt` 로 시작하면 **질문이 아니라 이미 승인된 실행 명령**이다.

```
prpt  =  프롬프트 작성  +  사장님께 전문 공개  +  B 에게 즉시 전달
```

- **「보낼까요?」를 묻지 않는다.** 보여준 뒤 승인을 기다리지 않는다
- 짧은 명령이어도 필요하면 A 가 채운다 — 왜 하는가 / 무엇을 바꾸는가 / 무엇은 유지 /
  무엇은 건드리지 않는다 / 완료 조건 / 검증 방법 / (필요하면) 되돌리는 법
- **작은 일이면 짧고 정확하게, 큰 일이면 상세하고 검증 가능하게.** 쓸데없이 길게 안 만든다
- 명령이 서로 모순되거나 해석이 불가능하거나 복구가 매우 어려울 때만 되묻는다

`prpt` 없는 일반 메시지는 **의견을 묻는 것**이다 — A 가 답하거나 선택지를 준다.

### 가장 중요한 것

> 사장님께는 **과정이 아니라 완성된 결과물**을 보여 준다.
> 우리끼리 고민하고 · 나누고 · 테스트하고 · 실패하면 고치고 · 검수한 뒤,
> 「이건 보여줘도 된다」가 됐을 때만 부른다.

## Part 지도 — A 부터 Z 까지 18판 (A 작성 · 2026-09-02)

### 왜 6·7 이 「새로 만든다」인가

A 가 2026-09-02 에 라우트를 직접 세었다. `apps/web/app` 아래에 **경기목록·경기상세
전용 주소가 하나도 없다.** 지금은 선수·클랜 화면 안의 카드로만 열린다.
「화면 5개」 중 둘이 아직 없는 것이다. 지어내지 않고 그대로 적는다.

### 이 표에 없는 것 (일부러 뺐다)

게시판 · 알(가챠) · 클랜 육각형 · 즐겨찾기 · 유료상품 · 광고 · 관리자 화면 손보기.
**지우지 않는다. 이번 판에 안 할 뿐이다.** 공개 뒤에 사장님이 정하시면 판을 새로 만든다.

### 앞뒤를 바꿔야 할 이유가 생기면

A 가 이 표를 고치고 사장님께 알린다. 몰래 순서를 바꾸지 않는다.

## 지시서 틀 (A 는 이 모양으로 적는다)

```markdown
### O-000 · 제목 한 줄
- 상태: 대기
- 적은 날:
- 왜 하는가: (한 줄. 「이게 안 되면 뭐가 곤란한가」)
- 무엇을: (만들 것. 화면이면 어느 화면인지 이름으로)
- 하지 말 것: (건드리면 안 되는 것. 없으면 「없음」)
- 어떻게 확인하나: ★필수★ 숫자나 눈으로 볼 수 있는 것으로.
  「잘 되면 됨」 같은 말은 확인 방법이 아니다
- 참고: (관련 문서·결정 번호·파일 경로)
```

**「어떻게 확인하나」가 비어 있으면 B 는 시작하지 않는다.**
그 칸이 없어서 일주일 동안 「수집 중」이라는 말을 믿었다.

## 왜 이 파일이 있나

2026-09-02, 프로젝트 14일차에 사장님이 정하신 것이다.

```
그동안        지시가 채팅에만 있었다 → 세션이 죽으면 같이 사라졌다
              요청 대장을 14일차에야 만들었고, 그 전 13일치는 복원이 안 된다
이제부터      지시는 파일에 남는다. 세션이 죽어도 남는다
```

역할을 나눈 이유도 같다. 기획하는 머리와 만드는 손을 갈라 두면,
기획 쪽 대화가 코드로 지저분해지지 않는다. 다만 **A 도 저장소를 읽는다** —
코드를 못 보는 기획자는 그럴듯한 것을 지어낸다. 그게 이 프로젝트가
가장 크게 다친 방식이다.

### O-001 · 홈을 「검색창 + 사이트 소개·사용법」으로 바꾼다
- 상태: 대기

  DB 를 읽는다. **A 가 2026-09-02 운영 화면을 직접 세었다** —
  개인랭킹 SPL 30명 + IPL 30명 + 10mountain 5명 = **65명**, 최근경기 SPL 6 + IPL 6 = **12경기**.
  (`apps/web/app/page.tsx` 주석에는 «각 상위 5명» 이라고 적혀 있는데 **화면은 30명이다. 주석이 틀렸다.**)
  전부 DB 까지 가면 **동시 5명이 한계**다 (2026-09-01 실측 · 동시 10명이면 12.3% 실패).
  홈이 가벼워지는 것이 곧 안 터지는 것이다. 그리고 오늘 정한 홈은 「검색창 + 소개·사용법」이다.
- 무엇을:
  1. **윗머리는 그대로 둔다** — 로고 · 통합검색 · 리그 바로가기 3개.
     `apps/web/app/_home/HomeSearch.tsx` 는 한 글자도 안 건드린다.
  2. 그 아래 두 구역(`HomeRankPreview` · `HomeRecentMatches`)을 **화면에서 뺀다.**
     `apps/web/app/page.tsx` 가 **안 부르기만** 한다. 파일도 export 도 그대로 둔다.
     `getHomeRankPreview()` · `getHomeRecentMatches()` 호출도 같이 빠진다 (그게 DB 를 읽는 곳이다).
  3. 그 자리에 **사이트 소개 + 사용법**을 넣는다.
     - 소개는 이미 있다 — `packages/ui/src/home/SiteIntro.tsx`. 지금 홈이 안 부를 뿐이다.
       되살리는 것은 `<SiteIntro />` 한 줄이다 (그 파일 주석에 그렇게 적혀 있다).
     - **「사용법」은 없다. 새로 쓴다.** 3~5줄이면 된다. 예: 닉네임을 치면 그 선수 기록으로
       간다 / 클랜 이름을 치면 클랜 기록으로 간다 / 리그 버튼을 누르면 순위로 간다.
       문장은 A 가 정하지 않았다 — B 가 초안을 쓰고 확인 칸 4번으로 검사한다.

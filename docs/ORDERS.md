# ORDERS.md — 지시서 창구

> **A(기획 세션)가 쓰고, B(실행 세션)가 읽는 곳이다.**
> 사장님은 A와 회의만 하시면 된다. 여기에 직접 안 쓰셔도 된다.
>
> 만든 날 2026-09-02. 만든 이유는 아래 「왜 이 파일이 있나」.

---

## 규칙 (짧다)

```
A 가 하는 일   사장님과 회의 → 여기에 지시서 한 칸을 새로 적는다 → B 에게 "썼다" 한 줄
B 가 하는 일   맨 위 「대기」 칸을 읽는다 → 만든다 → 검증한다 → 상태를 「끝」으로 바꾼다
사장님이 하실 일  A 와 대화만. 나머지는 둘이 알아서
```

- **새 지시는 맨 위에 쌓는다.** 아래로 내려갈수록 오래된 것이다
- **한 칸에 한 가지만.** 두 가지면 칸을 두 개 만든다
- **끝난 칸은 지우지 않는다.** 상태만 바꾼다 (`CLAUDE.md` 10-4)
- B 는 지시서에 없는 일을 하지 않는다. 필요하면 A 에게 되묻는다

## 상태 표시

| 표시 | 뜻 |
|---|---|
| `대기` | A 가 적었고 B 가 아직 안 잡았다 |
| `진행` | B 가 하고 있다 |
| `막힘` | B 가 하다 막혔다. 아래 「막힌 이유」를 A 가 읽고 다시 정한다 |
| `끝` | 검증까지 끝났다. 「어떻게 확인했나」에 숫자가 적혀 있어야 한다 |

## Part 단위로 일한다 (2026-09-02 사장님 확정 · 이 절이 위 규칙보다 우선한다)

### Part 가 끝났다는 뜻

```
사장님이 직접 보고 「생겼구나 / 바뀌었구나 / 좋아졌구나」 할 수 있는
기능 또는 UI 결과물이 최소 1개 나왔을 때   ← 이때만 Part 하나가 끝난 것이다
```

| 끝난 것으로 본다 | 끝난 것으로 안 본다 |
|---|---|
| 새 화면이 실제로 생김 | 코드만 정리 |
| 기존 화면이 눈에 띄게 좋아짐 | 내부 구조만 바꿈 |
| 새 기능이 실제로 동작함 | 조사만 끝냄 |
| 기존 기능이 눈에 보이게 좋아짐 | 계획만 세움 |
| 사장님이 직접 눌러 볼 결과물이 생김 | 아직 볼 것이 없음 |

### Part 안에서는 자율이다

- A 는 기획·판단·작업분해·검수 총괄. B 는 코드·구현·테스트
- 서브에이전트를 자유롭게 쓴다. 병렬로 나눌 수 있으면 나눈다
- **중간 승인을 받지 않는다.** 문제가 있으면 사장님을 부르기 전에 우리끼리 고친다
- 순서: 목표 확정 → 세분화 → 병렬 분배 → 구현 → **자체 검수** → 증거 확보(스크린샷·수치·테스트)
- 속도 · 정확도 · 효율이 우선이다. 방법은 우리가 고른다

### 사장님을 부르는 때 — **사장님이 지정한 Part 에서만** (2026-09-02 갱신)

```
사장님이 Part 지도를 보고 「이 판 끝나면 불러」 라고 찍어 주신다.
찍힌 판에서만 부른다. 안 찍힌 판은 끝나도 부르지 않고 다음 판으로 넘어간다.
```

- **완성됐다고 무조건 부르지 않는다.** 그게 이 규칙이 바뀐 이유다
- 찍힌 판이 아직 없으면 **계속 간다.** 멈춰서 기다리지 않는다
- 안 찍힌 판의 결과는 버리지 않는다 — `O-` 칸의 「어떻게 확인했나」에 숫자로 남기고,
  다음에 부를 때 **한꺼번에** 보여 드린다

### ★사장님이 찍으신 호출 지점★ (2026-09-02 · 원문 그대로)

> "1막 끝나고 한번 불러 ui보고 맘에 안드는 부분 얘기해줄거야
>  (**걍 ui하나 추가하거나 완성될때마다 불러**)
>  4막 전에 한번 더 불러 어떤 기록들을 가져와야하는지 나한테 한번 더 확인 받아
>  4막 끝나면 나를 한번 더 불러
>  5막 전에 한번 불러
>  **이 외엔 날 부르지마**"

| 지점 | 언제 | 무엇을 위해 |
|---|---|---|
| **1막 전체** | Part 1·2·3·4·5·6·7·8 **각각이 끝날 때마다** | UI 를 보시고 마음에 안 드는 곳을 말씀하신다 |
| 2막 (9·10) | — | **부르지 않는다** |
| 3막 (11·12) | — | **부르지 않는다** |
| **4막 직전** | Part 13 시작 전 | **어떤 기록을 가져올지** 다시 확인받는다 |
| **4막 직후** | Part 15 끝난 뒤 | 결과 보고 |
| **5막 직전** | Part 16 시작 전 | 확인 |

**1막은 판마다 부른다.** 「UI 하나 추가되거나 완성될 때마다」가 사장님 말씀이다 —
1막이 다 끝나기를 기다리지 않는다.

그 외에는 부르지 않는다. 예외는 위 「사람 판단 없이는 못 가는 것」 하나뿐이다.

부를 때의 보고 형식:

```
Part 번호 / 이름
이번 Part 의 목표
새로 생기거나 바뀐 것
사장님이 바로 확인해야 할 것

남은 문제
다음 Part 후보
```
가능하면 **스크린샷 · 수치 · 테스트 결과**를 같이 붙인다.

**예외 — 이때는 안 찍혀 있어도 부른다.** 사람 판단 없이는 못 가는 것.
선택지가 여럿이라는 이유로는 부르지 않는다. 제품 방향이 달라지는 것만 —
기능을 없앨지 / 유료·무료 / 핵심 흐름 변경 / 브랜드·디자인 방향 전환 /
데이터 정책 / 되돌리기 어려운 중대 결정.

### 사장님이 불만족하실 때 — 6칸 구조

사장님 피드백은 **A 가 다시 쓰지 않아도 그대로 B 의 작업지시서가 되게** 만든다.

```
1 지금 뭐가 마음에 안 드는가
2 원하는 결과
3 반드시 유지할 것
4 반드시 바꿀 것
5 건드리지 말 것
6 완료 조건 (무엇을 보면 완료로 인정하는가)
```

사장님이 짧게 말씀하셔도 A 가 **속으로 이 6칸으로 옮긴다.**
「이렇게 이해했는데 맞습니까」로 되묻지 않는다 — 뜻이 충분하면 그대로 B 에게 보낸다.
잘못 이해하면 큰일 나는 때만 묻는다.

처리 순서: 구조화 → 애매한 말을 개발 가능한 조건으로 → 기존 Part 목표와 충돌 확인
→ B 에게 전달 → 수정 → 자체 검수 → **완성됐을 때만** 다시 부른다.

### `prpt` — 즉시 실행 명령

사장님 메시지가 `prpt` 로 시작하면 **질문이 아니라 이미 승인된 실행 명령**이다.

```
prpt  =  프롬프트 작성  +  사장님께 전문 공개  +  B 에게 즉시 전달
```

- **「보낼까요?」를 묻지 않는다.** 보여준 뒤 승인을 기다리지 않는다
- 짧은 명령이어도 필요하면 A 가 채운다 — 왜 하는가 / 무엇을 바꾸는가 / 무엇은 유지 /
  무엇은 건드리지 않는다 / 완료 조건 / 검증 방법 / (필요하면) 되돌리는 법
- **작은 일이면 짧고 정확하게, 큰 일이면 상세하고 검증 가능하게.** 쓸데없이 길게 안 만든다
- 명령이 서로 모순되거나 해석이 불가능하거나 복구가 매우 어려울 때만 되묻는다

`prpt` 없는 일반 메시지는 **의견을 묻는 것**이다 — A 가 답하거나 선택지를 준다.

### 가장 중요한 것

> 사장님께는 **과정이 아니라 완성된 결과물**을 보여 준다.
> 우리끼리 고민하고 · 나누고 · 테스트하고 · 실패하면 고치고 · 검수한 뒤,
> 「이건 보여줘도 된다」가 됐을 때만 부른다.

## A 가 지시서를 쓸 때 지키는 것 (2026-09-02 · B 의 지적으로 추가)

오늘 A 가 네 번 틀렸다. 그래서 규칙으로 박는다.

### 1. 사실이 어긋나면 **코드가 이긴다**

```
A 가 사장님께 확정한 것 ≠ B 가 코드에서 본 것
  → 코드가 이긴다. 다만 B 는 고치기 전에 A 에게 즉시 알린다
```
오늘 두 번 어긋났다 — 게시판(A: 닫혀 있다 / 실제: 주소 200), 화면 개수(5개 → 6개).
둘 다 B 가 알려서 고쳤지만 **우연이었다.** 이제 규칙이다.

### 2. 문장마다 「확인함」인지 「추정」인지 밝힌다

A 가 「게시판은 닫혀 있다」를 단정문으로 썼고 확인한 적이 없었다.
**B 가 추정을 사실로 받아 코드를 짜면 거짓말이 배포된다.**
확인 안 한 것은 `[추정]` 을 붙이고, B 는 `[추정]` 이 붙은 문장을 **먼저 확인한 뒤** 진행한다.

### 3. 확인 조건은 「0개」가 아니라 **「무엇이 참이면 통과」**로 쓴다

```
나쁨   없는 기능이 0번 나와야 한다        ← 「없다고 밝히는 줄」이 걸린다
좋음   없는 기능을 **있다고** 쓴 곳이 0개
```

### 4. 못 하는 확인 방법을 계속 넣지 않는다

스크린샷을 세 판 연속 못 찍었다(크롬 창이 죽는다). 못 하는 조건을 계속 넣으면
**「미확인」이 기본값**이 된다. 스크린샷을 넣을 거면 **대신 쓸 확인 방법**을 같이 적는다.

### 5. 속도는 판이 아니라 **각 판의 확인 항목**이다

화면 여섯을 다 만든 뒤 속도를 재면 느린 원인이 여섯 군데에 흩어져 되돌릴 수 없다.
O-001 이 증거다 — 홈에서 `force-dynamic` 하나를 고치자 캐시 MISS 5회가 HIT 5회가 됐다.
그건 「속도 판」이 아니라 **그 화면을 만들다** 찾았다.

**화면을 만드는 모든 판(Part 3~8)의 확인 칸에 이 두 줄을 넣는다.**
```
이 화면이 DB 를 몇 번 때리나        (0 이면 가장 좋다)
캐시가 HIT 인가                     (x-vercel-cache 를 5회 재서 적는다)
```

### ★위험 검토 결과 (2026-09-02) — 문서가 틀린 것 둘★

**1. 「홈만 캐시가 걸렸고 나머지는 미확인」은 틀렸다.**
진짜 캐시층은 페이지가 아니라 `apps/web/lib/server/respond.ts` 에 있다.
```
okPublic / okPagePublic / guardPublic
  → Cache-Control: public, max-age=0, s-maxage=300, stale-while-revalidate=86400
```
**API 라우트 89개 중 34개**가 이것을 쓰고, 그 34개가 **화면 6개의 공개 읽기 경로를
사실상 다 덮는다** — 랭킹 · 선수 · 클랜 · 경기 · 검색. 나머지 55개는 `admin/*` · `auth/*` ·
`me/*` · 쓰기라서 안 걸리는 게 맞다.

**2. ★병목은 `connection_limit` 이 아니다. Supavisor 풀 크기 5다★**
우리 문서 전체가 `connection_limit=1` 을 범인으로 적어 두고 있었다. 코드를 보면 다르다.
```
packages/db/src/index.ts 29-47   운영 URL 에 connection_limit 이 없어도 console.warn 만 찍는다.
                                 고쳐 주지 않는다
같은 파일 운영 실측 주석          max_connections 60 · 현재 접속 17 ·
                                 ★그중 Supavisor 가 여는 것은 5개★
```
부하 실측의 「동시 5명이 한계」와 **정확히 일치한다.**
`connection_limit` 을 만져도 안 풀린다. 풀 크기를 키워야 한다 —
다만 `respond.ts` 56행에 «늘렸더니 Supabase 풀러가 먼저 무너졌다» 는 기록이 있다.
**이건 코드로 판단 못 한다. 사람이 Supabase 콘솔에서 확인해야 한다.**

**3. 운영에서는 DB 재시도를 일부러 껐다** (`packages/db/src/index.ts` 230행).
운영에서 P1001 이 나면 **곧바로 500** 이다.

**4. `lastKnownGood` 은 람다마다 따로다** (`lib/server/lastKnownGood.ts` 49행 — 프로세스 안 `Map`).
서버리스는 인스턴스가 수십 개 뜨고 전부 차갑다. **DB 가 흔들릴 때 지켜 줄 안전망이
공개일 첫 몇 분에는 거의 비어 있다.** 실질 안전망은 엣지의 `stale-while-revalidate=86400` 이므로
**공개 전에 6개 화면 주요 URL 을 미리 긁어 엣지를 데워 둔다** (30분짜리).

**5. 로그인·가입 rate limit 이 DB 트랜잭션이다** (`lib/server/rateLimit.ts` 136행 `prisma.$transaction`).
트랜잭션 풀러에서 interactive transaction 은 서버 커넥션을 붙잡는다. 자리가 5개인데
가입 러시가 오면 **여기가 먼저 막힌다.**

  **`ƒ` 는 DB 를 때린다는 뜻이 아니다.** 그 페이지들은 `'use client'` 라 서버에서 DB 를 안 읽는다.
  `ƒ` 가 뜻하는 건 **방문 한 번마다 람다가 깨어나 「모두에게 똑같은 빈 껍데기」를 만든다**는 것이다.
  천 명이면 람다가 천 번 깬다. `respond.ts` 31행이 이미 적어 둔
  *"함수가 식어 있으면 첫 요청이 10초"* 가 여기서 나온다.
  **`generateStaticParams` 가 저장소에 하나도 없어서** 동적 세그먼트가 전부 `ƒ` 로 떨어졌다.
  **원래 굳을 수 있는 화면들이다.** 굳히면 홈이 얻은 것(엣지가 다 받아 냄)을 나머지가 그대로 얻는다.
- 무엇을:
  1. 화면 다섯의 껍데기를 **굳힌다.** `ƒ` → `●` 또는 `○`
  2. **껍데기만 굳는다.** 데이터는 지금처럼 클라이언트가 API 로 받아 온다 —
     그 API 는 `okPublic` 이 이미 엣지에서 받아 내고 있다 (34개 · 오세라 확인)
  3. ⚠ **이게 실제로 `●` 로 바뀌는지는 아무도 확인 안 했다** `[미확인]`.
     오세라는 **지금 상태만** 쟀다. 안 바뀌면 **안 바뀐다고 적고 왜인지 밝혀라.** 억지로 만들지 마라
  4. ⚠ 오세라의 단서 — `board/[category]` 가 `ƒ` 라서 `useSearchParams` 의 Suspense 문제가
     빌드를 안 깼다. **게시판을 굳히려 하면 그때 터진다.** 게시판은 이 판에서 건드리지 마라
- 하지 말 것:
  - 화면이 보여 주는 값을 바꾸지 않는다. **껍데기 렌더 방식만** 바꾼다
  - 서버에서 DB 를 읽게 만들지 마라. 지금 안 읽는 것이 장점이다
  - 게시판(`board/**`)을 건드리지 않는다
  - 굳혀서 **로그인 상태 표시가 깨지면 안 된다** — GNB 가 사람마다 달라야 한다
- 어떻게 확인하나:
  1. **전/후 빌드 표** — `pnpm build` 출력의 `○ ● ƒ` 개수를 전/후로 적는다.
     화면 6개가 각각 무엇이 됐는지 표로
  2. **화면이 안 변했다** — 다섯 화면을 열어 **보이는 항목 수를 전/후로 세어** 같은지 확인
  3. **로그인 표시가 산다** — 로그인한 상태와 안 한 상태로 각각 열어 GNB 가 다르게 나오는지 확인.
     같게 나오면 실패다 (굳히면서 로그인 상태까지 굳은 것이다)
  4. **첫 요청이 빨라졌다** — 배포 뒤 각 화면을 **찬 상태에서** 한 번씩 재서 전/후를 밀리초로.
     오세라가 든 「식어 있으면 10초」가 줄어야 한다
  5. `x-vercel-cache` 를 5회씩 재서 HIT 비율을 적는다
  6. `pnpm typecheck` 8/8 · `pnpm vitest run --no-file-parallelism` 초록

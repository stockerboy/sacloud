## 4. 오늘 해결한 큰 문제 셋 — 다시 겪지 마라

### ① 사이트가 하루 종일 500 이었다 → **하드웨어였다**

```
증상   /api/home/top · /api/leagues/*/clans · /api/eggs/broken 이 20초 뒤 500
원인   Supabase 컴퓨트가 **Nano** 였다. CPU 93% · 메모리 0.5GB 인데 데이터가 2.9GB
       중계기(Supavisor) 풀 크기가 **15** 로 묶여 있었다
해결   ① 풀 크기 15 → **30**
       ② 컴퓨트 Nano → **MICRO** (같은 값. 「Free Upgrade」 배지가 붙어 있었다)
결과   `SELECT 1` 이 **31.8초 → 0.48초**. 66배
```

⚠ **Pro 요금제를 결제해도 이 값들은 자동으로 안 커진다.** 대시보드에서 사람이 올려야 한다.

### ② `Prisma.sql` 을 겹쳐 쓰면 **번들 안에서만** 깨진다

```
증상   선수 기록실이 500. `syntax error at or near "$4"`
       그런데 `tsx` 로 같은 함수를 직접 부르면 **성공**한다 (로컬 재현 불가)
원인   Prisma 는 끼워 넣은 값이 `Sql` 인지 `instanceof` 로 판별한다.
       번들러가 Prisma 런타임 사본을 두 벌 만들면 그 판별이 어긋나,
       `…::timestamp` 조각이 통째로 **값 하나**가 되어 SQL 이 부서진다
해결   `apps/web/lib/server/queries/playerLadderRows.ts` — 끼워 넣는 것은 늘 **값 하나**뿐이고
       캐스트는 질의문에 리터럴로 적는다
```

**다른 `$queryRaw` 에도 같은 덫이 있을 수 있다.** `Prisma.sql`/`Prisma.empty` 를
템플릿 안에 끼워 넣는 곳을 찾으면 의심해라.

### ③ 코드메드가 만든 **캐시 키 충돌** — 하마터면 남의 기록이 나갈 뻔했다

`guardPublic` 을 32곳에 일괄 적용할 때, 정규식이 `_request`(밑줄)를 못 알아봐서
**매개변수가 있는 16경로가 전부 같은 기억 칸**을 쓰고 있었다. 고쳤다.

**교훈: 일괄 치환 뒤에는 결과를 한 줄씩 눈으로 확인해라.**
